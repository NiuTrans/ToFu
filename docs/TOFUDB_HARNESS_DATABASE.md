# TofuDB：面向长任务的执行数据库

本文拥有 Harness 数据库架构迭代的目标、比较方法和解释边界。
生产存储契约仍由 [Storage](STORAGE.md)、[原生存储](STORAGE_TOFUDB.md)
和机器可读合同定义；下面区分已接入生产代码的优化与独立实验，不增加公共 API。

## 设计目标

让一个 Agent 工作数天、保留十万步历史、同时探索数百条路径、经历进程崩溃后，
推进下一步的成本仍主要取决于**新增工作**。这是 TofuDB 要争取的架构优势。
通用单行读写可以继续竞争；长任务的复杂度、并行探索成本和可靠推进能力决定主攻方向。

对外的产品命题是：**TofuDB 为持续运行的智能体保存可验证的执行状态，让探索共享历史、
推进只处理变化、恢复重用已确认的工作。** 自研引擎的价值必须由这些能力的端到端成本
证明；相同算法在 SQLite 上也成立时，继续追问物理布局、并行提交和恢复是否还能胜出。

| 高悬目标 | 要消除的重复工作 | 本轮可验证的边界 |
|---|---|---|
| 长任务下一步成本主要取决于新增工作 | 每次续读与检查点推进重新验证全部历史 | 生产上下文认证前沿；首次认证和重开另计 |
| 数百条探索路径共享同一过去 | 按分支复制完整历史和派生状态 | fork 元数据写入数与真实存储增长 |
| 事件更新只处理变化的投影 | 每个小事件重新解码未变化的大段历史 | 生产单事件 witness；保留原 checkpoint 阈值 |
| 独立 Agent 利用更多 CPU 同时推进 | 全局实体根与提交路径上的串行工作 | 已实现的独立分域根原型；尚未接入应用 authority |
| 重启成本取决于恢复前沿 | 重算全部历史和已确认工具结果 | 本轮只验证确认后恢复；前沿恢复仍待接入 |

Problem：围绕一次读写减少拷贝、调整连接或提前读取版本，不能消除整个任务不断重复的工作。
此前上下文续读只物化后缀，却仍遍历所有历史头并重算前缀摘要；连续推进时，累计头部
检查工作可能随任务长度呈平方增长。`turn.event.record` 已有原子事务，WAL 也已有
合并持久化，给现有能力重新命名并不会改变这些成本。

Decision：在现有 authority 中接入认证前沿与增量投影；以独立分域根原型验证下一层并行提交。
不可变执行图保留为分支共享的实验。先用工作量和正确性证明结构改变，再测同语义的物理引擎差异。
量级改善是研究目标，不是对尚未实现系统的性能声明。

Alternatives：继续只做局部微优化不能改变增长曲线；用弱 SQLite 基线会错误归因；
立即重写整个引擎会同时失去正确性参照和因果归因。现有 authority、WAL、故障注入、
owner 边界和语义执行器提供了构建新原语的基础。

## 执行图与增量上下文

把不可变的上下文片段、输入证据和父节点关系保存在共享图中。一个分支的可变状态是
受 CAS 保护的 head、generation 和 epoch；创建分支只增加 head，分支继续推进只写差量。
同一历史不应因为探索了 256 条路径就复制 256 份。

已经确认的祖先可以作为续读边界：沿当前 head 读取新增节点，验证其确实回到该祖先。
对于追加历史，读取 delta 个片段的逻辑工作与 delta 成比例，另计底层索引查找成本；
它不再需要从第一条历史开始验证。完整输出仍必须支付输出字节本身的成本。

这不是任意旧投影都永远有效的承诺。编辑、删除、压缩、更换投影规则和选择另一条路径，
都可能改变历史的解释。它们必须原子推进 epoch 或产生定义明确的修正 delta；旧 token
失效后重建。token 绑定 tenant、owner、branch、epoch 和投影版本，不能成为越权读取凭据。
generation 负责拒绝 head 回到相同内容后的 ABA 写入。共享节点的回收需要完整可达性证据。

生产中的 immutable blocks、快照、continuation、Turn replay 是可复用基础，但当前
只读 persistent snapshot 不是可写 branch；其创建可能触发 overlay 合并。
不能把已有 snapshot 的存在当作常数成本分叉已经落地。

已接入生产的 [上下文前沿](TOFUDB_CONTEXT_READ.md) 直接复用原有 lane-directory value：
authority 验证真实历史后保存有界 SHA-256 中间状态与终点。后续 `turn.context.read` 和
`model_continuation.put` 都从已认证终点继续计算，保持公开 v2 digest 完全相同。
历史编辑在同一事务内清除证书；展示性编辑保留；删除与压缩沿原有生命周期清理。
证书绑定 scope 和 authority-open epoch。重开后的读取完整验证，第一次推进保存完整重铸；
不相信旧 writer 可能遗漏的失效通知，也不在启动时扫描全部会话。

## 执行帧

数据库的优化单位应能表达一次已经就绪的执行推进：状态变化、顺序事件、恢复前沿和
相关凭据。对于允许共享同一持久化边界的输入，逐项验证并保留顺序与 replay，最终投影
和派生索引只发布一次。帧内 N 次事件不应必然导致 N 次完整投影物化。

当前 `turn.event.record` 已经原子更新 Turn、Attempt、恢复索引、事件日志和会话同步；
terminal 还处理 continuation 与队列确认。因此本实验要消除的是**重复派生工作**，
不能把“放进一个事务”包装成首次获得原子性。

真实 producer 已将就绪 raw events 合并到一次 `turn.event.record`，编译器产生一个 IR step。
因此本轮生产改进是给已有投影 head 保存 authority 铸造的大小、类型与规范化证据，
让符合条件的单事件补丁跳过未变化 checkpoint 的解码。空 phase、fallbackModel 等真实
producer 请求可以走此路径；缺失证据、嵌套或工具变化及 checkpoint 阈值走完整路径。
原 text-tail 快路径和 64-patch/bytes 阈值继续生效，首次铸证与周期性重建成本必须计入。

只能组合已经到达、允许共享持久化边界的输入。外部 effect、强制 flush、不同权限、
需要独立确认的步骤必须切帧。所有输入的持久化确认在对应 WAL 证据之后；不能等待
未来事件来凑批、提前 ACK，或删除中间 replay。每个会话每秒一个 phase 的负载可能
没有可折叠的同会话事件，它必须保留为无收益甚至退化的对照。

## 并行执行与恢复的下一层设计

前两项原语为更大的物理结构变化提供基础：**每个执行域拥有自己的不可变状态根，
整个数据库共享一个原子提交决定日志**。同一域内维护顺序，独立域在不同 CPU 上验证
和构造后继根；一次跨域提交包含所有受影响域的旧根、新根和相关凭据。持久化后的
提交决定才允许这些根作为一个集合对外可见。

全局提交路径的工作应尽量收敛到冲突域的版本验证和提交描述符发布，昂贵的状态折叠、
编码和索引构造在域内并行完成。读者使用同一已提交前沿，不能组合未提交根或不同
提交时刻的跨域状态。恢复也只重放有完整提交决定的根集合。共享预算、消息交接和
分支选择会形成真实依赖，必须计入跨域成本，不能靠降级成最终一致性获取吞吐。

提交协议需要明确四个阶段：读取同一已提交前沿并记录依赖根；并行构造不可变后继根；
重新验证全部读写依赖并持久化提交决定；原子发布新前沿后回复成功。崩溃后未被提交
决定引用的准备结果不能对外可见，回收也不能触及任何存活分支或恢复前沿。热点根仍有
真实串行依赖；研究目标是缩小必须串行的工作，而不是声称冲突能够凭空消失。

实验分支的选择还必须重新验证当前权限、预算与外部 effect 的幂等凭据。共享历史
不代表共享执行授权，也不代表任意两条已产生外部效果的路径能够自动合并。

当前原生路径已经有并行准备、不可变页面和全局提交验证；它们仍汇入同一 authority
的实体根和提交路径。增加线程池并不等于完成了以上改变。
[分域根原型](TOFUDB_DOMAIN_ROOTS.md) 已实现独立准备、所有读依赖验证与单前沿原子发布，
使用现有 raw Engine 的一个 Strict WAL 提交；相同 Rust 页树与准备算法也运行在单文件
SQLite WAL/FULL 上。它不替代生产 Entity/authority，尚未实现 GC 或恢复前沿压缩。
多个 SQLite 文件加原子协调器的对照仍待完成；尤其检查单域延迟、
热点域、跨域事务比例和重启成本。只有在相同持久化与原子性条件下证明收益，才形成
自研物理引擎的证据。独立准备可以并行，不等于持久化 writer 已经并行。

分域不是预定答案。另一候选是在共享索引上采用更细的版本验证与 epoch 提交；
[Silo 原始论文](https://people.csail.mit.edu/stephentu/papers/silo.pdf) 的比较表明，
分区倾斜或频繁跨分区事务会改变优劣。Agent 家族的共享父任务、预算和消息可能成为
这样的热点，必须把这些负载加入分域实验。

执行图也应成为恢复前沿的依据：已确认的模型输出、工具结果和状态变化可以重用，
未决外部操作要保留“结果未知”。数据库事务可以原子保存 effect intent 与内部状态，
却不能替任意远端工具保证只执行一次。远端幂等键、结果查询或人工核对仍是闭合
外部副作用的必要协议。沙盒分支不能继承真实用户的执行权限。

这两项属于尚待生产实现的架构方向。本轮原型不会自动改变实际 Agent 调度、工具授权、
资金结算或恢复策略。

## 对照实验必须回答三个不同问题

| 问题 | 必须比较 | 能得出的结论 |
|---|---|---|
| 数据模型是否改变增长曲线？ | 同引擎，全前缀验证与图后缀验证 | Harness 算法收益 |
| 自研物理引擎是否必要？ | 同语言、同图算法，原生 authority 与 SQLite | 指定操作下的引擎收益或差距 |
| 用户任务是否更强？ | 同模型、同工具、同任务的真实 Harness | 完成率、耗时、恢复损失与成本 |

SQLite 对照也必须有共享 node 表、branch head、CAS、增量查询和事务；不允许只用
全历史拷贝充当对手。持久化写入使用 WAL/FULL，并记录实际版本、配置、事务边界、
源代码与二进制身份。SQLite 多文件分区也可并行，跨文件一致性成本必须进入比较。

预定研究规模是 1,000 / 10,000 / 100,000 个历史节点，1 / 32 / 256 个新增节点，
以及 32 / 256 条共享历史分支。记录实际执行的矩阵；未运行的规模不能出现在结论中。
时钟样本使用独立进程交替顺序；建库、预热、读、写、关闭、重开分别记账。
逻辑 node 访问数、索引/page 工作和物理 I/O 是三个不同量，不能互相替代。

验收优先级：

1. owner、CAS、祖先与 epoch 拒绝正确；事务失败不留部分状态；确认后重开内容精确。
2. 固定 delta 增长历史，证明 prefix 工作消失；fork 的新增存储不随共享历史大小线性增长。
3. 同算法的强 SQLite 对照；保留单次操作、尾延迟、写入放大和内存退化。
4. 真实 Turn 的编辑、删除、压缩、分叉与 checkpoint 原子接入后，再跑原有容量/恢复矩阵。
5. 真实长任务评价完成率与时间，才可以声称 Harness 的整体优势。

局部原型通过第 1—3 项，仍不能代表第 4—5 项完成。

## 当前实验实现

[执行图原型](../benchmarks/harness_graph/README.md) 已接入真实原生 AuthorityDatabase；
[SQLite 参考适配器](../benchmarks/harness_sqlite_reference.rs) 在同一 Rust 程序中执行
完全相同的图协议。续读使用持久化 witness 验证 token，读取新增节点并校验祖先。
该算法的逻辑访问数是 `delta + 3`，每次访问仍支付后端索引成本；fork 是固定 4 次读、
3 次写，并非物理 CPU 或 I/O 的无条件常数成本。当前片段是不可变文本，尚未接入
实际 Turn 的编辑、压缩、provider 上下文、授权或保留/回收策略。

[增量投影实现与执行帧实验](TOFUDB_EXECUTION_FRAMES.md) 共用普通事件的
checkpoint/patch-chain owner。单事件 witness 已进入 `turn.event.record`；多步 IR 帧
仍为 `cfg(test)` 实验，不能用它的批量结果解释真实 producer 已获得的收益。
普通 semantic outbox 的捕获与原操作 payload 保持原子；本轮没有认证通用 native
被动目标重放能力，不能将 outbox 归档或主动重新执行称为被动恢复证明。

生产上下文的工作量验证：历史 8/128/2,048 条，新增两个 Turn 后，续读与推进保存
各检查 **3 条 header**；首次认证分别扫描 8/128/2,048 条。重开后先完整认证，
之后恢复后缀工作量。追加仍新增一次 directory 读取，必须计入完整推进成本。
独立公开接口测试还实际执行“新 writer 建证、旧 f70 writer 编辑历史、新 writer 重开”，
确认旧证书不能掩盖历史变化。

分域原型把页面构造移出提交锁，并用持久目录增量替换根。已提交 receipt 采用短读锁，
不再被另一个提交的 fsync 挡住；测试真正阻塞 WAL `sync_data` 时，其他域仍能准备。
所有只读 predicate 也参与提交验证，读者持有单一不可变前沿，跨域更新一同可见。
页面字节仍由同一个 Engine WAL 携带，重新哈希与持久化的串行成本没有消失。

正式比较分开回答：生产 context 操作的 before/after/SQLite 算法收益、真实 producer
事件周期的投影收益，以及同算法分域页树的 native/SQLite 引擎差异。
三者都不代替同模型、同工具长任务的完成率实验。

### 生产上下文：完整推进与冷成本

2026-10-19，冻结 f70 基线及组合候选的 CLI/共享库，在 XFS 临时目录运行真实
native embedded Strict 与 SQLite 3.53.4 WAL/FULL sidecar。两个 native 构建都使用
release、ThinLTO、16 codegen units、mimalloc，profiling 关闭。
每个初始历史规模按 before/after/SQLite/SQLite/after/before 新进程顺序执行；
18 个进程、576 轮推进与 18 次同库重开控制全部完成；各冻结构建起止身份不变，
三臂输入与规范化逻辑数据摘要一致。fixture 使用 `--payload-bytes 64`。
每轮实际追加两个 settled Turn，精确验证公开 v2 proof、返回后缀、checkpoint 与读回值。

下表单位毫秒。完整推进包含两次追加、一次续读、一次保存；每进程取后 31 轮中位数，
再取两进程中位数。第 0 轮的追加属于 fixture setup，不冒充零追加成本。
初始历史在每个进程中随 32 轮推进增加 64 个 Turn；这里没有长任务完成率或尾延迟 SLO 声明。

|---:|---:|---:|---:|---:|
| 8 | 0.917 | 0.769 | 4.330 | 1.19 倍 |
| 1,024 | 2.606 | 0.835 | 12.217 | 3.12 倍 |
| 8,192 | 14.776 | 1.218 | 54.117 | 12.13 倍 |

8,192 条历史的续读为 13.462→0.140 ms；续读加保存为 13.856→0.485 ms。
新路径没有把每次 O(N) 工作转移到保存：热保存为 0.363→0.334 ms。
首次保存包含认证，从 3.542 增至 14.781 ms。

新公开接口用例的 SQLite 基线 9 项、测量拒绝错误工作 10 项也已通过。
完整原生 gate 在稳定隔离源码上执行；共享 checkout 仍存在其他并行工作，不能把这个
结果解释为整座应用所有未提交修改都已通过测试。

### 生产事件：跨独立提交重用投影证据

真实 producer 形状的 fixture 同时包含 256 KiB content 和匹配的 text segment。
相同最终构建中关闭/启用 witness，直接计时 authority 事件执行与每次 Strict commit；
不含 Python、传输、公开 admission/compiler 和 fixture 构造。这里使用 opt-level 3、
LTO=false 的组件测试构建，不能冒充 ThinLTO 应用端到端时间。
12 个条件各执行 control/runtime/runtime/control 新进程，48 进程、576 样本、
7,296 次独立持久化提交全部通过完整状态、响应、物理 checkpoint 边界与重开校验。

下表包含首次铸证与原有 64-patch checkpoint 周期；单位毫秒，每格是两个进程
合计 24 个样本的中位数。64 个事件仍各自提交，没有把它们合并成一次确认。

| 连续 64 次事件的输入 | 普通路径 P50 | 增量投影 P50 | 倍率 |
|---|---:|---:|---:|
| 可压缩 | 90.619 | 23.104 | 3.92 倍 |
| 高熵 | 106.973 | 23.536 | 4.54 倍 |

该冷周期的 checkpoint 解码量从 33,595,584 降至 1,049,862 字节，旧 patch 重放
从 2,080 降至 65 次。已建立证据的单事件约快 3.91–4.75 倍；最终构建的首次
单事件未见原先回归。完整 12 行、CPU 与两轮原始记录见 [投影证据](TOFUDB_EXECUTION_FRAMES.md)。

代价仍在：冷 64 事件的 WAL 增加 9.6–13.6%；已建立证据后的首次嵌套/工具回退
慢 **24.0–31.9%**。`phase → 文本流/工具 → phase` 交替诊断没有消除物化，不能套用
连续 phase 的倍率。原型中删除重复解码的优势已进入生产 owner；尚未证明所有事件
混合或完整 Agent 任务都更快。SQLite 同样可以实现这类证据驱动算法。

### 分域根：同算法持久化与并行边界

独立原型在相同 Rust 不可变页树、读依赖验证、重试与原子决定协议下，对照 native
Strict WAL 与 SQLite 3.53.4 单文件 WAL/FULL。1/4/8 workers、独立域/单热点/100%
跨域共 9 个条件，按 native/SQL/SQL/native 执行 36 个进程，每腿 1,024 次成功事务。
**36,864 次成功事务**全部通过逐步状态、序列化顺序、只读依赖、receipt 和重开核验。

原生吞吐在这 9 个条件下为 SQLite 的 **1.77–2.62 倍**。独立域 1/4/8 workers
约为 5,172/6,817/6,267 次成功事务/秒；相应 SQLite 约为 2,919/3,133/2,944。
这是同算法持久化组件的证据，不是生产 Entity/Turn 的性能倍数；两边都有并行准备。

多核扩展仍未达到目标：原生 1→4 workers 仅约快 32%，4→8 反而慢约 8%。
8-worker 热点每腿发生约 7,100 次冲突，平均 CPU/成功事务升至单 worker 的 3.51 倍；
原生重开 202–237 ms，慢于 SQLite 的 152–160 ms。单个 WAL 仍携带并处理全部页字节，
下一项高影响实验应拆开持久私有页准备与原子决定，同时证明孤儿回收、崩溃恢复与跨域
一致性；现有结果不支持声称已经消除了串行提交瓶颈。

协议、全部 9 行对照、尾延迟与负例见 [分域根实验](TOFUDB_DOMAIN_ROOTS.md)。
debug/release 各 10 项协议测试和 7 项独立 Python oracle 通过；原始计时、预先声明的
矩阵与冻结程序分别位于本轮 `domain-formal/`、`domain-validation/`。

### 图实验：增长曲线与引擎差异

独立 Python 模型在 release 图程序上对两种后端分别验证了 659 个接受请求与 205 个
预期拒绝请求，包含 61 条分支、344 个命令凭据，确认后真实 SIGKILL 和重开恢复。
两种后端的逻辑工作计数完全一致。行写入故障注入另验证 node、head、witness 和
receipt 不会留下部分提交。这些测试不替代任意存储设备的断电验证。

2026-10-19 的第一轮 release 测量使用 SQLite **3.46.0**（Rust 依赖的 bundled 版本）。
主矩阵为 D=32、N=1k/100k 时 B=1/32/256、N=10k 时 B=1；另测 N=100k、B=32
的 D=1/256。64 个独立进程均正常退出，三份 manifest 完整，输出、逻辑工作量和
源代码/二进制身份检查全部通过。主矩阵每个后端有两个新进程，每进程 12 对交替
读取；补充矩阵每进程 8 对。下表为同图算法的 repeated 样本中位数，单位微秒。

| 历史 N | 分支 B | 新增 D | TofuDB | SQLite 3.46.0 | 每次逻辑 get（双方一致） |
|---:|---:|---:|---:|---:|---:|
| 1,000 | 1 | 32 | 80.05 | 118.69 | 35 |
| 1,000 | 32 | 32 | 88.86 | 135.71 | 35 |
| 1,000 | 256 | 32 | 129.26 | 155.96 | 35 |
| 10,000 | 1 | 32 | 95.27 | 123.97 | 35 |
| 100,000 | 1 | 32 | 110.42 | 151.81 | 35 |
| 100,000 | 32 | 32 | 131.90 | 178.55 | 35 |
| 100,000 | 256 | 32 | 323.66 | 176.89 | 35 |
| 100,000 | 32 | 1 | 23.59 | 49.24 | 4 |
| 100,000 | 32 | 256 | 1,427.86 | 1,260.41 | 259 |

核心结果是：历史扩大 100 倍，D=32 的 node 读取始终是 32、前缀 header 读取始终为 0。
fork 始终为 4 次 get、3 次 put；各行的物理索引和内存代价仍然存在。
TofuDB 在这轮多数小增量场景中较快，但 B=256 和 D=256 均出现反转。
不能把固定逻辑访问数解释成实际延迟完全不增长，也不能把单台机器的样本当作尾延迟 SLO。

代价同样保留：100k base 单独建库耗时 native 32.32 秒、SQLite 26.58 秒；主矩阵
最终 B=256 时，关闭后文件总量分别约 3.236 GB、0.639 GB，读取进程最高 VmHWM
约 220,288 KiB、57,984 KiB。native 直接使用 authority 默认缓存与 overlay，
没有 daemon 的后台维护/GC；SQLite 设置 48 MiB page cache。以上是整个实验目录
和进程的观察值，不是等内存预算实验，也不是经过回收后的 live 数据空间比较。
物理布局、旧页回收与恢复成本因此成为下一轮必须单独验证的研究问题。

只读文件分类进一步定位了该空间：约 1.757 GB 属于 `TDBHIS01` 事务历史块，
约 1.455 GB 属于 payload segments，活动 WAL、CONTROL 与 hints 合计约 21.7 MB。
现有引擎已有 history pruning、payload 迁移和后台 GC，本实验的直接入口没有调度它们。
未做可达性分析，不能宣称上述历史块都是垃圾，更不能据此预测 GC 能节省多少。
为区分未运行维护与结构性空间成本，本轮在独立副本上执行了现有维护入口，并核对
图状态、凭据和 pin 条件；维护后的读写延迟仍需另做正式测量。

副本控制调用公开 `compact_history(64)`，再运行最多 16 轮、软预算
120 秒的现有 GC。历史段从 531 保留到 64，目录由 3,236,208,045 降至
1,799,826,721 字节，减少 44.38%。GC 仍报告 `remaining=true`，所以这不是稳定态
live 空间，也不是全部可回收量。五个 namespace 的 **433,539** 行按稳定顺序、带
字段长度前缀的完整哈希相同；前后各 532 个 API 请求的响应字节相同，包含主历史
10 万片段全文、全部 256 分支的 head/后缀，以及命令重放和冲突拒绝。

原 fixture 的文件大小/mtime 清单保持不变。副本没有增加历史 snapshot/pin；该条件
不外推到任意 pin 保留策略。维护与测试编译并行，compaction 2.44 秒、GC 43.35 秒
只作为本次诊断成本保存，不作正式吞吐或延迟结果。证据在同父目录
`graph-maintenance/`，原始 5.06 倍空间反例与有界维护后的 2.815 倍观察值同时保留。

一个值得继续验证的物理设计是：让原生执行记录直接承载不可变片段、父引用和提交
凭据，派生根作为可重建索引，缩短从 branch head 到新增内容的读取路径。它需要证明
哪些通用事务历史仍是恢复必需、哪些证据可以共享，避免图历史和引擎历史重复保留。
这会涉及持久格式、回收和恢复协议，尚未实现；不能以删除必需证据换取漂亮的空间数值。

原始证据在运行机器的 `data/benchmarks/tofudb-harness-database-20261019/graph-346/`，
包含逐进程输出、建库/扩展/重开/关闭、每个 leg 的中位数、源文件哈希与反例。
源码组合为图提交 `44be4bc4f` 加 SQLite 适配器提交 `8697500ea`；单独检出前一个
提交不足以构建 SQLite 参考。合并后的仓库包含二者，精确测量身份以 manifest 为准。

### 较新 SQLite 的关键对照

相同 Rust 图源码进一步链接本机已有的 SQLite **3.53.4**，冻结二进制及 7 个动态库。
原生和 SQLite 在同一新二进制中运行；WAL/FULL、48 MiB cache、4 KiB page、mmap=0
均读回验证。9 项 Rust 测试和独立 512 步双后端 oracle 再次通过。该构建与 bundled
3.46.0 的编译选项也不同，所以这是更强的对手配置，不能将差异只归因于版本号。

N=1k/100k、B=32、D=32 的 16 个正式进程全部正常退出，24 组 exact output、
48 组 logical work 一致，源码、二进制、动态库结束身份匹配。

| 历史 N | TofuDB repeated P50（微秒） | SQLite 3.53.4 repeated P50（微秒） |
|---:|---:|---:|
| 1,000 | 88.27 | 120.81 |
| 100,000 | 124.40 | 181.91 |

这里每格合并两个进程、共 24 个 repeated 样本。100k 的原生两腿中位数为
124.40/124.49 微秒，SQLite 两腿为 262.39/181.17 微秒，保留进程之间的离散。
该点原生的 pooled 读取中位数约低 32%，但 open 为 250/254 毫秒，而 SQLite 为
0.9/0.4 毫秒；最高 VmHWM 约 199.6/57.9 MiB；关闭后空间约 2850.8/568.3 MiB。
它证明了特定增量读取的优势，同时保留重开、内存和未维护空间成本。3.53.4 本轮
没有重复 B=256 或 D=256；前一轮的反例仍然有效，不能把这两点扩写成全面胜利。

构建、动态库与 oracle 证据位于运行机器的
`data/benchmarks/tofudb-harness-database-20261019/sqlite-3534-reference/`；
正式矩阵位于同父目录的 `graph-3534/`。

## 可借鉴的一手研究

- [TigerBeetle requests](https://docs.tigerbeetle.com/coding/requests/)：请求批量执行、
  顺序可见与持久化确认可以共同设计，但整个请求提交不代表每个业务事件都成功。
- [DBSP](https://arxiv.org/abs/2203.16684)：以差量计算维护派生状态提供了可借鉴的代数；
  不自动使任意 LLM 摘要或任意工具具备增量语义。
- [Calvin](https://dsf.berkeley.edu/cs286/papers/calvin-sigmod2012.pdf)：预先确定事务顺序
  和依赖是一条减少协调的路线；动态读写集必须有发现与重新验证协议。
- [SQLite WAL](https://www.sqlite.org/wal.html)：单 WAL 的 writer 串行边界，以及
  多个 ATTACH 数据库在 WAL 模式下不具备整个集合原子性，是分域设计需要正面比较的边界。

这些是已存在的思想。TofuDB 的研究命题是将它们与 Agent 的执行、上下文和恢复语义
共同设计，交付可复现的组合优势；不主张发明了事件溯源、Merkle 图或批量事务。
