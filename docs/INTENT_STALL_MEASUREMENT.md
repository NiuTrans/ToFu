# 意图滞留补推：前提测量与设计稿

> **状态：已实施（owner 拍板 D1 + D2 一起做）。** epic `pt_33ba079f5cea4841`，实现 commit `5edd7d2e`。
> 本文前半是当初的测量（保留作为决策依据），§7 记录最终落地形态。
> 纪律来源：charter「采纳一个机制前，先用生产数据验证它针对的模式真实存在」。

## 0. 一句话结论

**该做，但不能只用票里授权的那一条结构判据 —— 实测它自己有 60% 误报。**
补推必须是**四条判据串联**（结构 A∧B + 可重试性 C + 交还语义 D），少任何一条都会把
「合规收尾」或「工具根本不存在」当成滞留去自动补推。

**7 天真正的补推目标 = 8 例**（不是结构命中的 20，也不是「非 handback/VU」的 11 —
后者还含 3 例不可重试）。

## 1. 现象与铁证样本

用户报「对话没头没脑地结束了，Opus 5 好多都这样」。

铁证：conv `ms34yw0k74o2lq` R18（2026-07-27 21:25:27，app.log 实锤
`finish_reason=stop ... tool_calls=0`）。链条：

1. R17 的 `run_command` 被前置钩子 **正确** 拦下（`rm -rf "$w"` 回退分支含未展开变量）；
2. R18 降级重试（首试 key_0 空转 130s、换 key_1 冷缓存、`build_body` 剥掉未签名思维）；
3. 模型返回 97 字符 “Let me use explicit paths only.” + `stop` + **0 工具调用**；
4. 任务循环按「stop = 收工」契约正常结束。**没有崩溃、没有错误、没有丢帧**
   （`raw_sse_anomaly.log` 对该 trace 零记录，7 个 SSE 检测器全部沉默）。

主循环没有任何一层察觉「临终文本表达了未完成意图」。endpoint 模式的 critic 有
`CONTINUE_WORKER` 判据管这个，**主循环没有**。

## 2. 度量陷阱（我在本轮栽过，务必记住）

**`task_results.tool_rounds` 不能作为本测量的数据源。**

铁证样本在该表里 `tool_rounds` 长度为 **0**（`apiRounds` 有完整 18 轮），
全库 7 天 1735 行里 **985 行（57%）** 同样为空 —— 第一版扫描因此只报出
2 例、且**漏掉了铁证样本本身**。

> 按 charter：**「检测器不报 = 检测器没在找」。一个「干净」结果必须用独立方法
> 交叉验证后才可信。** 正是拿铁证样本去反查检测器，才发现数据源选错了。

**正确数据源：`conversations.messages[].toolRounds`**（前端渲染同一份），
配 `finishReason` / `model` / `content`。7 天窗口 = 256 个会话、962 条
assistant 消息。

## 3. 测量结果（7 天全量，2026-07-27）

### 3.1 结构判据的原始命中

判据 = 「上一轮工具 rejected/errored」 **且** 「本轮纯文本 + `finish=stop` + 0 工具调用」。

| 漏斗 | 数 |
|---|---|
| 候选（stop + 有 toolRounds + 有正文） | 942 |
| 上一轮工具正常 → 排除 | 922 |
| **结构命中** | **20** |

### 3.2 ★ 结构命中里有 60% 是误报

| 分类 | 数 | 含义 | 该补推？ |
|---|---|---|---|
| `NUDGE_TARGET` | **8** | 真滞留且**可重试**（工具在集内，只是这次形式被拒/出错） | ✅ 唯一目标 |
| `handback` | 5 | 合规「把球交还人类」（在问问题/等拍板） | ❌ 抢答用户 |
| `VU_turn` | 4 | 自动化回合的既定收尾（带 `[PROGRESS:` / `[VU:`） | ❌ |
| `NON_RETRYABLE` | 3 | 工具**不在本轮工具集**（见 §4） | ❌ 无限循环 |

**★ 纯结构判据（票面授权的 A∧B）误报率 = 12/20 = 60%。**
即：只按票面判据上线，**六成补推打在不该补的轮次上** —— 一半是抢答正在等回话的
用户，另有 3 例会让模型反复重试一个它永远拿不到的工具。

> **修正记录（诚实起见）：** 本文初版把 `genuine_stall = 11` 整体报成「补推的真目标」，
> 而 §4 又从其中排除了 3 例不可重试 —— 两节自相矛盾。兄弟会话独立指出
> 「`rejected` 不是一个物种、至少两种且只有一种可重试」后，我把 C 轴做成**结构判据**
> （按拒绝原因是否含「工具不在本轮工具集」分流）重算，才得到 8 / 3 的干净切分。
> **两个数都变了：目标 11→8、误报率 45%→60%。**

### 3.3 按模型线（四分类精确计数）

| 模型线 | assistant 消息 | 结构命中 | **补推目标** | 不可重试 | handback | VU | 补推目标率 |
|---|---|---|---|---|---|---|---|
| `yuju-claude-opus-5-evaDaily` | 293 | 7 | **7** | 0 | 0 | 0 | **2.39%** |
| `aws.claude-opus-4.8` | 262 | 9 | **1** | 3 | 1 | 4 | 0.38% |
| `aws.claude-opus-4.7` | 136 | 3 | 0 | 0 | 3 | 0 | 0.00% |
| `kimi-k3` | 423 | 1 | 0 | 0 | 1 | 0 | 0.00% |

**★ 「好多 Opus 5 都这样」比初版结论更成立 —— 但仍不该做成 opus-5 特例。**
- 精确切分后 **8 个补推目标里 7 个是 opus-5**（2.39%），4.8 只剩 1 例（0.38%）：
  **用户的观感是对的，opus-5 确实是这个形状的主要来源**；
- 但 4.8 的 9 个结构命中里 3 例不可重试 + 4 例 VU 收尾 —— 它命中多**不是因为更爱滞留**，
  而是因为它跑的自动化回合多（VU）且撞上过工具集缺失。**两条线的病因不同，**
  这正是初版按 `genuine_stall` 粗算会误判「4.8 也有 4 例」的地方；
- 4.8 仍有 1 例真目标 → **机制必须模型无关**，不能只对 opus-5 生效；
- 兄弟会话用**完全不同的方法**（措辞轴 7 天扫 1712 个 task）独立得到同向结论：
  4.8 = 8 例 ≥ opus-5 = 15 例（其原始率 4.8 7.5% > opus-5 5.0%）。
  **两个独立方法都指向「非 opus-5 独有」，该结论可用。**
- 结论：**补推必须做成模型无关的通用机制**，不能做成 opus-5 特例。

### 3.4 措辞判据已被双向证伪（禁止使用）

- 本轮：`handback` 5 例全部带 “我建议…你定 / 告诉我 / 需要你确认 / 要我 kill 吗”，
  同时又都含 “我会/我直接” 这类第一人称行动词 —— **措辞正则无法区分**。
- 兄弟会话独立测得：53 条带行动意图的末句里 **26 条（49%）** 是交还或否定式，
  真实反例包括 “Give me the go and I'll execute the export + push”、
  “Pick any one of those decisions and I'll implement it immediately”。

**两个方法各自测出 60% / 49% 误报 —— 措辞判据永久否决，写进纪律。**

（注：本轮的 60% 是**纯结构判据**的误报率，兄弟的 49% 是**纯措辞判据**的误报率 ——
两轴各自单独用都不可用，这正是必须四条串联的原因。）

## 4. ★ C 轴：`rejected` 不是一个物种，而是两个，只有一个可重试

（本节的切分由兄弟会话独立提出并与本测量互相印证；它把我初版算错的
「真滞留 = 11」修正成「可重试 8 + 不可重试 3」。）

结构命中里的 `rejected` 必须再分两类，**而且两类的形状完全一样、只能靠拒绝原因区分**：

| 物种 | 实例 | 重试会发生什么 |
|---|---|---|
| **(a) 可重试**：钩子拒的是某个**具体形式**，工具本身在集内 | 铁证样本 R18：`run_command` 因未展开的 `rm -rf "$w"` 被拦，**钩子自己的文案就写着**「Re-issue run_command with that narrower target」 | 换写法真能成 → 补推**有效** |
| **(b) 不可重试**：工具**根本不在本轮工具集** | `project_board_complete` / `code_exec` —— 见下方原文 | 必定再被拒 → 补推**只会烧预算** |

**票面授权的那个形状对 (a) 和 (b) 命中得一模一样精准**，所以光有结构判据救不了：
它**必须同时判别拒绝原因**。(b) 的 3 例实测样本（conv `mrvpzoih636mdx`）：

```
tool='project_board_complete' status=rejected
reason: `project_board_complete` is not a real tool and was NOT executed.
        It is not in the list of tools available to you this turn.
        You have now called this non-existent tool 2 times — STOP calling it.
tool='code_exec' status=rejected
reason: `code_exec` is not a real tool ... Did you mean: schedule_create, produce_video ...
```

**对这类补推 = 逼模型重试一个它永远拿不到的工具 = 无限循环烧钱。**
（本仓 `JOURNAL.md` 顶部的 `CLOSURE-PENDING pt_a4c9d33e` 正是这个形状的存量证据：
实现早已完成，只差一次 `project_board_complete`，而该工具不在自主派单工具集里。）

**判据可结构化，不需要读措辞**：被拒原因属于 `tool_not_available` 类
（工具名不在本轮 dispatched toolset 里）→ 该滞留 **不可重试**，
正确处置是**升级为 typed error envelope 让用户看见**，而不是补推。

> **本轮重算就用的这个分流（可直接落代码）：** 拒绝原文包含
> `is not a real tool` 或 `not in the list of tools available` → 归 (b)。
> 这两串由工具分发层**自己生成**（非模型措辞），故属结构信号；
> 落代码时应换成**分发层的枚举标记**而不是字符串匹配（charter：少用字面锢点）。

按 charter「后端错误透明传递担保」，这类应走 envelope（需注册新 kind），
**属于本票的姊妹票，不在补推范围内。**

## 5. 设计稿（待 owner 拍板，未实施）

### 5.1 判据：四条串联，全部结构化（零措辞匹配）

一个 assistant 收尾轮被判为「应补推」当且仅当：

| # | 判据 | 数据来源 | 作用 |
|---|---|---|---|
| **A** | 上一轮工具 `rejected` 或 `errored`（非零退出 / `notRun` / `badge=blocked`） | `toolRounds[-1]` | 结构信号：刚受挫 |
| **B** | 本轮 `finish=stop` 且 **0 工具调用** 且正文非空 | 轮次结果 | 结构信号：只说不做 |
| **C** | 被拒原因**不属** `tool_not_available` 类 | 拒绝原因分类（§4） | 排除不可重试，防无限循环 |
| **D** | 本轮**未处于等待人类的状态** | 见 5.2 | 排除 handback / VU 收尾 |

A∧B 是票里授权的部分；**C、D 是本轮实测新增的必要条件**。
实测贡献度：缺 **C** 会对 3 例发生无限循环式重试；缺 **D** 会对 9 例（5 handback +
4 VU）抢答。两者相加 = 12/20 = 那个 60% 误报。

### 5.2 ★ D 的实现必须是结构的，不能是措辞的 —— 这是唯一需要 owner 拍板的点

「是否在等人类」有两条候选实现，我倾向 **D1**：

| 方案 | 做法 | 代价 / 风险 |
|---|---|---|
| **D1（推荐）** | 本轮是否调用过 `ask_user` / `request_human_input`，或任务是否处于 human-guidance 待答状态 —— **纯状态查询，零文本解析** | 覆盖不全：`handback` 5 例中有几例是「用自然语言问」而没调 ask_user 工具，仍会漏判为滞留 |
| D2 | 让模型在收尾轮自报一个结构化终止原因（`awaiting_human` / `done` / `blocked`），补推只在缺该标记时触发 | 需改系统提示 + 轮次契约，是**契约变更**；但它把「我在等你」变成可机检事实，根治 D1 的覆盖缺口 |

**我的判断：先落 D1（零契约变更、可立刻验证），并把 D2 记为后续。**
理由：D1 漏判的后果是「该补推的没补」（回到今天的现状，无新增伤害），
而误报的后果是「抢答用户」（新增伤害）。**宁可漏，不可误。**

### 5.3 补推动作的硬约束（防跑飞）

- **每个 task 至多补推 1 次**（CAS 标记落在 task 上，防 A→补推→又滞留→再补推的链）；
- 补推内容是**结构化系统提示**（「上一轮工具未执行成功，若仍需继续请直接调用工具」），
  **不复述模型措辞**；
- 补推必须计入 `apiRounds` 并可在请求检视器里看见，**不做隐形轮次**；
- 一次补推后仍是纯文本 stop → **停手并按 §4 升级为可见状态**，绝不第三次。

### 5.4 守卫要求（charter：断言结果、必须 NEUTER）

- 夹具用**真实事故时序**：铁证样本 R17 rejected → R18 纯文本 stop（禁止用便于通过的构造值）；
- 断言**后果**而非实现：「A∧B∧C∧D 成立 → 恰好补推 1 次」「handback 样本 → 0 次补推」
  「`tool_not_available` 样本 → 0 次补推且升级为可见」；
- **NEUTER×4**：分别摘掉 A / B / C / D，对应样本必红。摘 C 必须红在
  「对不存在工具发生了补推」这条上 —— 这是无限循环的入口；
- 判据要能区分「修对了」与「以另一种方式修错了」（charter 守卫失效第四态）：
  断言**补推次数与目标集合**，不断言某个字面提示词。

## 7. 实施记录（owner 拍板：D1 + D2 一起做）

**落点：** `lib/tasks_pkg/stream_handler/_intent_stall.py`（分类器）+
`_analyse.py` 的正常收工前接入点。选这里是因为同文件的 todo-continuation
执行器已经是同一形状（append user message + `action='continue'`），复用它的
机制而不新建一套循环控制。

**实现中发现的一个真实排序缺陷（守卫抳出来的）：** 初版按 A→C→D 顺序判定，
而 `ask_user` 成功时它**就是最后一个 tool round** —— 于是 A 读到「上一轮工具正常」
提前返回，D **永远跑不到**。即：最需要 D 的场景恰恰是 D 不可达的场景。
已改为 **D 先于 A** 判定并在代码里写明原因。

**D2 的契约形态（比设计稿预想的更轻）：** 不改全局系统提示。补推文本本身
就告知了 `[END_TURN: awaiting_human|done|blocked]` 的用法——模型只有在**被补推时**
才需要这个出口，平时的收尾不受影响。好处：零常驻 prompt 成本、零契约风险，
且未被补推的会话行为**字节不变**。未知 reason 一律当作「未声明」，
防止模型用任意文本静默掉这道安全网。

**守卫：** `tests/test_intent_stall_nudge.py` 15 条——**四个假阳性类别各一条独立测试**
（聚合测会让抑制器被逐支删掉而套件保持绿）。**NEUTER×6 全咬**：
A（恒判失败）→ 3 红、B（忽略 tool_calls）→ 1 红、C（取消不可重试排除）→ 1 红、
D1（致盲状态探针）→ 1 红、D2（忽略自报）→ 3 红、上限（去掉 1 次封顶）→ 1 红。
相邻环 62/62，干净 committed tree 复验 62/62。
