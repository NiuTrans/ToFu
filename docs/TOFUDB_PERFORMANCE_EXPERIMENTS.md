# TofuDB 性能实验与否决依据

本记录按用户要求保留失败方案，避免重复投入。运行时约束仍由
[性能章程](STORAGE_PERFORMANCE_CHARTER.md) 定义；这里记录假设、证据、
结论及重新尝试的条件，不把单机实验升级为产品保证。
可机读摘要在 实验数据。 归档主锁与空转根因修复已保留；长测收益、小文本尾延迟及内存回退、被纠正的观测方法见归档锁实验。 整块 zlib 编码替换因均值、CPU 和随机尾延迟回退否决；200,889 次完整回读、旧库双向重放及共享锁等待归因见编码器实验。 生产者字节收据证据虽消除转义响应重复扫描，但随机大文本 P99 仍回退，未发布；两轮成对测量、198,880 次完整回读及重放检查见收据证据实验。 收据非物化解析方案同样因端到端回退否决，转义解码成本基本未消失；完整判定、重放和控制数据见收据实验。 直接 Blob 压缩缓冲方案因混合延迟和累计内存回退未采用；八轮完整回读与下一根因（收据策略重复构造响应对象）见编码实验。 私有块发布改为复用不可变分配与绑定身份；长测收益、读取/小文本回退和零命中的缓存假设见私有块实验。 归档锁修复后的收据资格证据复测消除了转义响应重复解析；收益、所有回退及 SQLite 对照见收据复测。 JSON 入口类型分派减少了数值批量写入和点读的客户端成本；数据库收益与只读 UUID 测量修正分开核算，见点读入口实验。 客户端直接解析线程私有响应缓冲区，消除 orjson 路径的一份完整临时副本；配对测量、回退模式、内存边界和失败日志见响应视图实验。
2026-09-30 早期轮次的原生优化候选全部否决；其交付是排队归因报告改进和实验记录。
此前已验证的冲突/范围/JSON 优化作为对照基准 `573d71f7…`。
共享工作区随后出现并行原生修改，本轮未覆盖它们；实验结论仅对应记录的构建。

## 比较规则

- 同一 DolphinFS 卷、严格持久化、嵌入式客户端；1,000 个会话，
  每个会话四块不同的 8 KiB 内容，固定一秒到达间隔，30 秒请求期限。
- 顺序 A/B/B/A，保留慢样本、错误、准确回读和离线完整性结果。
  请求探针采样率均为 1；累计排队时间是多个并发请求之和，不能当作墙钟时间。
- 本轮使用 abandon/reopen 验证；不冒充进程 SIGKILL、断电或长期稳态认证。
- 本文只作 TofuDB 版本间对照。SQLite 原始 SQL 微基准与应用存储调用
  不是同一语义，失败的 SQLite 容量样本也不能作为速度倍率分母。

## 否决：提前开放写入并复制 WAL 窗口后缀

**问题与假设。** 轮转栅栏等待覆盖数据及窗口新增数据持久化。
候选捕获 WAL 前缀，继续接受旧 WAL 新提交，再把窗口后缀复制到新代。
新 WAL 双重同步后才发布 CONTROL，错误仍由旧 CONTROL 拥有旧 WAL；
32 项定向测试覆盖短写、I/O 错误和丢失一次同步，但不能抵消性能回归。

| 流式 P99，秒 | 12.871 | 16.939 | 16.340 | 10.610 |
| 接纳 P99，秒 | 4.984 | 6.628 | 4.821 | 4.015 |

## 否决：只把排空条件改成“覆盖区为空”

**问题。** 这是看似能消除停顿的一行改动。

**否决依据。** 当前正常恢复只从活动 WAL 恢复携带的数据块；历史段虽保存
原始事务字节，却不是活动 WAL payload 恢复的替代路径。窗口块尚未成为
可恢复存储时就删除旧 WAL，会丢失其恢复来源。此方案因不满足恢复约束而
未进入性能试验；没有虚构耗时或声称已实测失败。

**重试条件。** 必须先设计明确、持久且有界的数据依赖关系，证明跨代 WAL
或历史恢复路径、回收顺序和崩溃窗口都安全。仅增加超时、跳过同步或保留
无持久引用的旧文件不满足条件。

## 有效但不足：减少计数冲突、范围假冲突与 JSON 转换

**问题。** 不同会话在共享计数、同一物理叶页上产生无谓冲突；嵌入式入口
还重复解析/序列化 JSON。这些成本容易观测，却不是剩余等待的全部来源。

**决定。** 共享维护在提交阶段执行；范围校验比较范围内的逻辑版本并涵盖
overlay 消失/删除；嵌入式入口传递已验证的原始 JSON 字节。保留 OCC、
请求大小限制、私有准备缓冲和持久化边界。

**结果。** 两组 1,000 会话对照中，会话创建点冲突 974/998 → 0/1；
流事件范围冲突 646/576 → 0/0；流事件废弃准备累计耗时
11.561/9.770 秒 → 1.667/1.452 秒。然而流式 P99 仍从
11.916/12.033 秒仅降至 11.620/11.801 秒，采样累计等待仍约 98.3%。
因此这些改动有效，但“消除冲突即可解决主瓶颈”的判断不成立。

默认关闭探针的 5,000 次追加试验，吞吐由 821/832 提升到 896/942 次/秒；
P99 的基准与候选区间重叠，不能声称长尾稳定改善。1,000 次短试验也有
候选 P99 更差的样本，不能只选较大的吞吐提升。

保留版本源码摘要：
`573d71f7fe5e6e169981eb20f36c6b90169b1669269bfe38cd1cc2ba5841fa41`。
下一步必须把请求取得快照的排队与 WAL 发布排空分别验证。

## 否决：查询和事务准备同时脱离写入队列

**假设。** 提交后发布不可变的 root、sequence 和 overlay，持有一个
GC pin；请求直接登记自己的 reader pin，就能省掉取得快照的写入 FIFO。
同时让私有事务准备使用这条路径，可能减少两次排队中的第一次。

**安全结果。** 1,378 项原生库测试通过、2 项忽略；新增测试覆盖写锁被
占用时读取、旧快照跨合并、56 个读名额耗尽时写入继续、所有提交 I/O
故障、发布失败后的关闭重开要求，以及同步 GC 的暂停/恢复边界。
四次 1,000 会话运行均准确回读、完整性通过、无请求错误。

| 指标 | A1 原版 | B1 全绕过 | B2 全绕过 | A2 原版 |
|---|---:|---:|---:|---:|
| 流式 P99，秒 | 11.384 | 13.194 | 14.145 | 12.282 |
| 接纳 P99，秒 | 4.063 | 7.338 | 6.549 | 5.282 |
| 收尾 P99，秒 | 11.344 | 11.110 | 10.505 | 11.331 |
| 生产阶段墙钟，秒 | 28.427 | 32.893 | 33.499 | 29.542 |

**观察。** 首轮流事件累计 FIFO 等待 1,348.82 → 951.70 秒，但快照名额
等待 20.53 → 546.22 秒，等待次数 2,959 → 35,172；废弃准备
1.52 → 11.38 秒。后台物化从 352.94 → 460.26 MB，轮转 12 → 15 次。
`queue.depth` 均值 17.5 → 17.2 ms，查询也被读名额竞争抵消了收益。
第二次候选另有离线验证 39.10 秒、清理 10.65 秒的异常长尾，分别记录，
不混入生产阶段，也不无证据地归因于发布机制。

**分析。** 提前准备的事务仍须等唯一的提交者，期间持续占用读 pin。
移除第一层队列没有增加写入能力，反而把等待搬到了共享快照容量，增加
过期准备和唤醒竞争。这是数据支持的解释；通知风暴与后台物化各自的
因果贡献仍需单变量实验，不能只凭次数确定全部成本。

**决定。** 撤回事务准备绕过 FIFO 的路径，保留查询路径单独对照。
不能通过增大线程数、放宽 64/56 pin 边界或提高期限来掩盖这个回归。
若重试并行准备准入，应先证明公平、有界、为查询留出空间，并按提交
服务能力控制在途准备。提交校验、私有内存记账与持久化不可改变。

否决实现保存在提交 `e80cb8f99a6fab0352c023463857e793f72aedbf`，源码摘要
`b04231f91adf82c423714a30b950463011818e1450264918ef4c3c3eb71836cf`。
原始报告位于 `.tmp/tofudb-published-20260930/published-*-1000.json`。

## 中间结果：仅查询脱离写队列，追加成本仍需修正

**决定。** 查询直接从已提交视图登记自己的快照，事务准备继续经过原有
FIFO。发布者占一个 writer pin，查询/事务各自登记读 pin；64 总名额、
56 读名额不扩大。不修改磁盘格式、提交冲突校验或同步级别。

相同负载继续 A/B/B/A，A 为共享计数/精确范围/JSON 已优化版本：

|---|---:|---:|---:|---:|
| `event.list` 采样服务端均值，ms | 36.874 | 0.051 | 0.038 | 49.716 |
| `queue.depth` 采样服务端均值，ms | 24.112 | 0.784 | 0.363 | 44.295 |
| 流式 P99，秒 | 11.907 | 11.652 | 12.273 | 11.916 |
| 接纳 P99，秒 | 4.476 | 4.529 | 4.362 | 4.629 |
| 收尾 P99，秒 | 11.488 | 8.375 | 9.690 | 11.282 |

**结论与边界。** 查询服务端排队大幅下降，收尾 P99 两组分别改善约
27% 和 14%。这里的查询均值不包含独立统计的嵌入式 worker 排队，不是
用户端 P99，也不是数据库整体提升数百倍。流式 P99 一降一升，尚无稳定
改善；1 秒流式、5 秒收尾的容量目标仍未通过。四次均准确回读、完整性通过、
无请求错误；基准与候选的探针丢样数也保留在原始报告中。

发布视图共享不可变 overlay 节点，始终只保留一个最新视图；活跃请求
保留自己的历史视图。峰值客户端 RSS 与 WAL/物化/打包计数见可机读摘要，
不能从单次 RSS 的下降推断稳定的内存收益。

原始报告：`.tmp/tofudb-published-20260930/query-*-1000.json`。
此实验未解决 WAL 发布排空与后台物化成本，也未解决持续写入容量。


关闭探针的 5,000 次追加对照暴露了这个中间版本的写入代价：
A/B/B/A 吞吐为 814/782/795/963 次/秒，P50 为
0.673/0.720/0.719/0.656 ms，P99 为 2.515/2.706/2.769/2.036 ms。
因此不能仅凭读延迟和收尾改善，就声称没有写入回归。

代码检查发现，发布者持有两棵 persistent AVL 的旧根；`Arc::make_mut`
在每次修改路径时因此复制节点，即使没有真实读请求持有历史版本。
这是明确存在的额外工作；上述吞吐差异有多少由它造成，仍须再测。
修正方案是在已完成 WAL 提交后的纯内存更新阶段，短暂持有发布互斥，
先释放发布者自己的旧 overlay 引用，再更新并发布新视图。
实际读请求的独立引用和 GC pin 全部保留；该互斥范围禁止文件 I/O。

## 发布错误的封锁顺序

**审查发现。** 如果先退出发布互斥的作用域，再写入共享 restart-required
标记，内存更新失败后存在短暂窗口：新查询可能登记到已清空 overlay 的
不完整视图。此前的正常负载和故障回归通过，不能证明这个交错不存在。

**决定。** 在持有发布互斥期间完成失败标记，再释放互斥。拿锁失败本身
也使该发布源不可用。新增测试把并发获取放在内存更新失败的边界上：
更新中不能进入，恢复准入时新旧读者都已经被重开要求封锁。
修复提交 `2121a00420d2863b78f539b58388758ed7784ada`。
若重新研究发布方案，必须保留这个失败封锁顺序；本轮整个发布方案最终被否决。


## 否决：常驻快照发布的整体写入代价

再次完成 1,416 项原生测试（2 忽略）和 97 项 Python 验证。正确性通过，
性能仍不能接受，因此整个常驻发布实现均从交付路径撤回。

严格持久化 1,000 会话 A/B/B/A：流式 P99
13.714/12.477/14.306/12.853 秒，收尾
10.961/10.907/9.827/11.969 秒；`event.list` 采样服务端均值
24.641/0.076/0.083/30.720 ms。读收益很大，但全局长尾不稳定。

决定性反例是默认关闭探针的 5,000 次追加：P99

## 恢复根因修复与目录缓存否决（2026-10-01）

结构化证据。关闭请求 profiling

**问题与决定：重复解码。** 显式根覆盖游标逐事务调用 `transaction_at`

28.988 → 1.544 毫秒，不能当生产倍率。只增加源字节缓存仍重复解析；
