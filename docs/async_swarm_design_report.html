1. 问题：主智能体为什么"卡住了"

当前 Tofu 的多智能体协作模式下，主智能体（main agent）调用 spawn_agents 这个工具去派发子任务时，会从那一行开始一直阻塞，直到所有子任务跑完、再来一轮 master review、再 synthesize、再把整段最终答案塞回工具结果。这意味着：

现状：同步阻塞

  • 主智能体的一轮 LLM 推理被强行截断
  • 等待时间 = max(子智能体耗时) + 复审 + 综合（很可能 2~5 分钟）
  • 主智能体期间无法做任何事情：不能读文件、不能上网、不能回答用户中途的提问
  • 用户体验上像"卡死"，调试时也很难判断是哪一段慢

期望：异步收件箱

  • spawn_agents 立刻返回一个"凭据"（handle）
  • 主智能体继续做其它工作（搜索、读代码、与用户对话）
  • 子智能体完成后，结果以"通知消息"形式自动注入到主智能体的下一轮上下文里
  • 主智能体可以选择主动 await_agents() 阻塞等待，也可以被动收件
打个比方：现状像是一个项目经理把活分给三个下属，然后自己在工位上坐着发呆等他们交活。期望状态是项目经理在等活的同时，可以接电话、写报告、回复其他同事；下属交活时把邮件丢进收件箱，项目经理下一次抬头就看到。

2. 现状解剖：Tofu Swarm 的同步阻塞链

2.1 调用链路

当主智能体调一次 spawn_agents，发生的事情按顺序是这样的：

main LLM round
  └─ tool_call: spawn_agents(...)
       └─ lib/tasks_pkg/executor.py::_execute_tool_one
            └─ lib/swarm/integration.py::_handle_spawn_agents
                 └─ MasterOrchestrator.run_reactive()    ← 这里整个被阻塞
                      ├─ StreamingScheduler.iter_completions()
                      ├─ _master_review()  (额外的 LLM 调用 × N 轮)
                      └─ _synthesise()     (再一次 LLM 调用)
            ↑ 返回一段已经合成好的最终答案（字符串）
       ↑ 这段字符串作为 tool_result 拼回主对话
main LLM round 继续

注意一个有意思的事情：swarm 内部已经是流式的了 —— StreamingScheduler 是 DAG 调度，依赖一满足就开跑；iter_completions() 是个 generator，子智能体一个接一个吐结果。

但是这一切发生在主智能体看不到的"屋子里面"。对外暴露给主 LLM 的边界，是一次同步的 tool_call ↔ tool_result 配对，所以主智能体只能眼睁睁等。

2.2 为什么会有 master review + synthesise？

因为主智能体已经把控制权交出来了，只有等到一段字符串放在面前才能继续。所以 swarm 内部不得不"自己再起一个 mini-master"去做：

  • review（复审）：一个轮巡的小 LLM 看着已完成结果，决定要不要 spawn_more_agents 再派一波，或者 swarm_done 结束。
  • synthesise（综合）：再开一次 LLM 把所有子智能体输出合并成一段话。

这两步都是因为同步边界存在才必须存在。一旦换成异步协议，主智能体本身就是 master、就是 synthesizer，这两步基本可以删掉。

2.3 现有可复用的基础设施（不用从零开始）

已经有了

  • StreamingScheduler / AsyncStreamingScheduler
  • MasterOrchestrator 是长生命周期实例
  • _active_sessions 全局 session 表（带 TTL）
  • ArtifactStore 跨智能体共享数据
  • RateLimiter 退避

已经有但要扩

  • lib/push.py 是 UI 推送通道，目标是给前端
  • 需要新增一条 "模型收件箱"（model-facing inbox），目标是给主 LLM

需要重写或取消

  • _master_review() 异步路径下不需要
  • _synthesise() 异步路径下不需要
  • _handle_spawn_agents 改成立即返回 handle

3. 三条候选协议（A / B / C）及其取舍

核心难题是：LLM API 的合同要求 tool_call 和 tool_result 必须配对出现。如果 spawn_agents 立刻返回，那子智能体真正完成时，结果该怎么"塞回"主对话里？以下三种方案。

3.1 方案 A：Handle + 主动轮询 / 等待

同步友好 语义最简单

  • spawn_agents(...) 立刻返回 {swarm_id, agents:[{id, role, objective}], status:"running"}
  • 主智能体后续可以选择：
    • check_agents() — 不阻塞，拿一个状态快照
    • await_agents(ids=[...], mode="any"|"all", timeout=N) — 会阻塞，直到至少一个（或全部）完成
    • read_artifact(key) — 取中间产物
    • 这中间还可以做任意其它 tool_call（搜索、读文件、等等），子智能体一直在跑

优点：完美贴合现有 tool_call/tool_result 协议，模型显式决定何时阻塞。

缺点：纯轮询会消耗 token；好在用 await_agents 一次阻塞一批就够了。

3.2 方案 B：Inbox 注入（被动通知）

用户体验最好 边界条件最棘手

  • spawn_agents 同样返回 handle
  • 每个子智能体完成时，orchestrator 在主智能体下一轮 LLM 推理之前，自动追加一条 user-role 消息： 
    {role:"user", content:"[swarm-update] agent a1 (researcher) completed:
<compressed result>"}
  • 主智能体每一轮自然能看到这些"通知"，无需调任何工具

优点：像团队 lead 收下属邮件，最贴近人类协作直觉。

缺点：无法在已有的 assistant tool_calls → tool_result 配对中间插入 user 消息。如果主智能体此刻正在做某个 tool_call、还没拿到 result，注入会破坏协议。所以必须只能在"轮的边界"注入 — 实际上和方案 C 已经差不多。

3.3 方案 C（推荐）：Handle + 自动注入"swarm 摘要"

推荐 取 A 和 B 的优点

  • spawn_agents(...) 立刻返回 {swarm_id, agents:[…]}。不再做 master review，不再 synthesize。
  • 每一轮主 LLM 之前，orchestrator 排空一个per-task 收件箱：
    • 有新完成的子智能体 → 拼一条简洁的 user 消息附上：[swarm-update] N agents completed, M still running. Latest: …
    • 正在 tool_call 中（消息对未闭合）→ 暂存，等下次合适时机注入
  • 同时给主智能体两个新工具：
    • await_agents(ids?, mode="any"|"all", timeout=60) — 主动阻塞
    • get_agent_result(id) — 拉某个智能体完整结果（注入摘要里只放 preview）
  • 子智能体的工具列表里，明确剥掉 spawn_agents / spawn_more_agents / await_agents / get_agent_result —— 子智能体不能再派子任务。
  • _master_review、_synthesise、spawn_more_agents 这些 swarm 内部的"小 master"逻辑全部退役（先放到 flag 后面，验稳后删）。

3.4 方案对比表

4. Claude Code 是怎么解的：一份活生生的参考实现

把 ~/claude-code/src 翻一遍后能看到，Claude Code 没有一个统一的 "swarm" 抽象，而是把四种多智能体模式叠在同一个底层基础设施上。这种工程取舍特别值得借鉴。

4.1 四种模式概览

模式 暴露给 LLM 的工具 同步 / 异步 沟通方式 对应 Tofu 的什么
Subagent / Fork
即 CC 文档里的 "Task"		 Agent({prompt, run_in_background?}) 两种皆可，run_in_background:true 或自动后台化 tool_result 或 <task-notification> 注入 最像我们要做的 spawn_agents
In-process Teammate Teammate.spawn + SendMessage 始终异步、长生命周期 文件 mailbox + AsyncLocalStorage 隔离 暂时用不上（更重）
Pane Teammate (tmux/iTerm2) 同上，换 backend 始终异步，外部进程 文件 mailbox 用不上
TaskList 协调 TaskCreate/List/Update 纯协调，不跑代码 共享 task 文件 跟 ArtifactStore 概念接近

对我们最有参考价值的是 第一种（Subagent） + 底层共享的"统一命令队列"。下面分别讲。

4.2 Subagent 流：Agent 工具 + run_in_background

定义在 src/tools/AgentTool/AgentTool.tsx。同步调用是默认，但当下面任一条件成立时会"自动转后台"：

  • 调用方显式给了 run_in_background: true
  • 环境变量 CLAUDE_AUTO_BACKGROUND_TASKS=1 或 GrowthBook 实验门 tengu_auto_background_agents 打开时，前台跑超过 120 秒 的会被悄悄改成后台模式

异步路径的关键调用 registerAsyncAgent

位于 src/tasks/LocalAgentTask/LocalAgentTask.tsx:466，整个流程长这样：

1. tool_call: Agent({prompt:"...", run_in_background:true}) 2. 立即返回: {status:"async_launched", agentId:"a-7f2c...", outputFile:"/tmp/cc-tasks/a-7f2c.log", canReadOutputFile:false} 3. 主 LLM 继续干别的活 (search, read, ...) 4. ...time passes... 子智能体在同进程内跑，输出流式写入 outputFile 5. 子智能体完成 → enqueueAgentNotification(...) 把下面这段塞进 commandQueue: <task-notification> <task-id>a-7f2c...</task-id> <tool-use-id>toolu_xxx</tool-use-id> <output-file>/tmp/cc-tasks/a-7f2c.log</output-file> <status>completed</status> <summary>Agent "branch ship-audit" completed</summary> <result>...260 字摘要...</result> <usage><total_tokens>8421</total_tokens>...</usage> </task-notification> 6. 下一次主 LLM 回合开始前，orchestrator 把队列中的通知作为 user 消息排进对话 7. 主 LLM 看到通知，自然地 "Audit's back. Three blockers: ..." 继续推理

它的 system prompt 里怎么教模型用

截自 src/tools/AgentTool/prompt.ts：

"You can optionally run agents in the background using the run_in_background parameter. When an agent runs in the background, you will be automatically notified when it completes — do NOT sleep, poll, or proactively check on its progress. Continue with other work or respond to the user instead."
"Don't peek. The tool result includes an output_file path — do not Read or tail it unless the user explicitly asks for a progress check. You get a completion notification; trust it. Reading the transcript mid-flight pulls the fork's tool noise into your context, which defeats the point of forking."
"Don't race. After launching, you know nothing about what the fork found. Never fabricate or predict fork results. The notification arrives as a user-role message in a later turn; it is never something you write yourself."

注意最后一句：作者们已经清楚地把"通知什么时候到"这件事讲给模型听 —— 这是方案 C 的标准教法。

这套训练样本就把"handle 已发出 → 还没回来 → 用户中途插话 → 不要瞎编、给状态"的行为印进了模型脑子里。我们做异步 swarm 的时候，system prompt 的写法非常重要，不是写完就完事，得这样具体地举正反例。

4.4 底层共享：统一命令队列 messageQueueManager.ts

这是 Claude Code 这套设计真正的"灵魂"。所有要塞回主智能体的东西，都进入同一个进程级队列：

来源典型 mode典型 priority
用户在 REPL 里敲的字'prompt''next'
后台 agent 完成通知'task-notification''later'
teammate 发来的消息'channel''later'
孤立权限响应'orphaned-permission''now'
定时任务 / 主动 tick'proactive''later'

主对话循环每次结束一个 round，从这个队列里 dequeue()。优先级排序保证 "用户输入永远不会被系统通知饿死"。

关键代码：

// src/utils/messageQueueManager.ts
const PRIORITY_ORDER: Record<QueuePriority, number> = {
  now: 0,    // 最高
  next: 1,   // 用户输入默认
  later: 2,  // 系统通知默认
}

export function enqueuePendingNotification(command: QueuedCommand): void {
  commandQueue.push({ ...command, priority: command.priority ?? 'later' })
  notifySubscribers()
}

export function dequeue(filter?: (cmd) => boolean): QueuedCommand | undefined {
  let bestIdx = -1, bestPriority = Infinity
  for (let i = 0; i < commandQueue.length; i++) {
    const cmd = commandQueue[i]!
    if (filter && !filter(cmd)) continue
    const priority = PRIORITY_ORDER[cmd.priority ?? 'next']
    if (priority < bestPriority) { bestIdx = i; bestPriority = priority }
  }
  if (bestIdx === -1) return undefined
  const [dequeued] = commandQueue.splice(bestIdx, 1)
  notifySubscribers()
  return dequeued
}

对 Tofu 而言，这正是 lib/push.py 缺的那一半：push.py 现在只往前端推 UI 事件，但模型自己看不到。我们需要一个"模型收件箱"，跟 push 是双胞胎。

4.5 子智能体不能再派子任务（"prohibit sub-agents from sub-spawning"）

Claude Code 在 prompt.ts:267-275 里有一段非常具体的处理：

${
  isInProcessTeammate()
    ? `
- The run_in_background, name, team_name, and mode parameters are not
  available in this context. Only synchronous subagents are supported.`
    : isTeammate()
      ? `
- The name, team_name, and mode parameters are not available in this
  context — teammates cannot spawn other teammates. Omit them to spawn
  a subagent.`
      : ''
}

注意他们的做法：不是把 Agent 这个工具直接拿掉，而是让 prompt 描述里告诉模型某些参数"在你这个角色下不能用"。这是更柔和的方式：teammate 仍然能起一个 fresh subagent 跑研究任务，但不能起一个对等的 teammate。

对应到 Tofu 的现状：我们的 scope_tools_for_role() 已经做了"剥工具"的能力，但需要一个明确的单测来保证 spawn_agents / spawn_more_agents / 未来的 await_agents / get_agent_result 在所有非主角色下都被剥掉。

4.6 Claude Code 还干对了一件事：每个 agent 一个 output_file

每一个后台跑的 Claude Code agent，都会把自己的滚动输出写进 getTaskOutputPath(taskId) —— 一个真实存在于磁盘的日志文件。这件事的妙处是：

  • 主 LLM 大多数时候 看不到（系统提示告诉它别去 read）
  • 但必要时主 LLM 有这个能力去 read，比如用户问"那个 audit 现在到哪一步了"
  • 开发者调试 swarm 卡住时，tail -f /tmp/cc-tasks/a-xxx.log 一目了然

对比我们的 ArtifactStore：是内存的、只放最终产物，开发者基本没法在 swarm 跑的时候去看中间状态。建议异步化的同时把每个子智能体的流式输出落地一份到磁盘，handle 里返回这个路径。

5.3 自动注入的"swarm-update"长什么样

建议直接抄 Claude Code 的 XML 风格 — 模型对结构化标签的拣选能力更强：

<swarm-update>
  <swarm-id>swarm-abc123</swarm-id>
  <event>agent_completed</event>
  <agent-id>a1</agent-id>
  <agent-role>researcher</agent-role>
  <status>completed</status>
  <elapsed-seconds>42.8</elapsed-seconds>
  <tokens>8421</tokens>
  <preview>Found 3 candidate libraries: foo, bar, baz. foo has the
           cleanest API; bar handles edge case X better.</preview>
  <output-file>data/swarm/<tid>/a1.log</output-file>
  <remaining>1 agent still running (a2:coder)</remaining>
</swarm-update>

多条同时到达可以合并成一条带 <agents>[...]</agents> 的更新。

5.4 新增的两个工具

工具 用途 语义 子智能体能否用
await_agents(ids?, mode, timeout) 主智能体表态"我没别的活了，等" 阻塞至 mode='any' 一个完成 / 'all' 全部完成 / timeout 否
get_agent_result(id) 注入摘要里 preview 不够时拉完整结果 同步返回 SubAgentResult 内容 否

5.5 主智能体 system prompt 增量

建议直接借鉴 Claude Code 的写法：

## 关于 spawn_agents (异步模式)

`spawn_agents` 是异步的：调用后立即返回 `{status:"async_launched", swarm_id, agents:[...]}`。
你不需要轮询，也不应该轮询：
  - 子智能体完成时，会自动以 user 消息 `<swarm-update>...</swarm-update>` 出现在你下一轮上下文里。
  - **不要去 read 或 tail output_file，除非用户明确要你做进度检查。** 信任通知。
  - **不要编造子智能体的结果**。如果用户在通知到达前问起，给状态、不给答案。
  - 如果你确实没别的活可干，调用 `await_agents(mode="any")` 一次阻塞拿到至少一个结果。
  - 如果摘要里的 `<preview>` 不够，调 `get_agent_result(id)` 拿完整内容。

## 子智能体 (sub-agent) 不能调用：
spawn_agents / spawn_more_agents / await_agents / get_agent_result。
它们只能完成自己的对象任务并返回最终答案。

5.7 一段端到端的"演练"日志

假设用户问："帮我评估一下当前分支能不能上线"。下面是异步模式下应该看到的 round 序列：

[round 1]
  user → "帮我评估一下当前分支能不能上线"
  assistant → tool_call(spawn_agents, {agents:[
    {role:"git_audit",   objective:"列出当前分支的未提交 + 领先 main 的 commits"},
    {role:"test_audit",  objective:"检查相关测试是否存在并通过"},
    {role:"flag_audit",  objective:"检查 GrowthBook gate 配置"}
  ]})
  tool_result → {status:"async_launched", swarm_id:"sw-7c2", agents:[a1,a2,a3]}
  assistant → "已经派出三个子智能体审计，正在进行..."
  [round 1 结束]

[orchestrator 轮间钩子] inbox 空，无注入。

[round 2]
  user → "tests 那块大概多久?"
  assistant → "test 审计还在跑，应该很快回来。其它两个也都在并行进行。"
  [round 2 结束]

[a1 完成 → enqueue_agent_message("<swarm-update>agent=a1 status=completed
   preview='1 commit ahead, no uncommitted'</swarm-update>")]

[round 3]
  [orchestrator 轮间钩子] drain_agent_inbox → 注入 1 条 <swarm-update>
  user → "<swarm-update>agent=a1 ... preview='1 commit ahead, no uncommitted'</>"
  assistant → tool_call(web_search, "GrowthBook gate best practices")
  tool_result → ...
  assistant → "git 审计回来了：1 个 commit 领先 main，无未提交。继续等其它两个。"
  [round 3 结束]

[a2、a3 几秒内陆续完成 → 两条 update 进队]

[round 4]
  [orchestrator 轮间钩子] drain_agent_inbox → 注入 2 条 <swarm-update>
  user → "<swarm-update>a2... 'tests pass'</>
          <swarm-update>a3... 'gate not in build_flags.yaml'</>"
  assistant → "好的，汇总一下：✓ 1 commit 领先 ✓ 测试通过 ✗ flag 没配进 build_flags.yaml。
              准备上线之前需要把 flag 补上。"
  [round 4 结束 — 用户拿到完整答案]

对比当前同步模式：用户问完那一刻 → 卡 3 分钟 → 一段长答案空降。新模式下用户每一轮都能跟主智能体互动，而且主智能体在等的时候真的在做事。

6. 关键决策项（你需要拍板的几件事）

决策 1：默认开启 还是 opt-in？

建议第一阶段 opt-in via cfg.swarm_async=True。老的同步路径完全不动，一律走流量走稳后再删。

决策 2：摘要的"丰满度"

建议摘要里只放：role + status + elapsed + tokens + 200 字 preview + output_file 路径。
需要完整内容时让模型显式调 get_agent_result(id)。

决策 3：master review / synthesise 是否保留？

建议保留代码但异步路径下不调用，留作 fallback。一两个版本后确认无人使用，整段删除。

决策 4：await_agents 超时

建议硬上限 120 秒。这跟 Claude Code 的 auto-background 阈值一致，且能防止主智能体被一个挂死的子智能体钉死。超时后返回部分结果 + "still running" 列表。

决策 5：子智能体工具收紧到什么程度？

你之前问过"是否禁用所有工具"。我建议不要那么激进，但保证：
(a) 没有 swarm 系工具 (spawn/await/get/spawn_more)
(b) 没有 ask_user / human_guidance
子智能体仍然保留 web/read/grep —— 否则它们就退化成 prompt 拼接器，没价值。

决策 6：handle 的 task_id 是否对用户可见？

建议在前端 swarm 面板里显示，但不暴露给主智能体的 system prompt（避免它把内部 ID 写进给用户的回答里）。
