# Turn execution frames and production projection witnesses

## Production single-event path (2026-10-19)

**Problem.** The experiment below removes repeated materialization inside an
already atomic IR, but the actual producer generally emits one
`TurnEventRecord`. Its eager final checkpoint also enlarged small high-entropy
writes. A production phase event can carry an empty projection patch while
ordinary execution still decodes the entire checkpoint, replays its accumulated
patch chain, normalizes the projection and serializes unchanged text. The
existing text-tail owner already avoids this for eligible streaming text; the
phase/stable-segment path needs evidence to reuse that same authority state.

**Decision.** Keep the existing producer, operation, compiler and event owner.
`tasks_pkg.manager._events._persist_before_push` calls
`turn_lifecycle.record_task_event`, which issues `turn.event.record`; the native
compiler still produces exactly one `TurnEventRecord`. After an eligible request
has materialized its actual authority state, its compact projection head may
carry a versioned `frameWitness`. It records exact per-field JSON byte sizes,
string types, nesting depth, current revision, actor/status, and no-op evidence
from the existing stable-segment and guidance helpers. A subsequent supported
top-level delta updates those small facts and appends its original replay patch
without decoding or cloning the unchanged checkpoint.

Strict materialization returns transaction-local evidence that the old projection
already satisfies the shared segment normalizer. The event reuses that result
only for the same revision, actor and status, avoiding another normalization and
equality pass. An eligible cold write measures its actual new fields once and
uses those bytes for recovery, size admission and the published witness. Reuse
across a patch requires every normalizer dependency to remain unchanged. Full
field/proof corruption checks remain in their original materialization boundary;
silently repairing malformed evidence was rejected as a change in error behavior.

The shared producer fixture is generated by the real Python lifecycle and run
through native admission/compiler tests. It covers an empty `phase` patch and
the top-level `fallbackModel` update. The producer test also uses 256 KiB content
and a matching text segment. This is a production default single-event path,
not a new API awaiting a caller. Existing progress delivery already groups ready
raw frames through `task_event.preceding_events`; no queue, wait or ACK boundary
changes here. The multi-step frame remains an explicit test-only experiment.

**Boundaries.** Pure text appends retain the existing text-tail owner. Nested
paths, tool-round changes, terminal/settlement/effect acknowledgements, missing
or future-version witnesses, normalization dependencies and checkpoint count/
byte boundaries use ordinary materialization. Changing any of `segments`,
`content`, `thinking`, `toolRounds`, `fileChanges`, `modifiedFileList` or
`modifiedFiles` invalidates segment no-op evidence for the next event. Ineligible
nested/tool paths do not pay an extra witness-mint scan. Known-version malformed
evidence fails closed. Full materialization verifies field facts and applicable
shared-helper proofs; actor/status mismatch disables proof reuse. Depth and
serde reserved-marker cases retain the original normalization/refusal path.

Fast admission measures the actual compact Turn envelope and proves that the
shared settleability validator cannot enter its near-ceiling restart/prefill
scan. No fixed envelope estimate is used. Near the ceiling, original full
reconstruction and limits remain authoritative. Metadata is bounded by the
existing patch budget and owned/retired by its durable head, with no global cache
or separate recovery authority. Text-tail creation drops it. Lifecycle bridge/
checkpoint/restore constructors initialize no witness; every event revision
updates it from verified delta facts or replaces it after materialization.

`store_event_projection` shares the original physical checkpoint policy between
ordinary events and the test-only prototype. Small frames no longer force an
early checkpoint. Public revisions, exact replay patches, raw task events, sync
references and header revisions remain unchanged. Outbox capture retains the
original operation/payload atomically. The production catalog selects a receipt
only when the request contains the typed boolean `terminal: true`; a lost
terminal ACK replays its original success. Repeating an ordinary committed patch
retains its typed stale-revision error and adds no receipt/WAL write. Tests
retain receipt/retry/fault coverage, decrypt original outbox captures and
reexecute them through the same production compiler, compare complete state and
check reopen/commit faults. This is not certification of a generic authenticated
native passive replay target; that pre-existing product gap remains.

**Alternatives.** Eager final checkpoints
were rejected by the earlier high-entropy WAL counterexample. Trusting producer
`projection_segments_stable`, byte counts or types alone was rejected because
legacy guidance repair, normalization and depth are observable semantics. The
witness stays the fast path for metadata patches: it needs no projection at
all. Tool-round, segment and nested patches need the projection itself, which
[committed live-head residency](TOFUDB_JSON_MATERIALIZATION.md#committed-live-head-residency)
reuses with the durable head's own lifecycle instead of a separate cache.

The experiment and counterexamples below describe the earlier implementation,
not performance claims about this production path.

The final production-path focused gate passed 16 Rust tests in debug and release
(five explicitly opt-in experiments ignored), including every injected commit
write/sync failure. Both real Python producer fixtures passed at integration;
their captured requests also run through the native compiler gate. Count/byte
checkpoint rollovers, normalized segment repairs, admitted guidance repairs,
ordered same-field type changes, stale retry, ownership, exact outbox payload and
real reopen are covered. The added local-proof oracle checks all seven dependency
fields, actor/status/revision changes and exact JSON bytes against fresh owner
evaluation. Neighboring projection/text-tail suites passed 17/6 tests.

The final combined native gate passed **2,072 tests, zero failed, 14 ignored**,
and the public context interface gate passed **73 tests**. The ignored cases are
explicit measurement/resource experiments, not counted as passes; work and
timing experiments are invoked separately. These tests establish correctness,
not a runtime speedup.

### Production-path work attribution

The profile-on diagnostic uses the real producer projection shape with 256 KiB
content and the matching 256 KiB text segment. Each event owns its transaction
and commit. `cold` starts without evidence; `hot` establishes one ordinary
phase before measurement. The 64-event cases cross the original checkpoint
threshold. Exact complete public state is equal in every paired case.

| Case | Events | Checkpoint decoded bytes, control → runtime | Old patches replayed | WAL bytes |
| --- | ---: | ---: | ---: | ---: |
| Cold | 1 | 524,931 → 524,931 | 1 → 1 | 7,015 → 7,925 |
| Cold | 64 | 33,595,584 → 1,049,862 | 2,080 → 65 | 479,029 → 544,043 |
| Hot | 1 | 524,931 → 0 | 2 → 0 | 7,339 → 8,353 |
| Hot | 64 | 33,595,612 → 524,931 | 2,079 → 64 | 479,260 → 544,382 |
| Nested fallback | 64 | 33,595,580 → 33,595,580 | 2,079 → 2,079 | 483,717 → 483,717 |
| Tool fallback | 64 | 33,595,633 → 33,595,633 | 2,079 → 2,079 | 487,562 → 487,562 |

The cold cycle reduces 64 checkpoint passes to two in this fixture; the hot
cycle reduces 64 passes to one. This is work
elimination across independent commits, not a change from 64 fsyncs to one.
The bounded facts cost approximately 0.9–1.0 KiB of extra WAL per eligible
event in this fixture (cold64: **+13.6%**). Nested/tool fallback still performs
its original reconstruction and can pay verification of an existing witness;
equal work counters do not establish equal latency.

These results apply to consecutive phase/model-field events over an unchanged,
normalized projection. Text-tail creation clears the witness; a subsequent
stable-segment event must materialize again. Delta → phase → delta alternation
does not inherit the hot-path result. A separate exact-state/reopen diagnostic
for phase → text-tail/tool → phase confirms that both arms decode a 524,931-byte
checkpoint on every step; checkpoint, patch and entity-get counts are identical.
The witness adds 910–912 WAL bytes on the first/last phase without eliminating
materialization in that sequence. First mint, fallback and boundary costs
must remain visible alongside hot performance. SQLite can implement the same
evidence-driven algorithm; this diagnostic establishes native work reduction,
not a capability SQLite cannot express.

### Recovery size evidence for large histories

Problem: the fast path reserved a second copy of the whole projection to
cover restart settlement. Once a valid history exceeded that conservative
estimate, even empty child-status patches materialized the checkpoint again.
Decision: witness version 2 records the actual encoded restart settlement
size from the existing recovery owner. Metadata-only patches reuse it;
changes to content, thinking or tool rounds invalidate it. Materialization
verifies the count, and the ordinary snapshot/terminal reserve still applies.
Version 1 remains readable with a conservative fallback; older readers treat
version 2 as an optimization miss. No snapshot ceiling, checkpoint cadence,
durability barrier or recovery option changes. Alternatives rejected: raising
the snapshot limit moves the cliff; skipping recovery admission could admit a
live Turn that cannot settle. Tests use a 40 MiB history and compare ordinary
execution, restart readback, invalidation and malformed evidence.

The 2026-11-05 paired regression runs the ordinary materialized owner and the
production witness owner from the same debug test binary, with identical
40 MiB projections and three subsequent empty metadata patches. On local
temporary storage, the measured per-event medians were 1,937.207 ms and
17.326 ms. A separate run with both disposable databases under this host's
FUSE mount measured 1,954.594 ms and 3.031 ms. Each run checks exact command
results, full Turn readback, invalidation and reopen. These small debug-build
samples establish elimination of repeated materialization, not a production
latency SLO, filesystem ranking or whole-conversation speedup. First mint and
checkpoint rollovers still materialize; content/thinking/tool updates retain
the ordinary path. Run
`cargo test --manifest-path packages/tofu-db/Cargo.toml --lib execution_frame_large_history_reuses_recovery_proof_for_small_events -- --nocapture`;
set `TMPDIR` to an isolated directory on the filesystem being measured.
Metadata retention is measured in [storage operations](STORAGE_OPERATIONS.md#large-history-event-persistence).

### Recovery evidence compatibility (2026-11-08)

Problem: the recovery owner corrected `evidence` from `user_abort` to
`system_recovery` without advancing the projection witness version. Both
encodings were published as v2. The five-byte size difference made an upgraded
reader reject valid historical Turns with `Turn frame recovery bytes differ`.

Decision: new witnesses use v3 and exactly verify the current recovery encoding.
A v2 reader verifies either published encoding against the fully materialized
projection; the compatibility adapter changes only the old evidence label for
measurement and reuses the shared recovery owner for every option. Field sizes,
depth, revision, normalization and guidance checks remain mandatory. A v2
recovery size never supplies fast write admission: an ordinary materialized
write mints v3 first, so an old count cannot under-reserve the current settlement.
Version 1 and future-version fallback keep their existing rules. Reads do not
rewrite history or change the actual recovery verdict. The metadata shape and
retention are unchanged; only the one-digit witness version advances.

Alternatives rejected: accepting any size mismatch hides malformed evidence;
reverting the recovery verdict mislabels a server restart as a human stop;
reusing the old count can admit a Turn that cannot settle. Golden lengths for
both published envelopes, exact rejection of other counts, public readback,
lane-index parity, reopen and lazy upgrade are executable specifications in
`turn_execution_frame_runtime_tests.rs`. Changing recovery serialization must
preserve those historical fixtures and explicitly version new size evidence.

### Adjacent ordinary events in one transaction (2026-11-05)

Problem: the production delivery FIFO can already compose several ordinary
`TurnEventRecord` steps in one atomic IR. Nested tool/usage updates still decode
the same checkpoint and replay its growing patch chain for each step. On the
25 complete problem histories in `benchmarks/storage_history_cohort.py`, queued
delivery reconstructed 18.40 GiB of checkpoint inputs after the recovery-size
fix; the retained histories total only 406.66 MiB. This volume includes seeding
and verification reads, not just the timed continuation, and is not disk writes.

Decision: the existing sequential IR owner holds at most the immediately
preceding ordinary event's owned materialized projection. The next adjacent
event first reads its current Attempt and Turn header through the ordinary
transaction, retains scope/current-attempt/worker-claim and revision checks,
and moves that projection only when its scoped entity key and complete physical
header match. Normalization, guidance preservation, size admission, checkpoint
rollover and publication still execute through `turn.rs::event_record`'s shared
implementation. No persisted proof is inferred from this buffer.

Every other IR step clears it, including reads. Refusal, errors, another Turn,
text/witness fast paths and settlement discard it; only a fully published
materialized event with a live head supplies its successor. The IR drops the
last buffer before commit preparation. A failed or conflicting preparation
therefore leaves no cross-transaction reuse. The buffer moves an allocation
already needed by ordinary execution, with at most one preceding projection
retained between adjacent steps; it adds no persistent bytes, global cache,
retention setting, admission limit or durability option.

Alternatives rejected: a process-wide projection cache requires a separate
invalidation/lifetime owner; the experimental frame reducer duplicates ordinary
semantics and changes checkpoint costs. A generic transaction mutation counter
adds bookkeeping to every entity operation. Restricting reuse to adjacent steps
in the existing loop gives an explicit invalidation boundary instead. The
experimental `execution_frame::record` remains test-only.

Executable specifications are in `src/turn_event_adjacent_tests.rs`: exact
ordinary-owner state and reopen across checkpoint/fast/terminal boundaries,
stale version/owner/attempt refusal, complete rollback, commit conflict, and an
intervening checkpoint deletion that must still fail integrity checks. The
shared write/short-write/lost-sync fault matrix also runs through production IR,
with receipt replay and outbox atomicity. The isolated work-count test proves
three nested events read one checkpoint instead of three; invoke it with
`--ignored --test-threads=1` because its counters are process-wide. Complete
producer measurements and their limitations belong to
[task event delivery](TASK_EVENT_DELIVERY.md#complete-history-delivery-measurements).

### Terminal reconstruction and ownership (2026-11-05)

Problem: terminal event execution had already reconstructed and verified its
current Turn, but updating the Attempt's lane liveness loaded that same Turn
again just to read `laneId`. Storing the terminal document then deep-cloned the
entire projection while retaining the original for publication.

Decision: the event owner passes its same-transaction verified lane to the
shared Attempt writer. All other callers keep the original current-Turn loader;
no cross-transaction cache or header-only replacement for integrity validation
is introduced. Inline/terminal storage takes ownership of the projection and
publication borrows it from that Turn. Live heads retain their one owned body
for the existing adjacent-event handoff. Attempt serialization also borrows
its map instead of cloning it into a temporary JSON Value. The physical codecs,
checkpoint retirement, bytes admitted, event payloads and durability barrier
remain unchanged.

The isolated `terminal_record_reuses_the_already_verified_turn` specification
observed 524,782 checkpoint bytes reconstructed before the change and 262,391
after, exactly one verified read of its 256-KiB-history fixture. Run with
`--ignored --test-threads=1`; these counters are process-wide. Large terminal
receipt/outbox tests inject each commit write/sync fault and reopen its durable
image. The public backup/restore test retains a complete terminal history.

Alternative measured and rejected: sealing a terminal head onto its checkpoint
and patch chain avoided a terminal blob rewrite but introduced a new durable
format. In two alternating 25-history concurrent pairs (625 events per process),
cohort windows changed 32.778→34.034 seconds and 31.781→25.020 seconds;
terminal P95 changed 11.953→15.033 seconds and 15.856→6.317 seconds.
Checkpoint reconstruction input increased from 7,087,560,454→8,115,415,502 bytes
and 6,763,243,349→7,735,815,750 bytes. Complete results and SIGKILL recovery agreed,
but the inconsistent latency and increased read work did not justify a format
rollout. The sealed-head prototype is not in the production implementation.

## Batched structural events (2026-11-01)

**Problem.** Every structural task event (phase, tool start/result, round
end) needs its own `turn.event.record`: one commit, one projection revision and
one conversation-sync event. A delivery barrier waits until every queued event
is durable, so a backlog of K events costs K serialized commits. During the
storage congestion of 2026-10-31 09:00-10:40 one RPC took about 6.8 s while
barriers waited on 19-136 queued events: 24 barriers waited 2 minutes or more,
375 minutes in total, the worst 65.7 minutes. `task_event.preceding_events` is
the only multi-row form and admits progress frames only, because each
structural frame owns a revision and a sync event. The native engine already
executes several `TurnEventRecord` steps in one transaction; its compiler
produced exactly one per request. This supersedes the earlier rejection of a
producer batch ("ready-event batching already exists"), which covered progress
frames only.

**Decision.** The receipt-free command `turn.event.record_batch` is K ordinary
`turn.event.record` steps in one all-or-nothing transaction on both
authorities, answered by one ordinary result per entry. Every entry is a
non-terminal record of the same task attempt carrying its row; interaction,
background-acknowledgement and tool-effect records keep their own transaction
and barrier. Rows strictly ascend across entries and stay within the existing
storage-event RPC bound (500 rows, 60 MiB; `structuralBatch` in
`contracts/task_event_delivery_v1.json`, read by
`resolve_storage_event_budget`). Any refused entry rolls back every entry. The
SQL authority loops `_turn_event_record` in one session; native TofuDB compiles
K `TurnEventRecord` steps with a `SlotArray` result and never commits a mixed
applied/rejected outcome. K entries leave the same K revisions, K sync events
and K rows as K sequential calls.

Native execution also refuses (`database_resource_exhausted`, nothing written)
a multi-entry batch as soon as it no longer fits one ordinary commit: its
entity delta must fit the overlay envelope that `prepare_commit` uses, and its
new blobs and rows, less the carried payload of its single largest entry
(below), must fit the WAL-carried ceiling minus the composition headroom
already published as `resourceBudget.eventBatchComposition`. Without
that test, a 500-entry batch of small frames (about 4.6 KiB of new pages and
blobs per entry) drained every conversation's overlay through the tree path,
then synchronized about 1,300 loose blocks one by one under the authority:
10.6-21.4 s per batch with request profiling on, 111 s once under host load,
and `deadline_elapsed` in the benchmark. That is beyond the 10 s
authority-wedge threshold and the 5 s deadline of every concurrent request.
256 entries with 4 KiB tool results spilled the same way (6.8 s), while 136 of
them committed in 252 ms. A single entry is an ordinary record and is never refused
for its size. SQL has no such representation and commits the whole run.

*One large entry (2026-11-05).* Problem: on long-running Turns the first
structural event after streamed text retires the text tail and writes the whole
projection as one checkpoint; a 53 MB projection compresses to about 15 MB.
Every multi-entry batch containing that entry failed the test above, so the
producer's bisection repeated the full materialization and checkpoint
compression (about 1 s of authority hold each) about log2(K) times before the
entry committed alone on the same spill path. Over 37 minutes the server
logged 554 refused `turn.event.record_batch` calls, mean 957 ms (about 530 s
of authority time, 24% of all batch time); their `authority_hold` records show
`blob_codec_compress` of 115-148 ms and no WAL journal.

Decision: a batch may exceed one ordinary commit by at most one entry's own
carried payload. Execution records each applied step's increment of
`carried_payload_bytes` (staged blob bytes plus stream bytes, the measurement
of the test above) and refuses only when the total less the largest single
increment exceeds the ordinary carried budget, or when the whole transaction's
entity delta leaves the overlay envelope (unchanged). Alone that entry is never
refused for its size, and the rest still fits one ordinary commit, so no
composite can accumulate the many-small-entries spill above. The total less the
largest increment never decreases as steps are added, so refusal still comes at
the first step that makes it certain. All-or-nothing outcomes, per-entry
results, receipts, outbox capture, attempt fences, the producer and the SQL
authority are unchanged; no constant or setting is added. An admitted
composite whose total exceeds the WAL-carried ceiling spills the rest's new
blocks together with the large entry's instead of carrying them in a separate
record: at most one ordinary commit's carried payload, never the tree path.

Measurement: one large entry plus three small entries, recorded through the
producer's bisection rule on disposable authorities (debug build, exact
process counters, three identical repetitions). For the streamed-text
checkpoint shape, a patch folded into a checkpoint and a 2.5 MiB blob-carried
row, the run took 2 refused attempts and 3 commits before and 1 commit after;
blob compressions fell from 12, 18 and 9 to 4, 6 and 3 (about 172, 234 and
146 ms to 58, 77 and 50 ms of compression) and checkpoint materialization of
the streamed-text shape from 15.7 MB to 9.4 MB, with unchanged spills (one,
one, none). Specs:
`turn_event_record_batch_commits_one_entry_beyond_one_ordinary_commit_with_its_small_followers`
(results and state equal sequential records, also after reopen, and the
preparation lane admits the composite beyond the ordinary budget);
`turn_event_record_batch_exempts_at_most_one_entry_beyond_one_ordinary_commit`
(two large entries, or one beside small entries that alone exceed the budget,
are refused with nothing written);
`turn_event_record_batch_failure_after_the_exempt_entry_writes_nothing` and
`turn_event_record_batch_commit_faults_beside_the_exempt_entry_recover_all_or_nothing`
(a later failing entry, and faults at the first and last durability barrier of
each kind in the spilling commit, leave nothing or the whole batch). The
many-small-entries spec uses 64 rows of 32 KiB, which exceed the budget even
without their largest row.

Alternatives considered: the authority names the oversized entry so the
producer isolates it (one refused attempt still materializes and compresses
the checkpoint, and three commits replace one); the producer predicts native
size (the measured 2.6-7.5x wire factor makes any prediction a magic factor);
exempt only an entry that alone exceeds the budget (a second condition that
keeps re-executing medium entries beside small ones, to avoid a spill already
bounded by one ordinary commit); keep the prepared checkpoint across refused
attempts (a cross-request cache of private preparation bytes and its
invalidation, for work that need not repeat at all); a larger carried ceiling
or headroom (it bounds WAL records and replay memory).

`turn_lifecycle.record_task_events(task, entries)` is the producer. It projects
each durable wire once in FIFO order and chains K patches from the cached
committed revision r to r+K. Oversized inline diagnostics are shed per entry as
on the single path. It checks every per-entry result and remembers projection
state once per transaction. A refused composite commit bisects only that
interval in FIFO order; each unwritten sibling keeps its independent size. After an
unknown outcome the next call reads the exact rows before resending: all
present and identical means committed, none means resend on the same base,
some fails closed with `database_conflict`. A stale attempt revokes the whole
batch. An authority without the command answers `unknown_operation` and the
call uses the per-event path; that is a capability answer, not a flag. The
task event delivery FIFO calls it for every queued run of structural frames
([task event delivery](TASK_EVENT_DELIVERY.md#queued-structural-runs-persist-in-one-call)).

`benchmarks/turn_event_batch.py` replays one prepared FIFO run per K through K
`record_task_event` calls and through one `record_task_events` call on fresh
attempts of disposable authorities; both modes committed one identical digest
of projection, revisions, rows and sync patches. Medians of three alternating
runs (2026-11-02, shared 91-CPU host at load average 40-50, authorities under
`/tmp`); *contended* adds four background writers on their own conversations
and four CPU-bound Python threads. Batch RPCs include refused composite commits.

| TofuDB | contended | 16 | 3.93 s (16) | 196 ms (1) | 20.0 |
| TofuDB | contended | 64 | 16.3 s (64) | 393 ms (1) | 41.5 |
| TofuDB | contended | 500 | 131 s (500) | 8.98 s (12) | 14.6 |

K = 1 gains nothing; the run-to-run spread there exceeds the difference.
Native K = 500 made three refused attempts (500, 250 and 125 entries) and nine
ordinary commits (eight of 62 frames, one of 4) without a spilled block. These
are persistence clocks of one component boundary, not barrier, delivery or
application latency.

**Alternatives considered.**

- Extend `preceding_events` to structural frames: one Turn event would carry
  several structural changes under one revision and one sync event, changing
  the replay contract.
- Group by an estimated native cost, like the raw-event composition model: a
  structural record rewrites the Turn document and several indexes, and the
  measured new bytes were 2.6-7.5 times the wire bytes across workloads. Any
  estimate is either a magic factor or unsafe; the authority's own test is exact.
- Let large batches take the existing spill path: it keeps every write but
  holds the authority for seconds per batch.
- A smaller fixed batch cap: a tuning knob that ignores payload size, and SQL
  needs none.
- Raise the carried ceiling: it bounds WAL records and replay memory.
- Fuse the steps with the execution-frame experiment below: it is test-only,
  has no replay compiler, and ordinary steps already amortize the commit.

## Historical experiment: status and scope

The multi-event entry point is an internal `cfg(test)` experiment, not a public
operation. Its header frame port and IR entry point are excluded from production
builds; default transports cannot write experimental frames. The production
single-event witness now shares the containing module.
The production semantic compiler creates exactly one `TurnEventRecord` step per
`turn.event.record` request. No production caller invokes
`prepare_execution_frame_ir_with_deadline`. A workload delivering separate events
one second apart does not gain an N-to-one execution boundary from this change.

The experiment consumes multiple already-arrived steps in **one existing atomic
IR transaction**. Both the control and the candidate commit once, using the same
AuthorityDatabase, owner checks, transaction validation, WAL and durability policy.
No future event is awaited and no response is acknowledged before that commit.

## Problem

`event_record` already commits the projection, attempt event, conversation sync,
carried raw event, terminal continuation and queue acknowledgement together.
`event.append_batch` batches raw events; `preceding_events` preserves bounded
progress events while advancing the final projection once. WAL group commit
shares the physical flush. None of these eliminates repeated Turn materialization
when a single IR already contains several projection changes.

For a large running Turn, the ordinary step reloads the checkpoint and its patch
chain, clones and encodes the materialized projection, then updates the Turn,
lane, compaction, recovery, recency and header indexes. Repeating this in one
transaction repeatedly visits an unchanged large prefix. The historical patch
chain is bounded at 64 patches, so quadratic replay work occurs within that
window rather than growing without bound across the lifetime of a task.

## Decision

Prototype an explicit same-attempt execution boundary in
`src/turn/execution_frame.rs`, sharing `load_event_record_state` and
`publish_event_record` with ordinary `event_record`. Admission and replay remain
owned by Turn; there is no second state machine or storage authority.

The frame loads one private projection, consumes each existing typed patch,
retains every logical event and response, then publishes its final projection and
derived indexes once. The header advances by the number of logical changes and
uses the **last** input timestamp, including when timestamps are non-monotonic.
An incremental exact JSON byte witness checks the settleable snapshot limit on
every intermediate state. Away from the snapshot ceiling, only affected fields
and appended text are measured after the initial projection. Near the ceiling,
the shared settleability check still reconstructs restart settlement on every
step, scans tool history and can count the entire prefill text prefix. This
prototype does not remove that O(N × prefix) fallback. The private tree and
witness are dropped on error.

Accepted transitions are deliberately narrow: one already-running bound attempt,
one task and flow root, `projection_updated`, with top-level content, thinking or
phase set/append patches. All exact phase/raw/attempt/sync events are retained;
none is coalesced away. Pending starts, terminal settlement, tool structure,
interaction, effect acknowledgements, segment normalization, mixed attempts and
any other IR step are refused. Stored guidance receipts also require a no-op
proof through the ordinary preservation helper on a private copy of toolRounds.
A legally admitted receipt can still need normalization even when a new patch
only touches text; that state is refused without mutations. The initial proof
retains the shared helper's tool-history scan cost; arbitrary guidance history
is not claimed to admit in linear time. This is not yet the complete desired execution
frame joining checkpoint frontier, effect intent and usage receipt.

## Observable correspondence

Each original response slot and projection revision remains equal. Attempt events,
patch replay, hydrated reads, raw events, conversation sync and the final public
Turn/header must match ordinary sequential steps inside the same transaction.
There is no externally visible intermediate commit in either arm.

Physical versioned-document tokens and checkpoint layout intentionally differ:
the final Turn/header are physically replaced once, rather than once per step.
These tokens are private storage metadata, not the public projection revision or
header revision. The experimental port forbids later reads or conditional steps
inside the IR, so no same-IR consumer can observe an intermediate physical token.
A future general optimizer must prove that condition or refuse fusion.

Receipt lookup/insertion and encrypted logical outbox capture use the existing IR
owner. Retry and WAL crash tests cover their atomicity with the frame. However,
the experimental fixture payload has **no production semantic replay compiler**.
Passive logical replay and public admission are not certified by capture tests;
a wire protocol and its replay compiler are prerequisites for exposing this port.

## Alternatives considered

- More RPC batching or WAL group commit: already available and does not remove
  repeated checkpoint materialization inside one transaction.
- Coalescing separately acknowledged events: changes the durability/visibility
  boundary and is outside this experiment.
- A second event store, owner or projection state machine: duplicates authority
  and replay semantics; the prototype reuses existing Turn helpers instead.
- Enabling the frame on all ordinary events: a one-event frame can rewrite a
  checkpoint unnecessarily and currently has no work-count advantage.
- Claiming a SQLite limitation: SQLite can apply the same fold in one WAL FULL
  transaction and store the final projection once. This is a Harness algorithm,
  not evidence of an exclusive native database capability.

## Verification and work evidence

The profile-on diagnostic uses directly initialized AuthorityDatabase instances,
not an embedded/sidecar RPC benchmark. It compares ordinary IR execution with frame IR execution in
one process and one transaction each, N=1/8/64, using a 256 KiB stable projection
plus small Unicode/escaped text and phase changes. It measures actual engine work
counters and WAL bytes; debug timing is not a performance result.

Actual work measured on the prototype, with all final logical state equal:

| Events in one transaction | Checkpoint bytes, sequential → frame | Historical patches replayed, sequential → frame | Entity gets, sequential → frame | WAL bytes, sequential → frame |
| ---: | ---: | ---: | ---: | ---: |
| 1 | 262,269 → 262,269 | 1 → 1 | 27 → 27 | 7,525 → 7,975 |
| 8 | 2,098,152 → 262,269 | 36 → 1 | 223 → 83 | 30,703 → 25,042 |
| 64 | 16,785,216 → 262,269 | 2,080 → 1 | 3,555 → 531 | 184,388 → 160,221 |

Checkpoint decode, content-hash and collection byte counters agree: N=64 reduces
64 passes over the checkpoint to one. Both arms apply all 64 new patches; the
historical-patch counter measures reconstruction only. The general-patch path
visits a large stable prefix N times; this frame visits it once, plus the actual
incoming changes and N exact event publications in this ordinary-budget case.
The near-ceiling fallback above is not covered by that scaling claim. The fixture's repeated stable
text compresses well, so these WAL figures are not an incompressible-history claim.

The N=1 WAL regression (+450 bytes, 6.0%) is retained. There is no claim of a
latency speedup, default-path improvement, or a SQLite advantage from these work
counts. The current text-tail optimization is separately checked for logical
parity; this work-count fixture also changes phase and therefore exercises the
general projection path.

Focused verification covers per-slot correspondence for N=1/8/64, both inline
and checkpoint projections and text-tail input, non-monotonic final timestamps,
patch and hydrated replay, real close/open, stale-revision rollback, owner refusal,
unsupported boundaries, deadline refusal, invalid typed append, exact Unicode
and escaped-string byte accounting, competing preparation, receipt retry,
outbox capture, every observed write/sync fault with mandatory firing, torn writes,
silently dropped individual syncs, and acknowledged state after real SIGKILL.
The child process has a bounded readiness wait and a kill-and-join drop guard.

A separate Linux-only ignored `execution_frame_timing_leg` driver accepts
`TOFU_FRAME_EVENTS=1|8|64`, `TOFU_FRAME_FOLDED=0|1` and
`TOFU_FRAME_FIXTURE=compressible|high_entropy`. It requires a release test
binary with profiling disabled. Each process measures twelve fresh preparations

are outside the measured interval. Per-sample wall and process CPU times, WAL
bytes and common response/state digests allow balanced independent-process ABBA
runs. No low-sample P99 is used as stable tail evidence.

The high-entropy control has the same 262,144-byte stable field. For counters
0 through 8,191, SHA-256 hashes `tofu.execution-frame.prefix.v1` followed by the
counter as eight little-endian bytes. Each digest byte selects one of 64 URL-safe
characters with its low six bits. The process emits the exact prefix SHA-256.
This is deterministic high-entropy text, not a claim of incompressible bytes.
The measured historical candidate always wrote a final checkpoint, even before the existing patch
chain fills; high-entropy N=1/8 can therefore expose an early-rewrite penalty.
No patch-chain redesign is included to remove an inconvenient counterexample.

The timing binary uses opt-level 3, `CARGO_PROFILE_RELEASE_LTO=false` and
`CARGO_PROFILE_RELEASE_CODEGEN_UNITS=16`, identically for both arms. It does not
represent production fat-LTO latency. The first unused fat-LTO test build took
9m11s and completed before the fixture change; its log is retained separately.

SQLite can implement the same final-projection fold, so these numbers establish
a Harness optimization opportunity, not an exclusive database advantage.
