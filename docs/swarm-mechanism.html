1. 一句话心智模型

💡 核心思想

子智能体运行在一个后台守护线程（daemon thread）上，与主智能体当前的"回合（turn）"完全脱钩。 spawn_agents 永远不会自动阻塞主智能体——它发射后立即返回。

至于结果怎么回到主智能体手里，有两条完全不同的路径（这是本文档此前讲错、现已更正的关键点，详见 第 6 节）：

  • 路径 A（收件箱）：主智能体 spawn 后继续干别的活；子智能体完成时把便条投进收件箱（inbox）， 在主智能体下一回合开始前被注入为一条 user 消息。
  • 路径 B（await / get_result 的工具返回值）：主智能体主动调用 await_agents（阻塞等待）或 get_agent_result，结果直接作为工具返回结果（tool result）回来——完全不经过收件箱。

可以把它想象成：一位经理（主智能体）把任务分给同事。 路径 A：经理继续做自己的事，同事把便利贴贴在他桌上，他下次坐回办公桌（下一次 LLM 调用）时才看。 路径 B：经理干脆搬张椅子坐在会议室门口盯着等（await_agents），同事一做完就当面把结果递给他—— 这时便利贴（收件箱）根本没用上。

2. 主智能体能看到的三个工具

工具是否阻塞作用
spawn_agents 不阻塞 发射后不管（fire-and-forget）。在后台线程上启动 N 个子智能体，并立即返回一个句柄 （{status:"async_launched", swarm_id, agents:[…]}）。主智能体的回合继续进行。
await_agents 阻塞 唯一会阻塞的工具，且可选。当主智能体没有别的事可做时使用。最多等待 120 秒，等 any（任意一个）/ all（全部）完成后返回它们的摘要。
get_agent_result 不阻塞 当 200 字的预览不够时，拉取某个已完成子智能体的完整最终答案。

子智能体自身不能调用这三个工具——它们会从每个子智能体的工具集中被剔除 （SUB_AGENT_DENYLIST），因此 swarm 无法递归地再生出 swarm。

3. 一次 Swarm 的完整生命周期

1
主智能体调用 spawn_agents([...])。 请求路由到 _handle_spawn_agents，它构造一个 MasterOrchestrator 并调用 run_in_background()。
2
启动一个守护线程——名为 swarm-driver-<task_id>。它运行一个 StreamingScheduler，按 depends_on 依赖顺序，一次最多并行启动 max_parallel 个子智能体。
函数就在这里返回句柄——主智能体随即重获自由。
3
每个子智能体运行自己独立的 LLM 会话，带有按角色裁剪的工具集，并把思考/输出流式写入 data/swarm/<task_id>/<agent_id>.log。
4
当某个子智能体完成时，调度器触发 _on_agent_complete_callback，它会：
  (a) 发出一个 UI 事件（swarm_agent_complete）给前端实时面板；
  (b) 把一条 <swarm-update> 便条塞进收件箱。
5
结果回到主智能体——走两条路之一：
  路径 A：如果主智能体 spawn 后继续干别的活，则在它下一次 LLM 调用之前， orchestrator 清空收件箱，把待处理便条合并为一条 user 消息注入。
  路径 B：如果主智能体调用了 await_agents / get_agent_result， 结果直接作为工具返回结果回来，收件箱被绕过（便条留在队列里没人取）。
⚠️ 关键：路径 A 的注入只发生在"还有下一回合"时。若任务在收件箱被清空前就结束了， 那些便条会在任务收尾时被丢弃（日志：cleared N unread item(s) on task end）。
6
整个任务结束时，会话被中止、收件箱被清空、驱动线程被回收——不会泄漏。

4. 通信机制——收件箱（inbox）

这里有两条彼此独立的通道，千万不要混淆：

通道受众用途
lib/agent_inbox.py LLM（主智能体） 一个按任务区分的优先级队列，存放 <swarm-update> XML 便条。这是结果重新进入模型上下文的 路径 A，在主智能体下一次 LLM 调用前被清空注入。注意：若主智能体走路径 B（await）或任务提前结束， 此队列会被绕过或丢弃——这正是你在 debug 面板里常常看不到 <swarm-update> 消息的原因。
lib/push.py / UI 事件 浏览器 实时进度事件（swarm_phase、swarm_agent_complete …），用来驱动 swarm 面板的动画。 模型永远看不到这些事件。

一个"完成"如何变成模型可见的消息

当 agent a2 完成时，_on_agent_complete_callback 通过 format_swarm_update(...) 构造下面这条便条并入队：

<swarm-update>
  <agent-id>a2</agent-id>
  <role>coder</role>
  <status>completed</status>
  <elapsed-seconds>12.4</elapsed-seconds>
  <preview>...最终答案的前 200 字...</preview>
  <output-file>data/swarm/<task_id>/a2.log</output-file>
  <remaining running="1" pending="0"/>
</swarm-update>

随后，在主智能体的下一回合，orchestrator 的清空钩子会把它注入 （lib/tasks_pkg/orchestrator.py，就在 LLM 调用处附近）：

# ★ 在 LLM 调用前清空 swarm 收件箱
if not _has_unmatched_tool_call:          # 不要打断尚未闭合的 tool_call / result 配对
    _inbox_items = drain(tid)
    if _inbox_items:
        messages.append({
            'role': 'user',               # 一条真正的 user 消息——不是 system-reminder
            'content': '\n\n'.join(payloads),   # 把所有待处理便条合并成「一条」消息
        })

两条微妙但重要的规则

  • 合并（Coalescing）：所有待处理便条会被合并进一条 user 消息（更干净的 prompt 缓存、更少的消息条数）。
  • 配对安全（Pair-safety）：如果上一回合以一条带有未闭合 tool_calls 的 assistant 消息结尾（还在等它的 tool_result），注入会被推迟—— 你不能在工具调用和它的结果之间插一条 user 消息。

5. ⭐ 你的疑问：异步 agent 是不是偷偷阻塞了？

❓ 你的原话

"启动异步 agent 之后，主 agent 确实能继续调用其他工具，但看起来这些异步 agent 仍然是一起执行、 全部完成后才返回。这是通过 await 那个 agent 工具实现的吗？"

✅ 简短回答：不是——并没有隐藏的 await。

spawn_agents 瞬间返回，子智能体运行在一个脱离的守护线程上。驱动循环在那个线程上 （而非主智能体线程上）迭代 scheduler.iter_completions()。主智能体从未与它们 join。

那为什么看起来像"全部完成后才返回"？

因为关键在于结果什么时候、以什么形式重新进入对话。子智能体的结果不会流式插进主智能体当前回合的中间， 它只能在某个回合的边界出现——要么作为下一回合开头注入的 <swarm-update> user 消息（路径 A）， 要么作为 await_agents / get_agent_result 的工具返回结果（路径 B）。 无论哪种，从对话记录看都像"spawn → … → 突然所有结果一起冒出来"。这种"批量出现"是回合边界的批量送达， 而不是 spawn 本身在阻塞。两条路径的完整对比见 第 6 节。

产生这种观感的两种场景

场景 A —— 主智能体让自己一直忙着（真正的并行）

主智能体
spawn_agents grep_search read_files ▶ 下一回合 读收件箱 → 汇总
子智能体
已启动 a1 ▓▓▓▓▓▓▓ a2 ▓▓▓▓▓

主智能体自己的工具调用在墙钟时间上与子智能体重叠。 这是预期路径——真正的并行。结果在它们完成后经由收件箱送达。

场景 B —— 主智能体无事可做，于是主动 await_agents（结果走工具返回，不走收件箱）

主智能体
spawn_agents await_agents（阻塞 ≤120s） get_agent_result ×N 汇总
子智能体
已启动 a1 ▓▓▓▓▓▓▓ a2 ▓▓▓▓▓

这里的阻塞是真实的——但只因为模型自己显式调用了 await_agents（系统提示词的建议："等待期间若无事可做，就调用 await_agents"）。 这条路径下，结果作为 await_agents / get_agent_result 的工具返回结果直接回来， 收件箱里的 <swarm-update> 便条从头到尾没被取用，最后在任务结束时被丢弃。 这就是为什么这种对话的 debug 面板里根本没有 <swarm-update> 的 user 消息。

主智能体的工作 子智能体的工作（后台线程） 显式的阻塞等待

⚠️ 这一节之前讲错了什么

本文档早先的版本声称"结果总是经由收件箱、在下一回合注入"。 这只对路径 A 成立。await_agents 和 get_agent_result 不消费收件箱——它们从 MasterOrchestrator 的 _results_by_id 直接读结果并作为工具返回值返回。 收件箱的入队（_on_agent_complete_callback）照常发生，但若没有"下一回合"去 drain，那些便条就只是躺在队列里， 直到任务收尾被 clear() 丢弃。实测见 第 7 节。

真正发生阻塞时，它不过是 await_agents 内部的一个条件变量等待 （lib/swarm/master.py）：

while True:
    with self._lock:
        done_now = set(self._results_by_id.keys())
        if mode == 'any' and (to_wait & done_now):  break
        if mode == 'all' and to_wait.issubset(done_now): break
    remaining = deadline - time.monotonic()
    if remaining <= 0:
        timed_out = True; break
    self._completion_event.clear()
    self._completion_event.wait(timeout=min(remaining, 2.0))   # ← 唯一真正的"等待"

⚠️ 如何判断你遇到的是哪个场景

看对话记录 / 日志： 若 spawn 之后紧跟着 await_agents / get_agent_result 工具调用 → 场景 B（结果走工具返回， 收件箱被绕过，debug 面板看不到 <swarm-update>）。 若中间看到的是其他工具（grep、read 等），且之后还有 LLM 回合 → 场景 A（结果经由收件箱注入， 那一回合的 请求前 快照里能看到一条 <swarm-update> 的 user 消息）。 经验上，当 swarm 就是整个任务时，模型几乎总会选场景 B，所以你很少见到收件箱注入。

6. ⭐ 关键：结果回传有两条不同的路径

这是把一切串起来的核心。子智能体的产出如何回到主智能体的上下文，取决于主智能体 spawn 之后做了什么：

路径 A —— 收件箱注入路径 B —— 工具返回值
触发条件 spawn 后主智能体继续调用别的工具（grep/read/…），而且之后还有 LLM 回合 主智能体调用 await_agents 或 get_agent_result
结果载体 一条 role:"user" 消息，内容是 <swarm-update> XML await_agents / get_agent_result 的 tool 返回结果
是否消费收件箱 ✅ 是（drain() 在每回合 LLM 调用前执行） ❌ 否——直接从 _results_by_id 读，收件箱被绕过
是否阻塞主智能体 否（真正的并行） await_agents 会阻塞 ≤120s；get_agent_result 不阻塞
debug 面板可见性 那一回合的 请求前 快照里能看到一条 <swarm-update> 的 USER 消息 （没有特殊标签，外观和普通用户消息一样） 看不到 <swarm-update>；只看到 await_agents / get_agent_result 这些 ASSISTANT 工具调用和它们的 TOOL 返回
收件箱里的便条结局 被取用并注入 无人取用，任务结束时 clear() 丢弃，日志记 cleared N unread item(s)

✅ 为什么你在前端 / debug 面板从没见过收件箱

1. "收件箱"本身没有 UI。它只是 lib/agent_inbox.py 里的一个内存队列，是给模型看的， 不是给人看的——刻意没有任何面板、标签或图标。

2. 即便走了路径 A，注入物也只是一条普通 user 消息。按设计它不带 _isMeta 标记、不裹 <system-reminder>，所以在 debug 面板里它就是一条 USER 气泡， 内容碰巧是 <swarm-update>…</swarm-update> 而已，没有"收件箱"字样。

3. 而当 swarm 是整个任务时，模型几乎总走路径 B（await_agents），于是收件箱被整体绕过—— 这就是你"哪儿都没见过它"的真正原因。

7. 实战案例：对话 mpuxb6omxi1ti5 的日志复盘

这正是上面"为什么看不到收件箱"的活体证据。下面是从 logs/app.log 抽取的真实时间线 （Task 21a7950b，模型 claude-opus-4.8）：

16:06:48  R6: spawn_agents → 启动 3 个 agent（reviewer + 2×coder）   [工具 #11/#12]
16:06:54  R7: await_agents(mode='all', timeout=120)                  [工具 #13]
          ⏳ 主任务线程在此阻塞 93.1s
16:07:43      AGENT_COMPLETE coder-08ec3f86   (54.3s)  ┐
16:07:57      AGENT_COMPLETE reviewer-65bf6567 (69.0s)  │ 三条 <swarm-update>
16:08:27      AGENT_COMPLETE coder-d5eb8a36   (98.5s)  ┘ 依次入队收件箱
16:08:27  Driver done → await_agents 返回（result_len=2185）         [工具 #14]
16:08:35  get_agent_result ×3（取完整正文 5557/…/… 字）   [工具 #15/#16/#17/#18]
16:09:16  R7 输出最终答案，finish_reason=stop → 任务结束
16:09:16  [Inbox] cleared 3 unread item(s) on task end   ← ★ 决定性证据

这张时间线说明了什么

  • "为什么 agent 跑完后总有个 await"：其实 await_agents 是在 spawn 之后立刻调用的， 它就是那个在等的动作；在记录里它夹在 spawn 和结果之间，看着像"跑完才 await"。模型这么做是合理的—— 整个任务就是这三个审计，spawn 完它没别的事可干，于是按系统提示词的建议去 await_agents。
  • 三条 <swarm-update> 确实被入队了（_on_agent_complete_callback 照常跑）， 但结果是通过 await_agents + 3×get_agent_result 的工具返回拿到的。
  • R7 直接 finish_reason=stop，没有 R8。收件箱的 drain 钩子只在"新回合的 LLM 调用前"触发—— 既然没有下一回合，drain 从未执行。
  • 于是那 3 条便条原封不动躺到任务收尾，被 clear() 丢弃：日志里清清楚楚写着 cleared 3 unread item(s) on task end。这就是 debug 面板里没有任何 <swarm-update> 的根因。

想自己验证：在 logs/app.log 里 grep injected N swarm-update item(s) as 1 user message at round（路径 A 发生时才有这行） 与 cleared N unread item(s) on task end（路径 B / 提前结束时出现这行）。

8. 前端行为

浏览器从不读取收件箱——它渲染的是任务进行中推送的 UI 事件。相关处理逻辑位于 static/js/ui/sse_pipeline.js。

UI 监听的事件类型

事件对 swarm 面板的影响
swarm_phase (spawning / spawn_more / complete) 创建或收尾 swarm 面板；用各 agent 的目标填充卡片；设置最终的"✅ Swarm 完成 —— N 个 agent，T tokens"汇总行。
swarm_agent_complete 把某张 agent 卡片标记为完成，并展示它的耗时、token 数和 200 字预览。
swarm_agent_phase / _progress / _tool_call / _error 逐 agent 的实时状态更新（如"🔄 正在重试 [coder]…"、当前工具、错误信息）。

"回合漂移"难题——以及 UI 如何解决

由于 swarm 是异步的，一个 agent 可能在晚于启动它的那个回合才完成。届时原来那条 assistant 消息已经"漂移"（滚到了对话历史里）。朴素的 UI 会把完成事件挂到错误的消息上——甚至丢弃它。

流水线的做法是：给启动 swarm 的那条 assistant 消息打上 _swarmRoundNum 标记， 并给它的工具回合面板打上 _swarmActive / _asyncRunning 标记。之后到来的 swarm_agent_* 事件会向前回溯历史消息，找到拥有该 agentId 的那个面板并就地更新—— 因此即便完成事件在几个回合后才到达，也总能落到正确的、原始的 swarm 面板上。

用户实际看到的

  • 在工具流的时间线上、spawn 发生的位置，出现一块内嵌的 swarm 面板——一排 agent 卡片，每张展示角色 + 目标。
  • 卡片实时更新：转圈 → ✅/❌，并带上耗时与简短预览。点击卡片可展开它的完整输出。
  • 底部有一行汇总：agent 数量、失败数、总 token、总耗时。
  • 关键在于：尽管 agent 异步完成，面板始终锚定在它原始的对话位置——从而保持工具的时间先后顺序。
