# Task engine
`lib/tasks_pkg/` executes one model/tool attempt. It is an executor, not a conversation repository or browser transport. Explicit application tool delivery uses `lib/tasks_pkg/tool_delivery.py`: one verified successful sole-call round binds an application-owned durable verifier and exact model-supplied reply, closes the existing checkpoint, and reaches the ordinary terminal sink without another model request. It preserves the physical provider finish and usage; the port owns no durable store, acceptance, replay or model loop. Handler exceptions settle the tool round as an error and preserve the exception type and cause. Problem: unconditional schema correction advice misclassified environment failures. Decision: admission owns schema errors; the executor preserves the cause and uses the effect-recovery owner for typed runtime guidance (see contracts/TOOL_EFFECT_RECOVERY.md). Alternative: treating every ValueError as bad arguments also misclassifies authority failures. Verify with tests/tasks_pkg/test_handler_runtime_failure.py.

Live file-change stamps in `commit_round/_derive.py` are best-effort presentation; settlement rebuilds from the authoritative journal. Unexpected registry misses and stamp failures emit WARNING with a short task identifier and bounded state/exception-type metadata, never file entries or exception text. A miss probes state afterward (not an atomic witness); terminal/aborted late callbacks stay DEBUG. Problem: DEBUG-only failures hid missing live cards. Decision: use the existing incident/coalescing pipeline without new per-task log state; warning on every late callback was rejected as routine lifecycle noise. Specs: `tests/tasks_pkg/test_commit_round_derive.py`.

## Boundary
A text-only round may carry `None` tool schemas: discovery treats this as an empty tool set and retracts unavailable private-input directories before prompt admission. Keep the original schema carrier for provider compilation and token evidence; normalizing every consumer would change those contracts to repair discovery. Input is an API-ready message list plus task configuration. Output is a stream of typed task events and cumulative executor state. For conversation work, the task is bound to a durable `(turnId, attemptId, userId)` before execution. Fatal and BaseException exits hand the loop-retained messages back before terminal capture; ordinary terminal errors use the shared terminal stamp before DONE/persistence, preserving tool evidence and measured elapsed time without replay or reconstructing earlier compaction.

Queue-wait metrics are non-authoritative: ordinary observer exceptions are logged without preventing callable execution or Future/accounting settlement. Letting the observer escape was rejected because it strands a running Future; `tests/agent_core/test_agent_worker_executor.py` fault-injects this boundary. Queued cancellation in the demand Agent executor removes the job under the scheduler lock, then invokes Future callbacks outside that lock. Removed Futures complete the executor cancellation handshake so `wait()` and `as_completed()` observe a terminal result without waiting for a worker that will never consume the job. Direct Future cancellation and shutdown retain the same rule; running and quarantined workers keep their existing lifecycle.

Swarm scheduler startup isolation: **Problem:** demand `submit` starts physical threads, and holding the scheduler state lock during it blocked status reads, pending cancellation and completion publication. **Decision:** reserve dependency-ready specs atomically in `_running`, then submit outside the state lock; refused handoffs settle once through the ordinary completion callback/queue and unblock dependents without retrying execution. Reservations remain visible to idle/shutdown throughout startup, and workers retain pre-entry Stop/admission checks. **Alternative rejected:** dropping reservations until after submit lets idle/shutdown lose accepted work. `tests/swarm/test_swarm_startup_isolation.py` holds submission behind an Event and requires status plus pending cancellation to complete before releasing startup, checks failed siblings/dependents settle once, and checks Stop during handoff cannot enter the agent. This is controlled contention evidence, not a production throughput claim.

Execution synchronization boundaries: task startup's `scheduling_phase_lock` is per invocation (including durable start/workspace binding) and prevents stale queued-phase publication; prepared restoration serializes only the same task identity; event delivery's producer lock preserves task-local FIFO/durability barriers. The demand kernel's separate startup lock protects physical handoff rollback, while its lifecycle condition protects accounting; neither is a task-count quota. Swarm master snapshot CAS throttling holds only its timestamp lock, not storage I/O. Resource-probed worker hints size idle reuse, not demand admission. Retaining these correctness locks rather than deleting all locks preserves Stop and durable settlement. These are bounded owner inspections, not an exhaustive lock census.

The authoritative flow is:

```text
turn command
  -> pending generation attempt
  -> claim + bind executor task (pending/queued) -> worker entry + fenced start (running)
  -> model/tool loop
  -> append_event -> task-owned FIFO (executor continues)
  -> ordered background turn.event.record (revision patch + carried task event)
  -> v3 conversation sync
```

`manager.prepared.restore_prepared_task` rebuilds server-owned headless input via normal construction without hooks; domain proof and CAS own recovery/admission. Per-task identity locks reuse only identical unstarted carriers; independent restores have no global lock or 500 ms busy refusal. Waiters retain the same lock through construction, and idle keys disappear from the weak lock pool. Same-identity recursion is a lifecycle error. Metadata marks restorable tasks before publication; failed persistence signals local resources but returns an error instead of a durable receipt.

The required terminal port may prepare bounded opaque domain context for the owned result CAS; preparation failure retains debt, and rejected ownership suppresses delivery. The task result table is recovery/diagnostic storage, not a second transcript; renderable content and settlement stay in turn authority. Normal and Flow chat share demand execution: independent accepted work prepares physical workers immediately, resource hints size idle reuse, and settlement retains actual worker ownership. The root executor starts accepted work on demand; its short handoff deque owns cancellation before worker entry, with no active-count or queue-capacity gate. Launch worker settings size idle reuse. Proven-wedged threads keep physical ownership and retire on return without blocking unrelated submissions. The registered `executor_queued` phase describes transient handoff evidence; legacy configured-capacity fields are hints, not Agent slots. Per-task ordering keeps late queued observations from overwriting `workerStarting`. Provider backoff retains `retrying`. `worker_executor.py` accepts an optional state publication port so production pools aggregate live owners without overriding one another; the ordinary root snapshot remains unchanged. After settlement, only terminal `round_committed` and `preference_learned` observers use standalone task replay; their dedicated settled-Turn CAS owns projection enrichment, while every other late frame retains the zombie fence. Detached swarm frames (`swarm_phase`, `swarm_agent_phase`, `swarm_agent_progress`, `swarm_agent_complete`, `swarm_agent_tool_call`) join them on a terminal task: a spawned sub-agent outlives its settled spawning turn, and its pure panel/replay frames must persist standalone rather than re-enter the closed attempt and trip the fence into force-cancelling the swarm.

Automatic translation is triggered only after Turn authority settles. Its already-target skip is a whole-document identity decision: dominant-language classification of the raw buffer is insufficient because a target-language opening may hide foreign-language sections later, and because technical Chinese is often identifier-heavy (inline code, URLs, API names). Terminal root, Flow-visible child, and incremental segment paths share the conservative `lib/translate/skip_policy.py` predicate, which inspects prose after masking markup/code/URLs; mixed English prose proceeds to translation, while symbols, bare paths/URLs, and genuinely monolingual target prose may be committed as an explicit no-op. Literal `<think>` mentions in source or translated text are document content, not MiniMax reasoning wrappers, and must not truncate the rest of the message.

Pending task binding alone does not prove queue residence: cold/live presentation uses `executor_preparing` until the executor publishes explicit queue evidence. The queue frame is the attempt's first recorded event and already marks it running, so presentation shows `executor_queued` while it is the latest frame; the worker's first phase replaces it, and a storage wedge withholding later frames presents `storage_wedged`. Startup stage histograms distinguish persistence and context preparation from real executor wait. Best-effort birth/running diagnostics retain their shared 500 ms budget. Required admission uses bounded per-RPC windows and the same task-scoped persistence wait as terminal writes, retaining exact receipt/payload across storage pressure instead of rejecting accepted work. Terminal event debt drains before release; explicit finite diagnostic probes retain their timeout verdict. Version/status witnesses use owner-scoped compact `task_results.replay_get`, avoiding cumulative-result blob hydration, while the atomic checkpoint preserves abort tombstones and owner/parent/status fences.

Worker entry publishes an existing `working` phase immediately after the durable running transition: all tasks start with `workerStarting`. Canonical roots execute directly by default; only actual opted-in checkout creation emits `workspacePreparing`, then `workerStarting` when binding succeeds. Execution selection (`workspace_policy.py`; process `TOFU_WORKSPACE_MODE` overrides repository-local `tofu.workspaceMode`) is independent of linear Git publication. Existing registered workspaces keep their ownership regardless of the new default. Tools and the runner still cannot enter until every workspace binds; failed binding reaches ordinary rejected-start settlement. Correlated startup start/complete anchors separate dispatch, worker-entry and nested workspace-binding durations under the existing metrics/log owners; see [logging](../LOGGING.md#task-startup-timing-anchors). Completion uses paired `[TaskCompletionTiming]` anchors and `tofu_task_completion_stage_seconds` for persistence, workspace delivery/evidence and terminal listeners, with success/error/deferred outcomes. Spans are inclusive, not additive; identity stays in logs, never metric labels. Diagnostic failures cannot change receiver returns, exceptions or delivery-before-listener ordering; verify `tests/observability/test_task_completion_metrics.py` and `tests/tasks_pkg/test_finalize_persist_before_autopilot.py`.

## Internal stop provenance

**Problem:** physical abort also stops silent/deadline-expired invocations; misreading it as user Stop suppresses failure diagnostics and bounded delivery. **Decision:** `invocation.py` stamps cause/error before signaling; `turn_verdict` derives failed `invocation_stalled` / `invocation_deadline` ahead of client-abort evidence. Swarm preserves this on normal/exception exits, with isolated parent state and committed receipts. Explicit Stop retains its no-auto-wake gate. **Alternatives rejected:** longer timeouts hide stalls; waking cancelled agents violates Stop; a new UI status forks authority. Specs: Swarm invocation/failure continuation and turn-verdict tests. See [execution modes](../TASK_EXECUTION_MODES.md).

## Native durable execution composition

**Problem:** the native process could acknowledge an arbitrary host callback without binding the application's task/Turn recovery and delivery owner. **Decision:** `lib/tasks_pkg/native_execution.py::run_native_task` combines a single-use v2 route with `NativeTaskTerminalPolicy` and the existing `persist_task_result(..., _defer_heavy_release=True)` writer. Explicit principal, task, operation ID, candidate byte budget, terminal projector and lifecycle-owned executor are required before route consumption. The application projector uses existing text/round/accounting/Turn owners once; failed commit ACKs retry that frozen projection without model/tool reexecution. Changed candidate, task owner or projected outcome fails closed; a proven recovery ownership fence rejects rather than retries. Failed settlement may persist an error, never success. Cancellation joins the physical writer before releasing serialization. Heavy state remains available through native publication and is released by the application's existing terminal lifecycle. **Alternatives rejected:** direct SQL would fork storage fences; rerunning projection can duplicate terminal effects; detached executor futures can write after cancellation has apparently finished. This explicit entry is not the production default. Full protocol/context/tool policy and process-loss reconciliation still belong to their existing owners; the adapter does not infer paid usage or replay unknown effects.

Tests: `tests/agent_core/test_native_task_terminal.py`, `test_native_task_execution.py` and `tests/storage/test_native_task_terminal.py`. The storage tests use disposable authorities. Real native success, stream failure and cancellation must commit their matching task/Turn outcome; cancellation joins persistence before process admission returns to zero. These cases require `TOFU_NATIVE_TERMINAL_TEST_ARCHIVE` pointing to a verified archive. When testing a worktree test against the current application, use pytest importlib mode from the application root and set `TOFU_NATIVE_TERMINAL_TEST_APPLICATION_ROOT`; the test checks the imported execution owner. Native engine tests retain source identity verification and require `TOFUDB_BIN` to match that application source exactly.

**Problem:** configured native text required a caller-written application projector, so the native entry did not supply ordinary live task/Turn delivery. **Decision:** `text_progress: true` selects `project_native_text` unless an explicit callback is supplied. It validates the owned live task, appends content or reasoning under the existing text lock, then publishes an ordinary delta through the public manager facade after releasing that lock. The native controller owns ordering and byte admission; producer acceptance does not imply durable Turn visibility. Existing coalescing may defer the projection until its next boundary, and the terminal writer joins delivery debt. Received paid text survives publication failure and an already-signaled Stop; reset generation is unchanged by deltas. **Alternatives considered:** a separate native queue or sequence ledger duplicates delivery authority; resetting each delta breaks generation semantics; holding the text lock during publication deadlocks snapshot consumers. ## Selected native application checkpoints

**Problem:** durable native rounds need the selected authority and terminal debt ordering without a Python journal. **Decision:** NativeCheckpointPolicy delegates load/begin/complete/finish to the existing embedded storage port on the supplied executor. Explicit recovery restores financial/time policy; cancellation joins physical calls and retains an acquired capability. The shared Rust journal fences terminal work; C ABI finish freezes status/Suspend before retries. Only completed Suspend plus Aborted preserves recovery, and release additionally requires the canonical terminal writer's accepted ACK. Failed/unknown acquisition or terminal save never grants takeover. Joined cleanup forgets volatile metadata and preserves the original exception. **Alternatives:** releasing before canonical commit opens unfinished task recovery; a Python transition owner duplicates Rust authority.

Verify tests/agent_core/test_native_checkpoint_policy.py and tests/storage/test_native_checkpoint_policy.py with explicit private library, binary and source SHA environment variables from the checkpoint SDK test. Native checkpoint capability is optional and selected embedded only; SQL/daemon/default production execution promotion and full application performance remain pending.

## Shared ReAct lifecycle


Required storage steps use `persistence_wait.wait_for_persistence`; model/tool/ready boundaries use `checkpoint_invocation` regardless of creator. Transient pressure parks only the frozen write and is excluded from stall reaping while ownership remains proved. Presentation/domain ports and creator lineage do not select private retries or terminal builders. See the origin-neutral persistence section of [execution modes](../TASK_EXECUTION_MODES.md) for Stop/shutdown/receipt semantics. `run_agent_loop` is the sole LLM/tool round-loop authority for root chat, swarm workers, timer and research engines. It owns round numbering, continue/stop sites, three abort placements, timeout counting and the post-tool checkpoint. Root request building, anomaly policy, budget/protocol gates, event projection and semantic loop detection are typed `_root_agent_loop.py` hooks returning `LoopDirective`; they never own another LLM/tool `while` or infer completion from response text. FlowExecutor owns graph iteration only; role execution delegates through the shared agent runner.

Independent guards bound non-recovering tool loops. The shared no-progress guard runs only after tool execution and fingerprints the ordered calls, world version, and exact model-visible result snapshot. It accumulates only when all three are unchanged in consecutive completed rounds; a changed result, changed operation, changed world, verified success, or missing/incomplete result evidence resets and fails open. Read-only work and elapsed rounds alone are never stall evidence. Stable `nonretryable_failure_signatures` accept only a canonical non-retryable typed error (the sparse model error or a legacy full `tofu.tool-result/v2` record) plus the concrete tool/argument identity. Root and Swarm halt after three equal terminal-failure rounds with `exit_reason=nonretryable_tool_failure`. Any success, mixed/retryable/malformed or legacy result, or changed operation resets the streak; unknown results fail open. Problem: an unchanged rejected progress message could consume all recovery rounds without explaining that the task itself remained executable. Decision: the shared runner exposes its existing failure counter to the adapter, which inserts one ordinary `tool_progress` safety note before the final recovery round. The note directs argument correction or independent authorized work and distinguishes `retryable=false` from task failure. It is visible system intervention, never human permission. Alternatives rejected: removing the bound permits infinite loops; silently swallowing the error loses evidence; resetting the counter in presentation code creates another progress authority. Real child-invocation tests prove correction can finish, while unchanged failures still stop. Root post-dispatch policy also distinguishes byte-identical call/outcome loops from semantic no-progress no-ops and already-covered reads, gives one `_isMeta` safety correction, then stops continued waste. Problem (2026-11-04, conv `mw2008zee91571`): read credit and the turn-wide correction count outlived the evidence, so after pressure compaction replaced earlier results with re-call placeholders the model's re-fetches counted as redundant, and a correction from 36 rounds earlier authorized the stop. Decision: every credited read, partial-artifact obligation and previous-round result is bound to the tool message that carries it (shape plus SHA-256 of its content); compaction, removal, or a carrying message that omits the receipt (for example a program's return value) withdraws the credit, so re-fetching hidden evidence is progress and an identical call whose prior result left context restarts the exact, poll and failure chains. A redundant-read stop needs a re-read warning from the current redundant streak (new evidence, a possible write or an operator steer retires it), and an unresolved-artifact stop needs that source's own earlier warning; only the explicit-noop guard keeps the turn-wide rule that blocks laundering. One intervention per round: a round in which any guard corrected never also stops, so the model answers the newest correction and the next offending round stops. Alternatives rejected: clearing all read credit on any compaction forgets still-visible results and lets real loops escape; expiring warnings after a fixed number of rounds is a tuning knob; trusting request identity without visibility recreates the incident. For V2 partial results, the guard reconstructs its server observation from sparse `toolContent` plus the non-model `v1` round sidecar (and still reads legacy full envelopes). Range/cursor/limit and presentation-only changes retain one resource identity across registered idempotent tools; only the model-visible summary/items/error projection counts as evidence, so new pages remain productive but new artifact IDs cannot disguise an identical projection. The guard first directs the model to `read_tool_artifact`/`search_tool_artifact` or a visibly advancing narrower read, then stops one continued no-progress episode. Productive serial calls never trigger efficiency/adoption prompts or automatic gateway-only exposure: call count alone proves neither independence nor waste. Actual safety corrections and stops are recorded through `record_injected_note` as ordered `system_note` segments. Repeated identical successful verification ends explicitly incomplete, not as proof that the user's task is complete; genuine background-task acceptance retains its separate handoff semantics. Engine-authored stall/stream-continuation corrections and pure peer/swarm evidence are likewise transparent to current-user extraction; an inbox row containing human steering is not.

Tool-result evidence binds each normalized operation to its model-visible result
and retains the count of equal operation/result pairs. `progress_evidence.py`
owns normalization and counted IDs for the serial runner and native gateway;
the existing Python/Rust ledgers still own streaks and stopping. **Problem:** a
set of result-only hashes merged different targets and discarded multiplicity,
so swapped target values or changed repeated-result counts could stop productive
work. **Decision:** compare the complete operation/result multiset. Callback
completion order and provider correlation IDs carry no progress. **Alternatives
rejected:** hashing completion order invents progress from scheduling; removing
the breaker permits unchanged loops. Batch/probe completeness requires a true
boolean plus a collection of string IDs from that same source. Malformed
observations fail open; a valid independent source remains usable.

Native evidence retains only the current bounded hashes/counts and is consumed
once or released on close. No worker, durable state, model message or execution
cap is added. A 100-round synthetic ingestion measurement (32 results of about 4 KiB
per round, median of five runs) increased from 79.86 ms to 88.67 ms, about 2.8 µs
per call; this is local bookkeeping, not provider latency. Traced peak increased
from 18,588 to 27,034 bytes and live allocations after collection from 4,564 to
6,360 bytes. The 32 emitted IDs occupy 2,112 bytes instead of 2,048 under the same
feedback bound; 10,000 identical results occupy one 70-byte counted ID. Budget
overflow still withdraws evidence, and close releases the carrier. Checkpoints
retain their existing opaque digest schema: current snapshots preserve streaks;
a snapshot with older result-only digests establishes a fresh evidence baseline
on its first new result, without replaying completed tools or resetting budgets.
Specs: `test_progress_result_evidence.py`, `test_native_progress.py`, actual
pipeline batches in `test_native_gateway.py`, and shared-loop recovery tests.

Flow convergence policy follows the same evidence hierarchy. Similar critic or virtual-user wording is an advisory signal only: it may inject one strategy-change directive but cannot terminate a run. The same is true when a complete structured `[PROGRESS]` signal stays flat across edit-shipping turns with overlapping targets: a complex fix may need several incremental edits before a criterion becomes fully resolved. The zero-deliverable hint explicitly permits focused read-only investigation and forbids mutation merely to satisfy the guard. Hard boundaries remain transparent finite iteration/turn budgets. The manager's `stuck_no_progress` reaper is separate infrastructure liveness policy: it fails a task only when both the real-event clock and dispatch heartbeat are stale, exempts live human/model waits, and first interrupts the foreground command whose own output has been silent past the threshold while the dispatch heartbeat is stale (its sibling commands keep running), escalating to task failure only when that interrupt goes unconsumed. Terminal stdin prompts retire on text, EOF, timeout and wait failure; cleanup clears prompt metadata, emits the existing resolution event, and preserves a concurrently installed terminal round status.

One provider response is an ordered occurrence list. Every response position is an independent model action even when tool name, arguments, caller, or provider call ID are byte-identical. Blank, recycled, or duplicate IDs are reminted before history/settlement so each assistant call retains exactly one adjacent result; equality never elects one physical owner for sibling positions. Only a byte-identical transport retransmission proven to target the same stable stream slot may be suppressed before execution. Across provider responses the same payload is likewise a fresh model action governed by ordinary evidence/world-state guards.

Continue replay groups history by ordered `(attemptId/taskId, llmRound, contiguous occurrence)`, never a Turn-wide `llmRound` dictionary. Root Continue advances logical model/tool counters from retained chronology, including historical resets; private producer identities still distinguish batches. Merging equal historical numbers fabricates a provider batch, reorders history, multiplies checklist/tool context and can induce repetition. Legacy unstamped rows use contiguous order and observable `roundNum` resets without inventing ownership. Continue, checkpoint, segment, and cold-history reconstruction share one causal-prefix validator: explicitly superseded provider-attempt artifacts and identity-free display rows are transparent; any other identity-bearing malformed row stops replay before dependent calls. Exact result text is the execution receipt regardless of `done`, `error`, `rejected`, or `aborted` verdict, and structured arguments are canonicalized without mutating durable audit rows. A malformed supplied `toolHistory` fails the request before any partial history reaches a model. Resume text, tool rounds, checklist state, usage, and file metadata are validated and detached as one preflight before project setup or prefetch; hydration begins only after the whole snapshot is valid. `todo_write` is a Codex-style full-plan snapshot: the same call creates, updates, replaces, reopens, or clears the list, with optional `explanation`. Items contain `content` and `status` (`pending`, `in_progress`, `blocked`, `completed`); operation selectors, item IDs, nesting, revision preconditions and mandatory replan reasons are not model protocol. The bounded flat v3 current state stores `todos`, `explanation` and `update_count`; raw tool rounds remain the durable audit rather than a copied stack/history. New snapshots allow 24 items × 512-character steps and a 2,048-character explanation. Valid legacy v2 checkpoints migrate all ancestor and child lists in order (up to 144 rows), preserving their work and historical blocked statuses without resuming stack semantics. Invalid checkpoints fail before task mutation. Legacy `sync/replan` calls are full-snapshot aliases; stale child-only `push` calls are rejected with a full-list hint rather than silently losing parent work. Checklist progress is advisory: it neither re-drives a normal stop nor establishes task success. Existing stream, cancellation, wait and verification verdicts retain authority. Specs: `test_todo_tool_schema.py`, `test_todo_continuation.py`, `test_checklist_context.py`. Checkpoint resume reconstructs its interrupted assistant/tool rounds through the same canonical wire projector used by the next ordinary conversation rebuild, inserts that suffix before the optional resume prefill, and separately retains the raw rounds for durable settlement. The resumed request therefore keeps tool evidence and remains a byte-stable cache prefix for its successor. Resume snapshots carry no round-count or serialized-byte ceiling: oversized histories are folded by working-set compaction before dispatch, never rejected. `continuation_rounds.py` derives the root model/tool frontier from ordered retained batches, keeping gateway child ordinals separate. The shared chassis accepts that frontier without inventing paid dispatches or breaker credit. Resume config also carries the accepted checklist and usage/API ledger; live and failed resumed requests preserve cumulative accounting. Spec: `tests/tasks_pkg/test_seamless_continuation.py` and the root-adapter continuation regressions. Swarm history is durable on the `spawn_agents` tool round: the returned handle identifies that wave, while `_swarmSnapshot` carries each agent's status, full result preview, token/timing/file counters, and bounded tool-call timeline. Agent callbacks stamp incremental/final snapshots when the handle is already visible. Tool settlement is the mandatory race-repair boundary: once it writes `toolContent`, it immediately reconciles the still-authoritative active session onto that exact round. This closes fast-agent completion before handle publication; the monotonic snapshot version and equality check make callback/settlement/replay writes idempotent. A detached CAS writer remains responsible only after the owning attempt settles.

Swarm push preserves canonical `conversationId`; subscription `taskId` and producer `executionTaskId` are distinct transport identities, leaving durable task events unchanged (see [push identity](../contracts/EVENTS.md#push-transport-identity-is-not-task-event-identity)). Swarm completion records canonical child evidence before presentation callbacks; sink or snapshot failures cannot lose a result or prevent waiter notification. Inbox insertion is fenced against await/get/inbox delivery under the session result lock, while UI and persistence callbacks run outside it. Repeated completion callbacks are idempotent and delivery receipts remain bounded by completed session IDs. Terminal `swarm_phase:complete` denotes driver settlement, not universal success: `outcome`, fixed `outcomeCounts` (completed/failed/cancelled/stalled/unknown), and bounded `reasonCodes` distinguish cancellation, liveness stops, and missing evidence. The `swarm.driver_done` structured log carries those same aggregate fields without objectives, prompts, result text, or free-form errors.

### Structured and templated delegation

**Problem:** in Delegate Mode the root only orchestrates. Same-shape work (one audit per module, one check per URL) was written as N paraphrased objectives, so workers did not receive identical instructions, and N free-text reports grew the root context in a different shape for every task.

**Decision:** `spawn_agents` accepts top-level `templates` (`name -> {objective?, context?, role?, tools?, output_schema?}`; other keys are rejected) and per-agent `template` + `params`. A template is a shared preset. `lib/swarm/spawn_contracts.py` expands a templated agent's objective to the template objective verbatim, then the agent's own objective, then a `## Parameters` block of `- key: value` lines with sorted keys (strings verbatim, other values sorted-key JSON); blank parts are omitted and parts are separated by a blank line. Same-shape workers therefore share a byte-identical prefix while keeping distinct objectives for scheduler de-duplication. Context composes the same way (template first); agent `role`/`tools`/`output_schema` override the template. `params` without `template`, unknown names, non-object params, non-string objective/context, and a templated agent with no objective in either its template or itself fail before launch as retryable `invalid_spawn_contract`; an untemplated agent without an objective is `invalid_agent`. The item schema has no `required` list (no combinators); the handler enforces "objective or template".

**Problem (templates as presets):** workers commonly share role and context while each needs a distinct objective. Treating a template as a replacement for the objective (template objective required, `template` plus `objective` rejected) fails that shape before launch and pushes the caller to copy the shared context into every agent. **Decision:** objective composition follows the context rule, so a template may omit its objective and an agent may add its own. An agent that sets no objective still receives exactly the template objective plus its parameter block. **Alternatives considered:** a clearer rejection still costs a failed round for the natural shape, and its correction (moving each objective into `params`) would be a workaround presented as the API. Letting an agent objective replace the template objective would drop the shared prefix that same-shape workers rely on.

`output_schema` must be a draft 2020-12 schema with top-level `type: object`, local `#/` references only (no `$id`/`$anchor`/`$dynamicAnchor`) and at most 16,384 serialized characters. It persists on `SubTaskSpec`. The worker's objective message gains one `## Result contract` section (checkpoint rebuild keeps the retained message instead of appending another) and the child carries `_invocationOutputSchema`. A `stop` round without tool calls whose answer neither parses (raw JSON, one fenced block, or prose around one object) nor validates gets exactly one corrective round through the `output_contract` injection. The vetoed answer stays on the wire and in continuation prose, while the text accumulators reset so the corrected object alone is the deliverable. At settlement a valid answer becomes canonical compact JSON. A still-invalid answer keeps its raw text and `completed` status (never retried, so side effects are not replayed); `SubAgentResult.contract_error` (`output_schema violation: <pointer>: <message>`) reaches `<swarm-update>` `<error>`, `poll`/`get_agent_result` (`contract_error`) and recovery payloads.

**Alternatives considered:** provider-native `response_format` on every worker round was rejected because it constrains the tool-calling rounds that precede the final answer. Free-text results were rejected because the root context grows without bound and varies per task. Mid-text `{{placeholder}}` substitution was rejected because a shared verbatim prefix keeps same-shape workers identically instructed and prompt-cache friendly. Specs: `tests/swarm/test_spawn_contracts.py`, `tests/tasks_pkg/test_delegate_mode.py`.

Swarm snapshot matching is execution-scoped: the spawn handle's `swarm_run_id` retains the original session task across follow-up turns; `swarm_id` remains the launch-task alias. Snapshots carry the stable session identity in `swarm_id`. Legacy receipts match only by exact known identity, never by the conversation lookup key or reused agent names. Follow-up waves restrict snapshots to their own launch roster; a snapshot from another execution must never overwrite a prior run. The persisted `toolContent` is usually the SPARSE `summary_items` model projection (`{"summary", "items": [handle]}`), from which `lib/tools/result_envelope.py::_model_projection` intentionally drops `contractVersion`; every reader recovering the handle (snapshot matching, elision-stub salvage, frontend panel recovery) must unwrap through `sparse_result_items` / the swarm panel's equivalent — gating on the v2 marker alone recovers zero agents and renders an empty panel over fully-persisted data. Every resume operation (`continue`, `checkpoint_resume`, `answer_guidance`) also inherits the settled projection's `modifiedFiles`/`modifiedFileList` as `checkpointModifiedFiles`/`checkpointModifiedFileList`, so the resumed attempt's commit merge unions pre-gap edits with its own instead of the settled card listing only resume-window files. When a restart settled the orphaned attempt before its live file-change stamps were folded (the durable projection has no list to carry), attempt dispatch derives the turn-scoped list from the conv-isolated modifications journal — entries at or after the turn's creation across the primary and extra workspace roots.

Explicit Stop propagation, interruptible waits, child evidence, and honest terminal timing follow [TURN_SETTLEMENT.md](../contracts/TURN_SETTLEMENT.md#explicit-user-cancellation).

Native model-route delegation: **Problem:** a detached swarm child inherited the parent's ephemeral hard pin, but the parent execution session disposed those slots on turn settlement, leaving a live child with no dispatchable slot. **Decision:** the swarm persists the parent's owner-authorized model selection and routing policy (not its pin); each child uses `create_task` to mint and bind its own owner-scoped route group. Its execution session releases the group at child cancellation/completion/discard. An incompatible child model override is rejected as `model_route_unavailable` before minting; it never escapes to the global credential pool. **Alternative rejected:** leasing the parent's group would couple detached lifetimes to the parent and require cross-session lease accounting. Legacy pin-only callers retain their existing pin behavior. Spec: `tests/tasks_pkg/test_child_invocation.py`.

Delegation after a fallback round: **Problem:** a successful fallback round stamps its live model on `task['model']` for telemetry while `config.model` keeps the admitted selection. The child-route check compared children against the live model, so every `spawn_agents` after a fallback was rejected at launch as a child model override, and the session proxy recorded the fallback model beside the selection's ModelRef. **Decision:** a child that names the parent's live model or its admitted `config.model` inherits the parent's ModelRef, and the swarm session records the admitted selection's model. Children start on the parent's selection and run their own fallback chain; a round-local fallback is never delegated as a route. **Alternatives rejected:** minting a ModelRef for the fallback model would let delegation select a route the parent never admitted; dropping the live-model stamp would remove the real model from per-round telemetry. Spec: `tests/tasks_pkg/test_child_invocation.py`, `tests/swarm/test_spawn_tool_authority.py`.

Conversation-backed `await_agents` also yields for pending operator steer or background-command completion at its existing ≤100 ms wait checks. The result carries `yield_reason='pending_input'`, not timeout or agent completion; it consumes neither inbox evidence nor agent results and leaves children running. Cancellation wins. Injection still follows normal tool settlement, so a blocking sibling tool or an in-flight provider call is not preempted. Headless callers retain ordinary agent-status waits. Specs: `tests/swarm/test_swarm_inbox_yield.py`.

Background acceptance (`exitCode='background'`) is pending, neither failure nor success; a failed sibling still warrants correction, but failed execution never proves absence of side effects. Explicit `run_command(background=true)`, owner-requested per-command handoff, steer handoff, and automatic handoff after `AUTO_BACKGROUND_AFTER_S` (120 s) of actual subprocess time reuse the durable completion queue/inbox lane below in a task's own conversation: ending the foreground turn does not finish the command. The automatic threshold returns a pending handle without killing the process; `reaper_safe_wait_s` keeps it 300 s ahead of the stuck-task silence reaper. Commands already awaiting stdin and commands with no subprocess stay foreground. Every composition hands off when something can collect the result (`completion_delivery` in `lib/tasks_pkg/conversation_delivery.py`): a root task without its own conversation (headless request routes, storage-free runs) receives a finished command's result at its next round boundary from the command registry (`background_commands.take_run_completions`; once, and not after `poll` showed it), and its blocking `poll` also returns when another of its commands finishes; a child invocation collects it with `poll`; only a task with neither conversation delivery nor `poll` keeps every command foreground. A headless request's handed-off commands stop when its response ends; a storage-free run's keep running after it returns. An owner-requested handoff targets the currently running subprocess only, never the next command on the same task; it neither interrupts that process nor alters whole-turn Stop. If completion, interruption, Stop, or stdin wait wins the race, the request is refused or the command settles in the foreground instead of fabricating a background handle. The handed-off command remains owner-scoped and queryable/killable in the current server process. Because it began as a foreground subprocess, its pipes cannot acquire a restart-surviving record after spawn; only explicit local background commands write a durable record directory under `data/background_commands/` (output streams to files, exit code to a wrapper-written sentinel), so after a server restart the boot sweep delivers finished results, reattaches still-running processes with their poll/kill controls intact, and reports only processes that actually died with the server — the model never learns about the restart otherwise. The record keeps the names and opaque revisions of the vault credentials its command received, so a result rebuilt after a restart is redacted like a live one, or its output withheld when an entry changed since launch ([Tool execution policy](../contracts/TOOL_EXECUTION_POLICY.md)). The sentinel is written only after the command ran; when the shell rejects the wrapped script first (a syntax error), the live worker reports the runner's observed exit status and the shell's diagnostic instead of an unknown `-1` with no output (`tests/background/test_background_command_shell_errors.py`). Remote-worktree explicit background is rejected before execution; so are explicit background, timers and `current`-conversation agent schedules for a task without a saved conversation, whose response nothing it starts may outlive ([Headless API](../contracts/HEADLESS_API.md) records the decision). Complete publication envelopes and byte-budget receipt cursors follow [Storage operations](../STORAGE_OPERATIONS.md). The unified `poll` tool absorbs all background waits (background commands, swarm agents, cross-conversation tasks): `wait_s` blocks mid-turn up to `POLL_WAIT_CAP_S` (1500 s, reaper-clamped) and returns early on completion, pending turn input or Stop, a capped wait returns the running snapshot and is safely re-called because completed results stay re-readable, and an unknown handle is answered with the caller's live handles. `kill` stops a background command's process tree (SIGTERM then SIGKILL) or aborts one running swarm agent; killing one handle cannot cancel unrelated foreground work, and cross-conversation tasks are refused (use that conversation's Stop). The retired `check_background_command`/`kill_background_command`/`await_agents`/`await_task` names stay dispatchable for conversation-latched schemas, and name repair routes fresh mistakes to `poll`/`kill`. `run_command` has no model-facing timeout: commands run to completion unless killed or stopped by the user. Decision (owner ruling): one async-handle contract instead of per-family wait tools plus no time-budget abandonment — defeated alternatives are keeping three single-family wait schemas (one mental operation, three surfaces) and timeout-based kills (models cannot predict durations; stopping work is an explicit act, not a guess). Decision (owner decision 2026-11-03, superseding the 1500 s handoff of 2026-10-28): elapsed-time handoff at 120 seconds in every composition that can collect the result, instead of 1500 seconds, no handoff without a conversation, a command-name heuristic or a forced timeout; a foreground command held its agent for up to 25 minutes, or until the task budget ran out where no conversation existed, and returned after the five-minute prompt-cache expiry, command names cannot predict runtime, and a timeout would destroy ongoing work ([cost decision](../LLM_COST_OPTIMIZATION.md#long-waits-and-the-conversation-tail-ttl)).

**Owner Stop for one swarm agent.** The background-agent dock sends the same per-agent signal as `kill` through `POST /api/v4/swarm/runs/<swarm_id>/agents/<agent_id>/stop` (`stop_swarm_agent`), addressed by the exact run ID and refused for pending or settled agents; the agent settles `cancelled` while its run continues ([API contract](../contracts/API_CONTRACT.md#swarm-agent-stop), `tests/swarm/test_swarm_agent_stop.py`).

### Background command delivery owner

**Problem:** a child invocation (swarm worker, orchestration step, approval delegate) carries its parent's `convId` as execution identity but owns no turn in that conversation. Background commands keyed their durable receipt, inbox twin, restart record and collective wake by that `convId`, so a worker's completion entered the coordinator's transcript and woke it for a command it never started, a still-running worker command held the coordinator's own batch wake, and the worker was told its completion would be shown in the conversation while receiving nothing. **Decision:** `lib/tasks_pkg/conversation_delivery.py` decides delivery for every deferred lane: `conversation_delivery_available` is false for a child invocation, and `completion_conversation_id` fixes a background command's delivery conversation once at launch. The registry entry and the durable record (`conv_id`) carry that owner, so publication, retry, restart recovery and the batch fence never reach the parent; activity still lists the command under the conversation it ran in (`origin_conv_id`, display only). The child's receipt states that no conversation delivery is available and directs it to `poll`, or to return the handle to its parent when it has no `poll`; child tool assembly projects `run_command`/`poll` prose so neither promises automatic delivery (`lib/tools/background_guidance.py`). A completion that arrives after the child settled is retained in the owner-scoped registry, readable with `poll` by any task of the same owner that holds the command ID until completed-history eviction or process exit, and logged once with a typed reason (`launcher_running` or `launcher_settled`); its durable record settles `not_applicable`, so a restart never republishes it. A child with `poll` hands a foreground command off only after `AUTO_BACKGROUND_AFTER_S` and collects it with `poll`, because it drains no inbox: neither a steer of the borrowed conversation nor a coordinator's `send_agent_message`, which lands in the run mailbox and is injected at the worker's next round boundary, moves a worker's command; Stop remains the interrupt. **Alternatives rejected:** publishing into the parent conversation (wrong transcript and a spurious coordinator turn); a new push lane into the running child (an ended child cannot be resumed, so a result after settlement would still need `poll`, and it would add an injection authority beside the run mailbox); refusing `background=true` for children as for headless requests (removes concurrency the child can already collect with `poll`). Records written before this decision still name the parent conversation and publish there after a restart. Specs: `tests/background/test_child_background_completion_owner.py`.

**Leaf-worker command controls — Problem:** local Swarm leaf workers could start `run_command(background=true)` but neither collect nor stop it: role hints omitted `poll`/`kill`, the sub-agent denylist stripped `kill` (so `general` held an unscoped `poll` only), and `READ_ONLY_AGENT_EXTRA_BAN` banned both because a worker waiting on another orchestration lane can deadlock the root. A worker had to stop its own runaway test without `kill`, while guidance told workers to poll handles they could not. **Decision (owner, 2026-10-31):** every leaf-worker role that holds `run_command` also holds `poll` and `kill` (`lib/swarm/registry.py`; a per-spawn allowlist naming `run_command` keeps them), and their handler (`lib/tasks_pkg/handlers/poll.py`) confines a leaf worker — a child invocation whose executable catalog carries no `spawn_agents` (`lib.swarm.routing.is_leaf_worker`) — to the `bg_*` commands its own task launched. Its no-id `poll` lists only those; an agent, task, other-task or other-owner handle is refused with typed `background_handle_not_owned` before anything is read, waited on or signalled, so a cross-lane wait cannot start. Child tool assembly projects the worker's `poll`/`kill` prose to that scope (`project_leaf_worker_tools`), and a receipt without conversation delivery says to collect the result before finishing. Roots, and delegated runs that coordinate their own agents (a chat Goal worker holding `spawn_agents`), keep every owner-scoped handle. Read-only and provider-native workers keep the ban: they hold no `run_command`, and a native subagent executes inside the root task, where the own-command scope cannot tell it from the root. **Alternatives rejected:** dropping poll advice from worker receipts (a runaway command stays unstoppable); an unscoped worker `poll` (reopens the cross-lane deadlock); scoping by retained agent identity instead of the launching task (needs a new durable owner field, while the coordinator can already read or stop any command of its owner by ID). Specs: `TestLeafWorkerScope` in `tests/tasks_pkg/test_poll_kill.py`, `tests/swarm/test_swarm_tool_scoping.py`, `tests/swarm/test_swarm_role_catalogue_tools.py`, `tests/tasks_pkg/test_background_guidance_authority.py`.

**Timer continuations and `current` schedules — Problem:** the same borrowed `convId` still decided the other deferred lanes. The scheduler handler stamped `_source_conv_id` from `task['convId']`, and `deferred_completion_refusal` refused only headless requests, so a worker's `timer_create` continuation, or its agent `schedule_create` aimed at `current` or the parent's ID, started turns in the coordinator's conversation that the coordinator never asked for, after the worker had ended. A root task without a conversation (Evolution stages, embedded runs) was offered `timer_create` only to fail with an untyped error, and its `current` schedule kept the literal target `current`, creating a job for a conversation that does not exist. **Decision:** `completion_conversation_id` is the single owner for these lanes too. The handler stamps `_source_conv_id = completion_conversation_id(task)`, and `deferred_completion_refusal` refuses a timer and an agent schedule aimed at `current` or the task's own `convId` before the scheduler runs whenever that ID is empty: typed `no_conversation_turn` for a child or conversation-less task (headless requests keep `no_saved_conversation`), with a `nextAction` to check readiness within the run or, for a child, to report the condition or job in its result so the parent creates it. Tool surfaces say the same: child tool inputs and conversation-less root assembly (`ToolContext.delivers_deferred_completions`) withhold `timer_create`, describe the schedule target without `current` (`schedule_tools_without_current_conversation`) and project pull-only `run_command`/`poll` prose. An explicit background command stays allowed and pull-only, and a schedule into another existing conversation proceeds; a child's such job records no source conversation, so deleting the coordinator's conversation no longer disables it (deleting its target still does). Background control advice (`background_command_guidance`) takes the caller's `conversation_delivery_available` fact instead of hedging with "when available". **Alternatives rejected:** an explicit owner target that keeps the parent conversation as the continuation target (the worker owns no turn there and has ended when the timer fires, so the coordinator would be woken with a message it never wrote, and correlating such timers back to the worker needs a new owner lifecycle); keeping the parent as recorded provenance while refusing `current` (two conversation facts for one call, where the delivery owner must be the only one the executor can use); offering `timer_create` and refusing every call (a tool whose only outcome is refusal misleads the model, the precedent for headless requests). Device-online wakes (`await_device`, [remote execution](remote_execution.md#waiting-for-an-offline-device)) are the same kind of lane: the same refusal and the same tool assembly gate apply. Specs: `tests/tasks_pkg/test_deferred_lane_owner.py`.

Inbox delivery retains every accepted task notification until drain/clear, without the former 256-item oldest eviction. Completion paging makes progress through an item larger than its byte hint: one complete item returns with an exact cursor, rather than a capacity error. Byte hints are positive selection windows, not admission limits, and native queue replies no longer reject complete results above 8 MiB.

Background completion delivery has no 32-item pending/round/recovery ceiling: an unfrozen round drains every available twin and recovery follows all response pages to EOF. The 32-row value is only the initial page hint; complete windows grow geometrically, while short byte-limited pages retain their exact continuation. Callers may explicitly request a subset, and storage accepts any representable positive page size. A frozen delivery event settles its original retry-stable receipt before consuming newer occurrences. Problem: pending-count subtraction stalled available twins and default recovery stopped after 32 rows. Decision: complete demand traversal with response-sized windows and preserved publication identity. Alternatives rejected: larger fixed batch ceilings still strand later work; merging into a frozen receipt changes consumed evidence; one giant response ignores existing byte framing. Regression evidence: 513 durable receipts restore through 32/64/128/256/512 requested windows, explicit 35-item recovery stays bounded to that request, SQL pages of 500 and native pages of 100 pass the old ceiling, and every pending item remains discoverable. Consumption identity proofs are sets grouped by receiver slot and retain every consumed queue ID across clear/revival for the process lifetime. Ended-slot tombstones have no count eviction and remain until explicit revival; unrelated traffic cannot reopen a closed receiver. Process exit retires this volatile metadata; payloads and durable receipt history stay in their existing owners. Problem: 16,384-identity FIFO eviction re-admitted old twins, and 1,024-tombstone arbitrary eviction removed closure protection. Decision: preserve proof for as long as an old producer may publish, transferring fresh ID sets directly and resetting one test slot without scanning other slots. Alternatives rejected: higher caps reproduce the same identity loss; timeout expiry has no producer-quiescence witness; clearing proofs during revival allows old callbacks into a new turn. Measurement: one dense receiver retains 32,769 identities in 3.156 ms with 2,097,368 current/2,621,704 peak traced bytes excluding input construction; equal-cardinality tuple/OrderedDict representation used 4,662,992 current bytes. Memory follows unique identities and closed slots rather than payload volume. Tests preserve the oldest identity after other-slot traffic, clear/revival and a pre-commit late publish, and retain all 2,049 closed slots. Completion flush freezes the complete pending occurrence list into one retry-stable receipt; projection, facade, SQL and native ACK accept that list without a count quota. Closed-task tombstones, exact command/queue identities, protected intent, replay and atomic carrier/receipt/removal remain enforced. Problem: a volatile bucket discarded older work while a later ACK rejected a valid large drain. Decision: demand retention and complete acknowledgement; SQL uses 512-ID parameter windows inside one conversation-locked transaction, with global position/ID result order. Alternatives rejected: larger inbox caps still discard work; truncating ACK silently leaves durable twins for redelivery; splitting commits weakens receipt/removal atomicity. Measurement: 4,097 ordered synthetic notifications enqueue/drain in 393.442 ms with 5,763,413 traced peak bytes (including input construction and verification) and no residual items; storage tests cover 1,025 removals selected through 70,000 absent IDs, rollback on the second delete window, and one committed receipt removing 513 deliveries.

Background command admission has no application count ceiling, including foreground handoff and restart reattachment. Problem: the shared 32-entry registry rejected new execution when live commands or undelivered results filled it, after creating a durable record. Decision: retain all active/unpublished controls and prune only delivered/headless completed history using the launch-probed tool receipt cache budget, at settlement. Actual worker-start failure removes its control and durable record. Alternatives rejected: raising the fixed ceiling repeats saturation; evicting active or unpublished entries loses cancellation or delivery. Measurement: with a two-result history budget, 40 simultaneous workers stay controllable, drain to zero live workers and retain two completed controls; 40 failed publications remain retryable and do not block a new command or handoff. Specs: `tests/background/test_background_commands.py`. The in-memory task dictionary is a process-local execution carrier. Important field groups are:

- identity: `id`, `convId`, `_turnId`, `_attemptId`, `_userId`;

- lifecycle: `status`, `finishReason`, `error`, `aborted`;
- accounting: `usage`, `apiRounds`, cost/fallback metadata;

## Persistence discipline
Managed root `append_event` admits a detached snapshot without waiting for storage; its ordered writer persists before push/hot replay and may carry the exact task event plus a revision patch in the same Sidecar transaction; the event envelope never repeats the cumulative projection. An oversized carried frame — the Sidecar payload cap or the 64 MiB wire frame — retries once with cumulative text and opens a 30-second full-projection probe circuit, keeping raw-event durability exact. Writes without that carrier fail closed; a later full probe or terminal settlement converges the Turn document. Terminal events may also settle slim, and a toolRounds lane crossing its frame budget (`TOFU_TOOL_ROUNDS_FRAME_BUDGET_BYTES`, default 16 MiB) elides the oldest settled rounds' free-text payloads with replay identity intact. Projection normalization copies an explicit L1/frame placeholder into only its uniquely identity-compatible segment mirror, so a stale render copy cannot restore old bytes; ambiguity leaves evidence untouched. A `spawn_agents` round without a durable snapshot first donates its handle to a minimal roster snapshot (status `unknown`, version 0), so the reloaded swarm panel still expands to an honest roster instead of a dead header. If even the text-only frame is rejected the worker is cooperatively aborted (`storage_frame_overflow`) instead of burning tokens on unpersistable events. Pure text progress may be coalesced. Structural events, interaction requests, and terminal events persist immediately. The next structural/terminal write carries cumulative text, so coalescing changes cadence, not final state.

## Failure rules

**Output-token limits.** Problem: a `length`/`max_tokens` response was resent
unchanged, discarding paid reasoning; a response cut inside tool arguments
could also reach repair and dispatch. Decision: the shared post-stream decision
replays the cut assistant text/reasoning and its protocol sidecars, then asks
the model to resume without changing sampling or thinking settings. For GLM,
the existing request compiler sends `clear_thinking=false` when that history is
present. Every tool item in a cut response is unverified: projected calls
and protocol sidecar items are both removed, even if their visible arguments
happen to parse. None executes or is replayed before the continuation.
Responses retains reasoning, text and its non-wire state-origin marker. The
old order witness also covers the removed calls, so it is retired and the
checked converter uses ordinary sidecar ordering instead of inventing an
interleaving. The native Rust root path owns the same rules. After an admitted
tool batch the output-limit recovery budget resets alongside the existing
terminal budget. The existing two-attempt terminal budget bounds consecutive
unproductive stops and resets after an admitted tool batch. Exhaustion preserves
cut text or reports `abnormal_stop` without whole-turn replay. Alternatives
rejected: lowering reasoning (ineffective on the measured GLM route), increasing
provider limits, and evaluation-only continuation. Verify
`tests/tasks_pkg/test_output_limit_recovery.py`, abnormal-terminal and

Rust `output_limit_*` agent tests.

**Unavailable handler verdict.** Problem: the resolver's missing-handler branch
returned error prose while ordinary settlement promoted the round to success.
Decision: that branch emits the existing typed `tool_unavailable` category,
stamps an error before presentation, and releases its runtime context even when
an observer fails. No effect intent or handler execution is created. Direct
executor and pipeline consumers retain one failed audit; recovery directs the

rejected: inferring failure from arbitrary prose can misclassify tool data;

Internal event-delivery failures are typed local failures, not provider failures. Primary, reactive, configured-fallback and pool-rescue calls propagate them without another model/key attempt; the fatal handler bypasses turn auto-retry. The error envelope classifies `EventDeliveryError` as `server_busy` (revocation or owner cancellation as `aborted`), reports `task-event-delivery` as its source, and retains the explicit first cause in technical detail without classifying provider-looking words in that cause. A later terminal publication or result persistence failure is logged but cannot replace the original fatal envelope. **Decision:** retain the original cause and use the existing settlement/recovery owner. **Alternative rejected:** retrying a provider or masking the first failure with a terminal-lane error cannot repair local durability. `status: rejected` means the tool did not execute; the public `rejection` descriptor carries its stable kind, tool, reason, and known retryability. `_rejected` and result-level `rejected` are compatibility aliases. The descriptor survives the round, tool events, cold Turn projection, and activity timeline. If it is the last terminal tool act, finalization emits a typed task error: `hallucinated` maps to `tool_not_available`; all other refusal kinds map to `tool_call_rejected` with original detail. Abort/interruption wins. Activity keeps status `skipped`, summary `blocked`/`unavailable`, and kind as `reasonCode`. In the transcript the tool row owns the rejection inline (badge + the full, unclipped reason, kind code appended when absent), so the conversation view model drops the timeline's `blocked`/`unavailable` row whenever the matching round carries the descriptor; a trimmed or absent round keeps the timeline row as the last visible record. Genuine failures follow the same rule: an error round owns its full tool content inline (no first-line/300-character clipping, line breaks rendered, no line clamp), so the view model drops the timeline's `failed` row — a log-policy-bounded excerpt — whenever the matching round renders the error lane; `execute_tools` gateway rows are exempt because they replay as child-validation rows, and a trimmed or absent round keeps the timeline row as the last visible record.

Targeted carrier hand-off — Problem: a wake-up through the scheduler lock costs a lock round trip, and under GIL pressure every contended acquisition is a GIL hand-off. Broadcasting to all parked carriers once made each event an O(resident) convoy (LoopWatch stalls of 5–7 s with 291 resident Push frame carriers). Waking one carrier per job still cost five scheduler-lock acquisitions per job: the submission, the woken carrier re-acquiring the lock, its claim, a completion hold before the Future resolved, and a post-callback hold. A stall dump showed 20 threads queued on the Push frame pool's lock (9 completing carriers, 6 woken carriers re-acquiring it, 5 submitters including task-event delivery and turn translation), and admitted jobs whose woken carriers had not yet re-acquired the lock made submitters start a new carrier per job. Decision: the hold that admits a job commits it to the most recently parked carrier and hands it to that carrier's private inbox (`_Carrier`, a `queue.SimpleQueue`), so the woken carrier runs it without the scheduler lock. While a carrier is parked, admitted jobs wait in `_pending` only for robbed carriers that are already awake to claim them (take-back notices, below). A carrier already holding the lock for its own claim first takes back the oldest hand-off whose carrier has not woken yet; the inbox pops atomically, so exactly one of them runs it, and the robbed carrier claims next. A finished job is appended lock-free to `_finished` before its Future resolves, and every hold settles those records before it reads job bookkeeping. A waiter that snapshots or retires the pool never sees a resolved job as still active, and results never wait for the scheduler lock. The carrier's next hold ends its callback occupancy and claims, parks or retires, so a steady-state job costs one submitter hold and one carrier hold. A handed-off job counts as its carrier's active job from that hold, but its Future enters RUNNING only when a carrier takes it from the inbox (its own carrier, lock-free, or a carrier taking it back under the lock). Until then `Future.cancel()`, `cancel_task` and `shutdown(cancel_futures=True)` withdraw it exactly like a job still in `_pending`: the cancellation's notification releases its accounting, the carrier that takes the cancelled job completes the cancellation handshake and never runs it, and whichever of the two holds the lock first settles it, once. Entering the Future in the admitting hold (this hand-off's first version) made every handed job uncancellable before it ran: production `owned_results` stops then started slide, scene and podcast work after an abort or failure (four recipe specs failed deterministically), and lane `cancel_task` callers could no longer withdraw unstarted translation and VLM jobs. Re-checking each caller's stop predicate at job entry instead would fix one caller and leave the `Future` contract broken for every other. Carriers take hand-offs and admitted jobs, skipping provisional jobs whose owners are still starting carriers, before considering retirement. Surplus retires only at completion boundaries (a carrier that finds no job retires itself, then any parked surplus) and on cancellation, resize, abandonment or terminal transitions, with one hand-off per parked carrier; admission and take-backs never retire, and a robbed carrier retires only as a carrier that found no job. Only shutdown and initializer failure release all parked carriers, and only once no provisional job can still be admitted. A job that committed carriers beyond admitted demand can absorb is published in one hold; any other submitter starts carriers it reserved itself, with its one-shot recovery, so no submitter waits behind another `Thread.start()` ([startup ownership](../DEFENSIVE_PATTERNS.md#worker-startup-transactions)). Alternatives considered: waking parked carriers through a shared `_work_ready` condition (one re-acquisition per job, plus the admitted-but-unclaimed backlog); irrevocable hand-offs (a running carrier retired while jobs waited for GIL-delayed carriers: about five such jobs per retirement, and twice the carrier starts); also retiring surplus at reclaim or admission (it retires the carrier the next resubmission needs, which costs about 40 % more carrier starts); a completion hold before the Future resolves (one more contended hold per job, and results wait behind submitters); a plain lock as the wake primitive (it cannot absorb a second hand-off to a carrier that has not consumed the first). The earlier objection to per-carrier slots, a second scheduler duplicating cancellation and shutdown, does not apply: only the scheduler hold hands off, and a withdrawn hand-off settles through the existing cancellation notification. Shrinking idle residency or moving loop-side reads behind another executor moves the same contention. Measurement (synthetic, Python 3.12, this host; medians of three alternating 3 s runs per cell, idle hint 8 unless stated): scheduler-lock acquisitions per parked round trip 5.0 → 2.0. A Push-shaped load (four fire-and-forget producers and a loop-like probe) runs 15.3k → 15.8k with equal probe latency. Carrier starts per 1k jobs go 105 → 115 and 131 → 137. Eight pure-Python CPU-bound threads saturate the GIL; results are noisy and mixed. Round trips improve 3.5 → 5.5 jobs/s and 32 closed-loop submitters 137 → 165. However, 32 submitters with an idle hint of 32 drop 278 → 167, 200-job bursts 45 → 33, and the Push shape 311 → 219 (probe submit p99 185 → 157 ms). Take-back notices below trace and close most of that. `tests/agent_core/test_worker_targeted_wakeup.py` is the executable specification.

Take-back notices — Problem: with eight pure-Python CPU-bound threads saturating the GIL, the targeted hand-off lost 32 closed-loop submitters with an idle hint of 32 (278 → 167 jobs/s), 200-job bursts (45 → 33 kernel, 54 → 38 application pool) and the Push shape (311 → 219). A take-back re-parked the robbed carrier although its wake-up was already spent, so on its GIL turn it found an empty inbox and blocked again inside `SimpleQueue.get` without looking at other waiting work, while the next admission bound its job to the carrier that had just drained and blocked. The old shared condition let any woken carrier take any queued job. Decision: a take-back leaves a notice (`_TAKEN_BACK`) in the robbed carrier's inbox instead of re-parking it. The robbed carrier, woken for that hand-off anyway, claims in its next hold like a carrier that finished a job: the oldest waiting hand-off, else the oldest admitted job, else it parks or retires as surplus. Until that hold it counts in `_woken_claimers`, and admission wakes a parked carrier only while admitted jobs in `_pending` outnumber those claimers; the rest wait for carriers whose wake-up is already in flight. Each hand-off still ends in exactly one return from `park()` (its job, a notice or a retirement), so a take-back never costs a wake-up; a woken carrier still runs its own job without the lock, and a robbed carrier takes one hold where it used to block again. A parked round trip keeps one submitter and one carrier hold. No job waits behind a running job while a carrier idles: a counted claimer is awake and runs nothing, and when it takes an older hand-off instead, the carrier robbed of that one inherits the count; a carrier that leaves its loop while counted withdraws the count and dispatches again.
