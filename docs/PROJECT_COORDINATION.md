# Project Coordinator and team workspace

Responsibility: explicit coordinator binding, passive same-project messages,
consideration receipts, optional model-input boundaries and explicit-human
consultation or bounded-file dispatch, linked rework and checkpoint-pinned publication. This describes the source contract in this
checkout, not deployment status: an isolated tested candidate does not prove
canonical integration or live backend loading.

The router layer builds on this owner without a second binding, policy or
worker loop: the owner's Global Router is the bound Coordinator of a
Tofu-created router home, forwarded human requests (`route_to_project`,
`origin.forwardedFrom`), report relay, standing instructions and the separate
`workerModel` setting are described in [ROUTER.md](ROUTER.md).

Problem: importing the file-scope admission boundary for an ordinary project
tool eagerly initialized `jsonschema`, even when no dispatch grant existed.
Decision: `repository._validator` imports the schema engine on its first actual
validation, retaining the existing bounded validator cache and exact schema.
The ordinary admission path still checks for bound authority; actual profile
validation fails closed if its validator cannot load. Alternatives rejected:
prewarming taxes startup/idle, and bypassing file-scope admission would remove
live ownership and revocation checks. The fresh-process specification is
`test_project_dispatch_lazy_validation.py`; repository and file-scope tests
retain malformed-input, concurrent admission and revocation coverage.

The frozen repository-tool comparison
retains 1,060 exact-output workers using the prior source/Git path and this
change plus explicit Rust discovery, with identical native CSR ranking.
First-operation P50 ratios are 0.245–0.411 and CPU ratios 0.411–0.558 across
all five repository cases. This cumulative comparison does not isolate native
discovery. Two Python warm CPU pairs still fail, at 1.143 and 1.159; later
phase/processor diagnostics do not waive them. Native discovery remains
explicit, and inherited child RSS, other domains and full application/default
admission remain unresolved. The existing file-lifecycle fixture's missing
durable effect acknowledgement reproduces on the frozen reference as well.

## Interactive Coordinator and workers

Problem: executing work in the Coordinator or its temporary children hides the
independent worker conversations that users need to follow. Decision: the binding
selects an ordinary root Agent with a registered `project_coordinator` context
block and dispatch-only tool policy (`lib/tasks_pkg/coordinator_policy.py`).
It plans, delegates the current human request into independent workers, reviews
their results, exchanges project messages and reports to the human. File, shell,
browser, arbitrary program and Swarm/retained-agent execution are denied before
tool effects, including discovered tools and batch calls. Catalog filtering alone
is not authorization. Restrictions remain pinned through the selected turn;
provider-native multi-agent and programmatic execution stay disabled even when
old turn/checkpoint latches requested them.

Problem: Workers inherited the Coordinator role's narrowing (no
`execute_program`, `programmaticCalling=off`, no Swarm/retained agents), so a
delegated conversation had fewer capabilities than the same human's ordinary
conversation. Decision (owner, 2026-11-04): a `project` Worker gets exactly the
capability boundary of an ordinary conversation of that human, inside its
isolated workspace. Request ingress keeps the human's submitted tool settings
beside the role's (`_coordinatorSubmittedToolSettings`);
`delegation.capture_worker_policy` grants those settings and the gateway's
`execute_program`. Admission fences a Worker's `tools` to exactly that policy.
`workerDeniedTools` keeps only the Coordinator/Router/Watchdog role tools and
deferred wakes (timers, schedules, `await_device`, `create_conversation`,
`integration_submit`), which would start work outside the grant and its Stop
fence. Alternative rejected: a separate Worker toggle, which would reintroduce a
second capability ceiling diverging from ordinary conversations.

A Worker's sub-agents (`spawn_agents` children and their swarm parent proxies)
carry no grant of their own. `admission.share_dispatch_root` gives each a
process-local reference to the live Worker task; every admission and workspace
resolution revalidates that root, so the children use the Worker's isolated
workspace and stop with its Stop, revocation or settlement. Alternative
rejected: copying the grant carrier into each child, which would let a child
outlive or diverge from the Worker's authority. A child's artifact port
(`RunArtifactTools`) is first-party, not a custom tool environment, and a
Worker grant holding `spawn_agents` admits the artifact tools its runs give
children ([Project-dispatch execution admission](contracts/TOOL_EXECUTION_POLICY.md#project-dispatch-execution-admission)).

Problem: the per-call role refusal (`Coordinator policy unavailable`, fail
closed) converted every lookup exception, so a project-dispatch task whose
`_projectDispatchAdmission` carrier was removed received a refusal and kept
running instead of failing its authority check. Decision: a dispatch task (a
Worker or an automatic Coordinator continuation) takes any role from its grant.
`bind_account` pins that role from the grant it validated: request and grant
fields no mutation can change. `coordinator_scope` answers a bound task from it
without reading storage; a removed or replaced carrier raises the dispatch
`AbortedError` and aborts the task, and an unbound dispatch task validates its
grant first. A revoked grant or changed task identity is the verdict of the live
admissions that precede every effect: the model request's dispatch intent and
tool admission, which every executor runs before the role policy (see [One live
validation per tool-batch admission](#one-live-validation-per-tool-batch-admission)).
A request built for a dead grant is never sent. Only a failed ordinary
Coordinator binding lookup refuses the single call while the human turn
continues. Alternatives rejected: refusing per call (a fenced task would outlive
its authority) and revalidating the grant in every role check (it re-read a
fixed role on every round and call).
Specification: `test_project_dispatch_runtime.py` (removed carrier, revoked
grant) and `test_coordinator_policy.py` (unknown binding fails closed).

`lib/conversations/coordinator_tools.py` adapts `create_conversation`,
`dispatch_project_assignment` and `get_project_assignment` to the existing
conversation repository and ProjectDispatchService. Creation retries use immutable
request/binding identity, tolerate normal retitles/settings edits and verify the
owner-scoped readback. Creating a chat never starts execution or grants permission.
`dispatch_project_assignment` consumes an existing grant. `delegate_project_work`
derives a grant from the current accepted human request as described below; model
text and worker reports never become human authorization. Workers use the ordinary command → turn/attempt → task path.
The Coordinator has no separate model loop, scheduler, task states or budget.
Binding starts no work; existing turn/continuation policies retain ownership.
Unbound, foreign, child and storage-free invocations receive no role. The narrative
cursor remains independent. Alternatives rejected: prompt-only restrictions can
be bypassed; temporary children remain in the parent conversation; another runtime
would duplicate admission, Stop, settlement and publication authority.

### Coordinator-started sidebar conversations (owner decision 2026-11-03)

Problem: delegated Workers, watchers and unstarted shells crowded the owner’s ordinary conversation rows and date-group counts. Decision: each Coordinator owns one collapsed-by-default sidebar group directly beneath its own entry, outside the owner’s date groups. It contains every conversation created by `create_conversation`, `delegate_project_work` or `dispatch_project_assignment`, including empty shells, historical workers and terminal/cancelled work. A short localized header carries the total, the aggregate running count and the date groups' down chevron, turned to point right while collapsed. A reply awaiting review is marked only on its own row, visible once the group is expanded (owner decision 2026-11-04: a header dot repeated the rows' marks and made every collapsed group read as awaiting acceptance). Expanded compact rows show title, status and relative time, newest first. The body scrolls independently without a row cap, and expansion is remembered per Coordinator in browser storage. Keyboard activation, `aria-expanded`, visible focus and reduced motion are required.

A known Coordinator mounts its group even when the initial catalog contains no local Worker; the paged inventory supplies cold history on demand. Only a member joining or leaving the local catalog invalidates that inventory: the inventory can only add members the catalog lacks, while revisions, counts and timestamps of known members already arrive through the catalog. An added member becomes an ordinary catalog shell, so it keeps the stored folder its roster row carries (below). Invalidating on every member revision was rejected because it re-scanned the owner catalog several times per second while Workers ran; members a read adopts re-baseline membership so they never trigger a second read. The existing presence refresh also refreshes it when the Coordinator is selected. Every list refresh reaches the group, so an expanded body is rebuilt only when its rendered rows, active row, status or relative time change; otherwise hover and focus would reset on each stream tick. Adopting each page refreshes the catalog projection before the group paints, so the expanded body contains its Workers rather than an empty shell. Opening a grouped Worker also refreshes the shared active-row projection: the ordinary flat-list fast path cannot find a row owned by the group. The current selection therefore survives subsequent catalog and stream updates without changing grouping policy. A group first placed beneath an interim history row moves beneath the Coordinator's card once the catalog names that Coordinator, so one Coordinator never shows two groups.

Server-issued `_coordinatorSource` at creation is the only direct origin evidence. The project-inventory projection additively backfills older conversations from the same paged durable assignment records used by Manage work; it never infers origin from titles or ID prefixes and does not rewrite stored settings. The global catalog projects only stored metadata: reconstructing every project's complete assignment history there made each sidebar refresh contend with active dispatch writes and could fail the whole list. A shown Coordinator group reads that project's paged roster even when no child carries provenance locally, adopts the returned rows, and retries a failed discovery on the next catalog/push refresh. Ordinary catalog reads therefore never depend on dispatch-history availability. Ordinary owner chats, swarms and sub-agents are unchanged. Search still opens workers and marks their Coordinator provenance. Grouping never deletes, archives or changes direct links, and Manage work retains the complete project inventory. A replaced Coordinator keeps a separate historical group beneath its own clickable row; its workers never rejoin the owner’s date groups. When that Coordinator is not present in the current catalog, the sidebar does not fabricate an empty historical row; the Worker remains available through search, direct navigation and Manage work.

Each sidebar view decides which entry anchors a group. Pinned entries anchor their own groups: the shown project’s bound Coordinator, and the main coordinator’s card (the Global Router) in a view with no folder and no project. The Global Router and the Watchdog stay reserved in every view, so neither is ever listed as a row or classified as a replaced Coordinator; the Watchdog never delegates and has no group. Any other conversation of the view, under the list’s own folder filter, that started conversations is a replaced Coordinator: it gets one clickable row directly above the list, and the list omits it. While the shown project’s binding is loading nothing is classified as replaced, because its current Coordinator cannot be told apart yet; a pre-painted cached binding still anchors its group at once. Every group owns the nodes it inserted (row, host, body), is rebuilt when its anchor changes and is removed when it leaves the view, so a late binding or a folder switch never leaves a second Coordinator row behind. A view whose conversations all sit in Coordinator groups is not empty, so the list shows no folder-empty notice beneath them.

Alternatives rejected: global rather than per-Coordinator folds lose ownership; title/prefix heuristics misclassify owner chats; hiding or archiving Workers destroys evidence; rendering one long expanded group buries the owner’s own conversations; classifying replaced Coordinators before the binding settles, or across folders, painted the current Coordinator and other projects’ Coordinators as extra rows. Specifications: `tests/project_mod/test_coordinator_conversations.py`, `frontend/src/features/coordinator-conversation-group.test.ts` and the real Coordinator Chromium journeys in `tests/frontend/test_project_coordinator_browser.py`.

Problem: a row's status derives from client-side Turn state, which the page holds only for hydrated conversations, so every running Worker that had not been opened read “Done” until clicked. Decision: the inventory page stamps `busy: true` from the same owner-scoped live-task projection as sidebar catalog rows (`list_running_tasks`), and every catalog merge path (full list, folder, older page, inventory page) wakes exactly the busy shells the client does not already know are running, deduplicated per conversation. A shell with no hydrated Turns shows no status rather than “Done”. Alternatives rejected: hydrating every grouped Worker on paint loads transcripts the owner never opens; a group-only status read would add a second liveness authority beside the catalog projection. Specifications: `tests/project_mod/test_coordinator_conversations.py`, `tests/api/test_api_v1_project_coordination.py` and `tests/frontend/test_frontend_folder_members_load.py`.

Problem: a sidebar folder that names no directory has no project path, so its leader slot fell back to the main coordinator’s card and offered no way to create a project Coordinator; the folder read as a project whose Coordinator had disappeared. Decision: a selected folder always owns the leader slot. When it names no directory, its project Coordinator row says so and opens that folder’s Project settings; once a directory is added the row reads that exact path’s binding and offers Create. The main coordinator’s card stands in only where no folder is selected and for router-managed homes. Folder names never take part in project identity, which stays the exact path with trailing separators stripped: POSIX compares names as bytes, so NFC and NFD spellings are distinct directories and never share a binding. Alternatives rejected: deriving a directory from the folder name invents filesystem locations; binding by folder would add a second identity beside the path that diverges when folders share a root; Unicode-normalizing paths would merge distinct directories. Specifications: the directoryless-folder and non-ASCII grouping cases in `frontend/src/features/project-coordination-entry.test.ts`, and the non-ASCII, proxy-re-encoded identity case in `tests/api/test_api_v1_project_coordination.py`.

Problem: every provenance backfill re-read the project's complete assignment history, so each project-roster read grew with lifetime delegation (106 storage RPCs, about 70 ms per project at 94 admissions on native TofuDB) and a concurrent admission could make the snapshot page retry. Decision: `RecipientOrigins` in `lib/project_dispatch/history.py` reads each admission once per process. Requests are immutable after admission and their order index commits with them, so the mapping per owner/project and storage client stays exact; the project head’s assignment count is the freshness witness. An equal count costs one head query, a larger one reads only the newer admissions, and a smaller count or another client starts over. Retention is one mapping per owned project read, holding each delegated recipient once (about 10 KB at 94 Workers). Alternatives rejected: a time-based cache adds a staleness knob; copying origins into conversation settings migrates non-authoritative data; a durable provenance index would duplicate the assignment authority. Specifications: `tests/project_mod/test_coordinator_conversations.py`, `tests/storage/test_project_dispatch_repository_segments.py` and `benchmarks/catalog_origin_reads.py`.

### Delegation within the current request

Problem: the tool and stored assignment independently capped the delegated brief
at 4,096 characters, rejecting detailed objectives before a Worker could start.
Decision: both consume the same request schema, admitting up to 65,536 characters
and preserving the complete brief through validation, immutable storage, retry
identity and Worker input. Batch objectives/responsibilities use that same bound;
their combined assignment must fit it. Empty/oversized briefs still fail before
Worker creation. This changes context capacity, not the source of authorization.
Alternatives rejected: truncation loses constraints, requiring shorter briefs
pushes the harness limitation onto the caller, and changing only the tool schema
leaves downstream admission broken. The maximum UTF-8 brief payload is 262,144
bytes. The regression fixture's serialized assignment measured 14,712 bytes
with a 4,220-character multilingual brief and 208,880 bytes at 65,536 characters.
Existing document/commit byte bounds remain in force and no durable evidence
is evicted. `test_coordinator_brief.py` verifies tool-to-Worker fidelity,
Unicode boundaries and exact replay; the native Worker journey also carries a
brief longer than the former limit.

Problem: requiring the human to create and authorize every Worker defeats the
Coordinator entry point. Decision: `delegate_project_work` creates an ordinary
conversation in the Coordinator's folder and admits a `project` worker through
the existing dispatch repository and command service. The frozen capability
ceiling comes from ordinary tool assembly before the Coordinator-only filter.
Worker input includes the original request (explicitly marked excerpt above
12,000 characters, with source Turn/conversation links) and the delegated brief;
custom system-prompt settings are preserved. Context never enlarges the grant.
The live owner, tenant, binding epoch, physical assistant Turn/Attempt and its
canonical human parent must agree. Execution principals with no reusable API
scopes are supported without manufacturing a human principal. Arbitrary synthetic
inputs, Plan/read-only requests, stale attempts and durable Stop cannot delegate.
Only an internal continuation grant may reuse the exact original request policy.
Public grant APIs cannot supply this internal policy. Legacy consult/file grants
keep their narrower behavior. Worker calls use ordinary tool resolution and
registered isolated Git workspaces; recursive agents, timers, schedules and
arbitrary tool programs are excluded. Roots that cannot host such a workspace
are refused before any Worker exists (below).

`await_project_workers` waits in the existing tool invocation using disposable
terminal subscriptions and interruptible Stop. It returns as soon as any selected
Worker that was unsettled at call start settles (`wait=progress`, naming the
still-pending IDs to wait on next), at once with `wait=settled` when every
selected Worker has already settled, with `wait=pending_input` when input waits
for the Coordinator's next round (below), or with `wait=timeout` after
`timeout_seconds` (default and maximum 1,800 s, otherwise honored in full). Under
`wait_for=delivery` a Worker settles at canonical delivery, at a `blocked`,
`failed` or `preserved` delivery receipt (returned with its `delivery.reason`),
or when its execution ends without completing. Durable attempt/delivery evidence
alone declares settlement: a terminal notification only starts a prompt recheck
every 0.5 s for up to 10 s, because it can precede the attempt's durable status;
otherwise a 5 s recheck covers notification loss and queued admission. Polls
read only the grant, attempt status, Turn metadata and delivery receipt
(`view_for_coordinator(settlement_only=True)`); excerpts and settled causes are
read once, for the returned rows. It creates no polling model request, new pool
or idle daemon. At most the existing 128 assignment references are observed per
call; excerpts are capped at 4,000 characters with explicit truncation. A
timeout preserves running workers. The same ordinary Coordinator loop then
reviews evidence and arranges further work under the original request.
Problem: a valid 1,800 s wait could outlast the task's silent-progress window
and be force-failed as `worker_lost`. Decision: each completed durable status
poll refreshes the waiter's existing dispatch heartbeat. A responsive wait
remains live even when Worker results have not changed; a blocked or failed
read supplies no heartbeat. Transport-only ticks remain self-ticks, and the
normal wait deadline, Stop and per-call cancellation still apply. Alternatives
rejected: shortening the declared wait changes its contract; an unconditional
heartbeat exemption hides a blocked handler. Verify the full execution/delivery
wait and blocked-read cases in `tests/project_mod/test_coordinator_workers.py`.
`wait=pending_input` yields the call to the human. It fires while the
Coordinator conversation's inbox holds a steer (a human chat message, forwarded
request or channel batch) or another background completion, the lanes that end
`poll`'s blocking waits (`pending_input` there too), checked every wait slice;
or once an incoming project message submitted after the call started appears in
`get_project_messages`, read at each settlement recheck. It is checked before
the first wait, so input already waiting ends the call at once. Its instruction
names the still-pending Worker IDs to wait on next; Workers keep running and the
input arrives at the round boundary right after the tool result. When every
selected Worker settled meanwhile the call returns `wait=settled` with their
evidence instead, and the input still follows.
Problem: N11 — six Turns were force-failed as `worker_lost` while a Coordinator
waited (11-04 22:32, 23:40; 11-05 01:23; 11-06 11:40, 11:53, 12:34). The first
three were inside `await_project_workers` on a boot predating the per-poll
heartbeat above (live since 11-05 09:59); that heartbeat is the fix, so a
responsive wait is never reaped. The last three were inside
`delegate_project_work`, undeclared synchronous dispatch under host overload —
not a wait at all, and not made safe by any wait marker. Decision: keep the
heartbeat as the await's only liveness evidence; a `_delegationWaits` marker
whose freshness equals the stall threshold would be redundant while polls
complete and would double a genuinely blocked status read's reap, because the
reaper restarts silence from the last explained verdict.
Problem (2026-11-09): `delegate_project_work` prepared the 1.4M-file plain
folder of the autoharness project inside the call (`require_isolated_worker_root`
runs `prepare_managed_repository`: whole-tree `ls-files`, a per-path content walk
and `add -A`) for 6,931 s; the reaper force-failed the Coordinator at 1,836 s as
`worker_lost` and the delegation's late result was lost. Decision: preparation
reports every observed advance (a Git tree the kernel shows executing, a completed
command, a walked path) to its caller, and delegation refreshes the Coordinator's
existing dispatch heartbeat with it, exactly as a completed status poll does;
Worker binding does the same for the Worker before its first round. A step that
stops advancing supplies nothing, so a stuck delegation is still reaped one
threshold after its last advance, and the Coordinator's Stop ends the preparation.
Alternatives rejected: a `_delegationWaits` marker or an unconditional exemption
hides a blocked handler (as for the await); raising the stall threshold is a knob
that only moves the false reap; preparing after delegation would create Workers
and grants for roots no Worker can use. Verification:
`test_a_long_root_preparation_keeps_its_delegating_coordinator_live` and
`test_a_root_preparation_that_stops_advancing_leaves_its_coordinator_reapable`
(`test_coordinator_workers.py`),
`test_a_workers_root_preparation_is_its_liveness_before_its_first_round`
(`test_project_dispatch_file_lifecycle.py`). A device command
claimed by a connected device publishes `_deviceWaits` and is `device` under
the bridge's own presence rule (`_command_active_locked`), which has no
observation clock of its own; an unclaimed command or a disconnected device
explains nothing. Verification: `test_explained_wait.py`,
`test_stuck_task_reaper.py`, `test_coordinator_workers.py`.
`review_project_work` pins the exact completed result; its `actor=coordinator`
never means human acceptance. An optional exact registered checkpoint requests
publication through existing integration gates. An accept whose delivery cannot
publish that checkpoint (the receipt records another attempt, an attempt that did
not complete, or a state the receiver never acts on) is
refused before the review is recorded, naming the receipt's state and reason
("Delivery follows the attempt that completes" in
[Project integration](modules/project_integration.md#task-owned-canonical-delivery)).
`await_project_workers(wait_for=delivery)` observes the real delivery receipt.

Problem: in a production Coordinator conversation these waits were 68% of wall
time. Waiting for all selected Workers held finished results until timeout (13
multi-Worker calls, late wake p50 137 s); delivery waits ignored blocked
receipts, so 25 of 26 timed out (5,517 s) while the cause sat in
`delivery.reason`; the notification-to-durable-status gap left single waits to
the 5 s boundary (3.4-6.1 s after completion); every poll read the whole Worker
Turn (2.28 MB for 121 rounds) to keep 4,000 characters. Decision: any-settle
return measured against the call-start state, held receipts settle delivery
waits, a bounded prompt recheck after notification, and settlement-only polls.
Alternatives rejected: returning while any selected Worker is settled (a call
that repeats a finished Worker returns at once, in a paid model loop); keeping
the all-settle wait behind a schema flag (the measured cost); counting only
canonical delivery (strands the Coordinator on causes only it or the human can
resolve); treating the in-memory notification as settlement (not durable
evidence); caching projections between polls (stale evidence, unbounded
memory). Known limit: a call that selects only held deliveries returns at once,
so a receipt that clears by itself (`workspace_busy`) is rechecked later, not
awaited alone. Verification: `test_coordinator_workers.py` and the native
`test_coordinator_workers_authority.py`.

Problem: a wait held the Coordinator turn for up to 1,800 s while checking only
Stop and Worker settlement, so a human steer, a forwarded request or a Worker's
question waited for the timeout; a Worker asking the Coordinator that awaits it
stalled until then. Decision: yield on the inbox lanes `poll` already yields on,
plus project messages newer than the call start, reusing the existing wait
slice and settlement recheck, as one outcome named like `poll`'s. Alternatives
rejected: shorter timeouts (a tuning knob, still blind to input); yielding only
to human chat messages (a forwarded request, a channel batch, a background
completion or a Worker's question would still wait for the timeout); a separate
outcome per input kind (the Coordinator acts the same way on each: read the
input, then wait on the named Workers); yielding to every unconsidered project message (one
that stays `submitted`, from an ineligible sender or an unconfirmed carrier,
would end every later wait at once in a paid model loop); a mailbox notification
lane or listener (passive project messages deliberately have no wake). Known
limit: a message submitted after the round acquired input but before the call
started arrives when the wait ends. Verification: `test_coordinator_workers.py`.

Problem: a resumed or later human-request Coordinator could accept an earlier
Worker's checkpoint but stamp publication with the reviewer's physical task.
The live publication gate correctly required the Worker's original delegation,
so legitimate review failed after retaining an unusable publication receipt.
Decision: review still validates the current caller, binding, original human
source, grant and exact result/checkpoint, then pins publication to the original
Worker delegation. An authorized repeat of the same review also repairs that
receipt's subject, preserving its original timestamp and all immutable pins.
No grant is enlarged or recreated. Alternatives rejected: loosening the live
publication gate admits unverifiable authority; requiring another human grant
breaks continuity for already-authorized work; preserving the bad subject on
replay strands existing receipts. `test_coordinator_publication_handoff.py`
covers physical resume, later human steering, retained-receipt repair and Stop.

`delegate_project_work` accepts the existing version-pinned `dependencies` and
`rework_of` shapes. They use the same dependency/review/publication admission;
no parallel graph executor is introduced. Pending review or delivery defers the
same grant, and changed result/checkpoint pins refuse execution. The graph reads
these durable links. `test_coordinator_dependency_links.py` exercises automatic
delegation, deferred replay, stale pins and exact rework links.
Unknown model/tool effects, source withdrawal and checkpoint changes still block
publication. A completed Worker or an accepted review alone never proves delivery.

Problem: a model `dispatch_intent` whose settlement observation was lost (CAS
exhaustion, storage outage, an ambiguous intent ACK whose void is refused, or a
restart) stayed durable forever, so publication refused a long-finished Worker
with an unnamed "In-flight paid execution" error. Decision: the publication gate,
lane settlement and startup recovery settle such an intent as an unknown-usage
lower bound only when the execution attempt is no longer live and this process
holds no open ExecutionBudget lease for that exact root/ordinal; a fold
watermark never hides a retained open row. Refusals name the blocking model or
tool occurrence. Alternatives rejected: voiding the intent (it may have been
billed), dropping the in-flight rule, or a timeout-based sweep (a slow live call
is not proof of an ended one). `test_project_dispatch_ended_intents.py` covers it.

Physical retries/resumes of the same accepted human input retain one source
cohort, idempotency identity, first issued Worker policy and shared allowance.
They recover, review and finish the earlier Workers; a new physical attempt
cannot hide unfinished work or reset its spending. A new human message can read
`get_project_workers(scope=project)` through bounded history pages and review or
cancel earlier Workers in the same live owner/tenant/Coordinator binding epoch.
Returned source Turn/current-request facts distinguish earlier objectives. Review
still requires live original authority and exact completed evidence; cancellation
never renews a grant. Synthetic continuations can read that history but control
only their original request. The alternatives—attempt-local status, treating a
new message as an empty project, or giving every synthetic continuation human
steering authority—lose continuity or cross the original authorization boundary.
`test_coordinator_worker_handoff.py` and its three-authority storage replay verify
resume/replay, completion, human steering, bounded history and synthetic refusal.

### Worker workspace preflight

Problem: Workers run in registered isolated Git worktrees, but nothing made a
project root able to host one. In a plain folder (the RSI Exam project: notes,
task packages and about 3.6 GB of data, never under Git) `delegate_project_work`
still created conversations and grants; each Worker paid for a model round, then
`admit_tool` refused its first tool call, and that refusal settled as
`interrupted/user_abort` with its reason erased, so the Coordinator reported a
phantom Stop. A first fix refused such roots early with `git init`/`git commit`
instructions; the owner rejected that, because the people using these folders
never run Git (decision 2026-10-25).

Decision: Tofu prepares the folder itself. `workspace_delivery.isolated_workspace_refusal`
first calls `managed_repository.prepare_managed_repository`, then checks the one
root contract: the accepted project path resolves to the real top level of a primary
local checkout with at least one commit. Preparation turns a plain folder, or an
unborn repository with an empty index, into a Tofu-managed repository: one
baseline commit by `Tofu Integration` with a matching index (the folder reads
clean), `tofu.managedRepository=true`, and a create-only default `AGENTS.md`
when the folder has no root guide (`CLAUDE.md`, `.cursorrules`, `AGENTS.md`,
`COPILOT.md`). User files are never modified, moved or deleted. The repository
is assembled in a `.tofu_git_init_*` directory and appears as `.git` only when
complete; a crashed attempt is discarded by the next one; preparation holds the
per-root `integration_control._repo_lock`. Its whole-tree Git (`ls-files`,
`add -A`, `read-tree`, `write-tree`, `check-ignore`) has no total deadline: like
the integration snapshot it runs under the shared `GIT_STALL_SECONDS` window
([project integration](modules/project_integration.md)), so a large folder takes
as long as its volume needs and only a Git tree that stopped executing for a whole
window fails the preparation as a typed `volume_stalled` refusal. The caller
observes each advance as its liveness (above) and its Stop ends the preparation; a
failed or stopped preparation leaves the folder as it was. The content policy
lives in `.git/tofu-managed.json` and a managed section of `.git/info/exclude`,
which linked worktrees share:

- never versioned: runtime, dependency and cache trees (`FORBIDDEN_CHECKPOINT_*`),
  `.tofu*` artifacts and the root `.venv` (bridged per checkout by `workspace_runtime`);
- shared: files of at least 10 MiB, untracked directories of at least 2,000 files
  that are mostly not source text, virtual environments, nested repositories,
  paths the folder's own ignore files hide (`git check-ignore` decides, so the
  parent of a shared path is never mistaken for one), root runtime directories
  and, once the owner chose so, nested projects (see the next paragraph).
  Worker binding (`workspace_delivery._binding`) links them into every checkout
  (`link_shared_paths`); workers read them in place, file tools refuse writes
  through them because the target resolves to the canonical checkout, project
  search skips links, and reclamation treats exact links as reconstructible;
- everything else is versioned: isolated, reviewed and published as before.

**Large folders and nested projects (2026-11-09).** A project manifest at the
folder root (`managed_repository_discovery.PROJECT_MANIFESTS`: each ecosystem's
build/package manifest, not dependency lists or generic `Makefile`s) makes the
root the project and preparation proceeds as above. Otherwise
`managed_repository_discovery.discover` lists the folder top-down and stops at
nested Git repositories, virtual environments, nested projects and paths the
folder's ignore files hide (`ActivitySupervisedExchange` keeps one
check-ignore answering per path, so an ignored directory is never listed);
their paths are excluded before any Git walk, so Git never enters them either.
A directory that holds nothing but nested projects is one shared folder of them.
The owner can additionally name whole folders of read-only run/reference data
(`shared_folders=...`, recorded as `sharedFolders`): they are shared whole and
never entered, which is how a project whose `work/` holds runtime distributions,
wheels, bundles and reports avoids versioning them.
Each listing is appended to a discovery journal in
`integration_control._control_root()/preparations/` (never in the folder), so an
interrupted or refused preparation resumes where it stopped; the journal is
discarded once preparation succeeds, and a mismatched header or torn record
discards only what follows it. When such a folder holds projects with a manifest
of their own, only the owner can say whether they belong to this project, so
preparation refuses with `ambiguous_project_root` instead of guessing: its
`details` carry the candidates grouped by top-level folder, the question, the
options and the recommended answer (`shared`), and nothing is written into the
folder and no Worker exists. The answer is supplied as
`prepare_managed_repository(nested_projects=...)`, recorded as `nestedProjects`
in the manifest, and never overridden by a later call (`decision_recorded`).
`scripts/prepare_project_folder.py` reports a folder read-only
(`preview_preparation`) and applies the owner's answer.

Measurement (autoharness on DolphinFS, 1,397,250 files, read-only dry run):
discovery listed 37,631 directories in 65 s instead of walking and listing 1.4M
paths, and refused with the typed question (21,673 nested projects: `work/`
21,668, `reference/` 5); resuming from the journal took 8.7 s. Sharing nested
projects alone would still version 21,825 files (694 MiB) of runtime
distributions, wheels, bundles and reports (192 s). Sharing `work/` and
`reference/` as the owner's data folders instead versions 89 files (7.4 MiB)
with 4 shared paths in about 12 s. A folder with a project manifest at its root
and bulky data is still prepared in one pass with its data shared.

`preview_preparation` and the script write only into their scratch directory;
nothing is created, changed or removed in the folder during a dry run. The
script applies the owner's answers without Git:
`python3 scripts/prepare_project_folder.py <folder> --nested-projects shared
--shared-folder work --shared-folder reference --apply`.

Every preflight refreshes the policy before the Worker's input snapshot, so
newly added bulky data (and nested projects, under a recorded `shared` answer)
joins the shared set, which only grows; no further commit is made. Repositories
with their own history are never changed. Remaining refusals carry a `code`
naming the cause and a bilingual remedy without Git commands: a subdirectory of
another repository, a linked worktree, a missing or remote root, an unwritable
folder, an unborn repository with staged files (Tofu does not commit someone
else's staged work), an ambiguous project root (above) and a stalled volume.
Delegation calls the check through `admission.require_isolated_worker_root`
before creating any conversation or grant (accepted replays are not rechecked)
and returns a refusal with `execution_started: false`, the typed `code`, its
`details` and do-not-retry recovery (an ambiguous root names the owner question
instead). Worker binding repeats it for files/project grants before workspace
creation or the first model request, failing through `task_start_failed` with
the remedy as its hint, so the same cause reaches the Coordinator when the
delegation ran on another host. Late `admit_tool` refusals raise
`ToolAdmissionRefused` and settle as failed
(`docs/contracts/TURN_SETTLEMENT.md`). `await_project_workers` adds the settled
`error` (kind/detail/hint) for failed, interrupted or truncated Workers.

Measurement (RSI Exam on DolphinFS, Git 2.34, dry run against a scratch Git
directory): first preparation 15 s (content walk 10.7 s, baseline 3.6 s);
1,143 versioned files and a 21 MB `.git`; four shared paths (27,125 Qlib `.bin`
files and three parquet panels of 93 to 331 MiB) instead of about 28,000 more
versioned files and 720 MiB copied into every checkout; `git status` 0.1 s and
clean afterwards.

Alternatives rejected: refusing with Git instructions (the people who own these
folders never run Git); running Workers directly in the canonical folder (loses
isolation, review and publication); versioning everything (checkout cost on
network volumes grows with file count, and every Worker would copy the data);
a separate non-Git snapshot/publication store (a second delivery authority);
committing someone else's staged index; guidance that overwrites a person's
file. For large folders: a file-count cap, size budget or timeout (the owner
rules out caps, and a cap only moves the failure); guessing which nested
projects are part of the project (a manifest-less monorepo and a folder of
copies look alike, so only the owner decides, once and recorded); sharing
nested projects unconditionally (would silently make a project's own packages
read-only to workers); preparing into a worker checkout before the owner
answered (writes into the folder and creates a Worker that cannot work).
Verification: `test_managed_repository.py`,
`test_managed_repository_large_folders.py` (typed ambiguity with an untouched
folder, both owner answers, pruned discovery, resume, typed stall, read-only
preview), `test_activity_supervised_process.py`,
`test_project_dispatch_file_lifecycle.py` (plain folder to isolated write,
review and publication back into the folder), `test_workspace_completion.py`,
`test_coordinator_workers.py` (the owner's question as the delegation's tool
result) and `test_tool_admission_refusal_verdict.py`.

Problem: rejecting a project path solely because it contains a symlink forced
people to reopen the same folder and resend their request, even though the real
directory was already known. Decision: resolve local project aliases (including
symlinked ancestors) inside preparation and workspace admission. The original
project key, Coordinator/Worker conversations and accepted grant remain unchanged;
Git operations, locks and workspace registration use the resolved physical root.
Dispatch ownership and delivery receipt lookups resolve the grant's project path
at the filesystem boundary and still require the exact owner, task, registered
workspace and captured canonical root. Retargeting an alias cannot transfer an
existing Worker's ownership or publication to another directory. Broken aliases,
repository subdirectories and linked worktrees retain their existing refusals.
Alternatives rejected: reopening/rekeying the project loses conversation and
authorization continuity; merely removing the preflight refusal leaves physical
workspace lookups mismatched; bypassing isolation weakens the delivery contract.
The alias variants of the preparation, workspace refusal, Coordinator delegation
and file lifecycle tests verify this path through isolated write and publication.

### Project-grant publication fence (2026-11 decision)

Problem: publication (`lib/project_dispatch/publication.py`) applied the
file-grant path rule of `lib/project_dispatch/scope.py` to `project` checkpoints.
That rule refuses a path when any segment is `data`, `logs` or `uploads`. A
project grant pins `writePaths: ["."]`, and publication checks every old and new
path, so 43 tracked source files could never be added, changed, renamed or deleted
by a Worker. They are the model catalog in `lib/model_info/data/`,
`lib/site_packs/data/` and the Android `com/tofu/client/data` package. Delivery
stopped at `project_publication_write_scope_exceeded`.

Decision: the fence depends on the grant mode.

- Root `data/`, `logs/` and `uploads/` are refused for every grant, in any letter
  case.
- Publication passes `project_grant` for `mode: project`. A project checkpoint may
  then change a nested package with one of those names. This is the project-mode
  intent that `lib/git_checkpoint_policy.py` states for `FORBIDDEN_CHECKPOINT_ROOTS`:
  "Root-owned runtime/reconstructible trees. A nested source package stays legal."
- Build-output names (`build`, `dist`, `target`) follow the same split. A project
  checkpoint is a commit already filtered by the project's own `.gitignore` and
  `git_checkpoint_policy`, so tracked content there (for example a rendered
  `docs/report/build/` deck) is source; refusing it held whole paper/merge
  deliveries at `project_publication_write_scope_exceeded` despite `writePaths: ["."]`.
- File grants keep refusing these names at any depth. This covers descriptor I/O,
  profile prefixes, shared files and file-grant publication.
- Both modes refuse the following at any depth: checkout control, undo evidence,
  Tofu artifacts, dependency caches (`node_modules`, `.venv`, `__pycache__`), and
  `.env`/`.env.*`. The `.env.*`
  rule includes `.env.example`, because the fence cannot tell a template from a
  filled-in credential file.
- Refusals stay `ValueError` and name the refused root tree or segment. A held
  publication logs the first refused path once (`[ProjectPublication]` warning).

Measured over every tracked file under `.`: in project mode, 43 files become
publishable and two stay refused (`.env.example` and `uploads/images/.gitkeep`).
File mode is unchanged.

Alternatives rejected:

- Root-anchoring `data`, `logs` and `uploads` for all grants. This weakens
  file-grant confinement, whose specification refuses `src/data/secrets` and
  `src/logs/app.log`.
- Allowlisting the affected files. Every new nested `data` package would repeat
  the incident.
- Reusing `FORBIDDEN_CHECKPOINT_ROOTS` wholesale. That would add refusals for
  `output/` and the evaluation trees, which is a separate decision.

Known residue: the any-depth names still refuse Bazel `BUILD` files, Nx
`project.json` files and committed `dist/` trees in other projects. None is
tracked here.

Specifications:

- `test_project_dispatch_scope.py`: file grants refuse nested names and project
  grants accept them. Both modes refuse root runtime trees, credentials and
  metadata.
- `test_project_publication.py`: project grants deliver nested `data` packages,
  including renames. Root runtime trees and `.env*` files that a Worker commits
  stay blocked. File-grant publication still refuses nested names.

### No spending ceiling (2026-10 decision)

Problem: each request used to share 2,000,000 tokens, 128 model requests, 4,096
tool calls and two hours, with at most 16 model requests per Worker. In real use
(`coordinator-1a390889…`) every Worker and continuation stopped within minutes on
"previous model usage is unconfirmed"; unconfirmed attempts kept their whole
reservation, so the request reported "Coordinator needs a new budget" after a
handful of failures. The user had to return and re-authorize repeatedly, which
defeats handing off the work.

Decision: Coordinator requests, Workers and continuations carry no token, model
request, tool-call or time ceiling. `budget` is `{}` and profiles omit
`maxToolCalls` on new grants; their `executionLimits` are all null, so
`ExecutionBudget` admits without a finite cap and a missing provider receipt is a
recorded lower bound instead of a fence. The dispatch CAS still records every
physical occurrence exactly once (`accounting.py`) and `request_budget.py` keeps
the per-request account for identity, resume continuity and usage projection.
Earlier finite grants keep their recorded spend ceilings. Worker parallelism
has no task-count or memory ceiling. New policies omit `maxConcurrent`; older
issued values remain immutable receipt data and never refuse new Workers.
The grant CAS still checks source-policy identity, and Stop, binding,
human-source and exact-attempt authority remain on every model/tool call.

Alternatives rejected: an optional limit that is off by default (the user asked
for complete removal); raising the defaults (same failure, later); asking the
user to grant more budget on exhaustion (requires the user to stay present).

### Request usage view

The request account (`requestBudgets` in the dispatch record, keyed by accepted
human Turn/projection and binding epoch) holds an immutable task/attempt/nonce
per physical root account, registered at task startup inside existing rollback.
An attempt owing a deferred input translation binds after its worker records
the verdict, using exactly that settled source revision. After a restart, an
interrupted attempt resumes as a new task/attempt under the unchanged durable
source and joins the same account; it never resets the old physical nonce.
The source Turn/projection, tenant and subject remain live fences: a restart
is not supersession, but a changed request or principal is refused.
A new attempt on the same human input joins the same account. A request whose
input is not genuine human input (a report relay, a channel event or any other
nonhuman initiator; `SyntheticSource`) opens no account and starts normally;
delegation from it is still refused.

A request the Global Router forwarded (`origin.forwardedFrom`, ROUTER.md R2) is
genuine human input once `verify_forwarded_turn` admits it: the owner's verbatim
words of the current request, or of an active standing instruction. Its
nonhuman evidence (the router note, the instruction's triggering event) rides
**inside the same input** as labelled context after the owner text
(`originalContent` keeps the owner's verbatim words, which is what
`authored_text` and the forward verification compare); it is never a second
input, because a second input would start its own synthetic Coordinator request
whenever the steer window was closed and be refused here. So an authorized
forward — including one applied from a standing instruction while the owner is
away — delegates Workers, pages them read-only and finishes its request through
the unchanged `source_for_task` path, opens the ordinary request account above,
and needs no new "继续". The instruction's `projectPath` scopes where it may be
applied and pausing/cancelling it stops future applications
(`route_to_project`); work already forwarded keeps the authority it was admitted
with. Specifications: `tests/router/test_proactive_instruction_dispatch.py`.
GET
`/api/v4/project/coordination/budget` (owner-scoped `conversations`, passive)
returns combined Coordinator + Worker tokens, model requests, tool calls, active
Workers, whether receipts are complete, and any pending decision. The former
POST defaults endpoint and settings editor are removed. `get_project_workers`
returns the same view as `request_usage`. The browser shows usage only in the
explicit management dialog, never in the chat. Guards:
`test_coordinator_request_budget.py`, native `test_coordinator_workers_authority.py`
and `coordinator-budget.test.ts`.

Alternatives rejected: treating role binding as standing authority, forcing a
human click per Worker, copying a separate model loop, and repeatedly asking the
model to poll. Current scope is the original accepted human request;
standing missions remain outstanding. Automatic continuation below uses the
same request account. Segmented persistence
retains assignments beyond the former project-lifetime limit. Verification includes
`test_coordinator_workers.py` and `test_coordinator_workers_authority.py`: native
Turn birth, ordinary file/shell tools, isolated Git delivery, report unread state,
exact replay and storage restart, without paid provider calls. The wait test
observes zero additional physical sends and zero retained terminal callbacks;
the native journey verifies the delivered worktree is reclaimed.

### Session-free coordination (owner decision 2026-11-02)

Problem: the Coordinator canvas stacked a request plan, a "needs your help"
report banner, a paged work-and-session list with copy/view references, a
dependency graph and a usage table. The human had to track sessions, workers
and states to learn how their tasks were going, and follow-ups surfaced as a
banner instead of a question they could answer. The evidence-cited plan
(rejected below) was correct but unreadable. Messaging also did not behave like
two people talking: `await_project_workers` ignored a human message for up to
30 minutes, `ask_human` could only block, a reply quoted while the Coordinator
worked lost its quote, and the Coordinator's role guidance (824 tokens) was cut
to its 600-token context block, silently dropping its last instructions.

Decision. The human only chats with the Coordinator; the Coordinator tracks
sessions and tells the human what matters.

- Task board. The bound Coordinator authors the board with
  `update_task_progress`: a one-sentence `summary` plus up to 24 tasks in the
  human's words, each `pending | in_progress | completed | cancelled` with an
  optional one-line `progress` note (`progressRequest` in
  `contracts/project_coordination_v1.schema.json`). It is model-authored on
  purpose: deciding what the human cares about and summarizing it is the
  Coordinator's job. It is a summary, not evidence, and grants no authority;
  Worker records and conversations remain the evidence.
  `lib/conversations/coordinator_progress.py` keeps one validated head per
  owner/project (`project.coordinator.progress.v1`) for the current binding:
  full replacement under CAS, unchanged content is a no-op, a lost
  acknowledgement replays as unchanged, a replaced binding starts empty and an
  older binding can never overwrite a newer one. Writes push the existing
  `project` hint. GET `/api/v4/project/coordination/progress?path=`
  (owner-scoped `conversations`, passive) returns `progressState`. The board
  is also the Coordinator's checklist and refreshes live from its write's
  round ([One progress source](#one-progress-source-owner-decision-2026-11-08)).
- Browser. `frontend/src/features/coordinator-progress.ts` is the only thing
  pinned atop the bound Coordinator chat: a collapsible card that reads as a
  todo list and starts folded to its head, one line holding the title, the
  in-progress count, the summary and the update time (an empty or unavailable
  board says so there); opened, the summary takes its own line. Each task is
  one line behind a status glyph (a ring while pending, half filled in
  progress, a filled check when completed, a filled cross when cancelled):
  in-progress work first, then the Coordinator's order, finished tasks folded.
  Only an in-progress task shows its note, cut to one line; every other note
  is its row's tooltip and stays in the accessibility tree. The footer holds
  one explicit "Manage work" button for the existing management dialog, led
  by a Project Router's Worker model control ([ROUTER.md](ROUTER.md) R5)
  instead of a line of its own. The card persists across repaints of the same
  Coordinator chat, so fold, scroll and focus survive live board updates. It
  starts folded because the sidebar already shows the in-progress count and
  lists the Coordinator's Worker conversations, so an open board only
  repeated them in the chat's reading space; removing the board instead would
  also drop the summary and the in-chat way to management. No session list,
  references, graph, usage or report banner remains there. The sidebar entry
  shows the in-progress count (or "all done") with the summary as its
  tooltip. A Worker chat keeps one "return to Coordinator" button.
- Display translation. Problem: the board stayed in the Coordinator's working
  language beside its auto-translated replies. Decision: while the human reads
  the Coordinator chat auto-translated (the publishing turn's config, else the
  conversation's stored settings; a project-dispatch continuation's config
  pins translation off, so only the settings decide there), every board
  write (`update_task_progress`, or a `todo_write` publishing the checklist),
  an unchanged board too so a failed translation retries, schedules one
  optional job on the shared reconstructible
  translation lane (`lib/conversations/coordinator_progress_translation.py`).
  The job translates only the board texts that lack a translation in that
  language through `lib/translate/display_texts.py`, which runs each text as a
  segment of the settled-turn segment core (cache, protected spans, enrichment
  and 429 budgets, polite contention), and merges them into the same head under
  CAS as `progressTranslation`: reconstructible display data, never evidence.
  A republished board keeps the translations of texts it still shows; a dropped
  job (restart, refused admission, translator failure) leaves the board as
  written until the next publish. The card shows covered texts translated,
  with the shared "Original" toggle back to the board as written. Alternatives
  rejected: having the Coordinator write in the reading language (the board
  would leave its working language and turning translation off could not
  restore it); translating in the browser or on the GET read (rendering and
  reads are passive and start no work).
- Questions are chat cards. Follow-ups are never board entries or report
  banners: the Coordinator asks with `ask_human`. `blocking=false` posts the
  card, whose question states the default the Coordinator works on meanwhile,
  and returns at once; the human's answer is an ordinary message quoting
  the question (the card fills the composer's existing reply-quote and sends,
  or adds to an existing draft), so it steers a live turn or starts the next
  one. `blocking=true` waits as before; a chat message sent instead of the card
  ends the wait and reaches the model as the answer or new direction. Only a
  steer the seam authored as human input counts, and a Global Router forward
  of the owner's message only once `require_human_turn` verifies it: channel
  events, relayed reports and questions and other nonhuman steers sharing the
  lane never answer for the human ([ROUTER.md](ROUTER.md) R1 "Asking the
  owner"). A Project Router's question also reaches the owner's Global Router
  as a nonhuman notice (ROUTER.md R3). Asking is
  intrinsic to the role (like Plan Mode clarification): human Coordinator turns
  always expose `ask_human`, and new continuation policies freeze it, so a
  Coordinator continuation may ask too (`admission.asks_human`; older policies
  keep `humanGuidanceEnabled=false`). `request_user_decision` is no longer
  offered; decisions already recorded still resolve through recovery.
- Messaging. In a Coordinator chat, the Global Router's and the Watchdog's
  included, the composer delivers into a live turn without the steer/queue
  prompt (the server still queues when the live window closed); Worker and
  ordinary chats keep the prompt. Server bindings, not the folder the sidebar
  shows, identify the chat ([RENDER_CONTRACT.md](RENDER_CONTRACT.md)
  "Translation attribution"). `await_project_workers` returns
  `wait=pending_input` as soon as a human message, or any other input listed
  under the wait above, is waiting.
  Steered messages keep their reply quotes as
  Markdown block quotes. Opening the visible Coordinator chat reads its latest
  message with the exact Turn ID, like any messaging app.
- Role guidance is `COORDINATOR_ROLE_GUIDANCE` in
  `lib/conversations/project_coordination.py`; a test pins that it fits the
  `project_coordinator` block budget with the canonical counter.
- Routers ([ROUTER.md](ROUTER.md#r1-a-router-is-a-coordinator-the-global-router-is-the-home-coordinator))
  are bound Coordinators and inherit the board and chat-card questions; the
  Router Watchdog's narrower ceiling has neither.

Alternatives rejected: keeping the evidence-cited plan projection
(`coordinator_plan.py`, removed with its schema, route and view: correct but it
made the human audit records instead of reading progress); leaving follow-ups in
a banner (another state to track, with no answer control); timed decisions via
`report_to_user(kind=decision)` plus `request_user_decision` (a report the human
cannot answer in place); blocking every question (stalls work that has a
sensible default). Keeping the board and the `todo_write` checklist as two
lists was superseded on 2026-11-08 (below).

Verification: `tests/project_mod/test_coordinator_progress.py` (board and
translation merge), `tests/translate/test_display_texts.py`,
`tests/project_mod/test_project_coordination.py` (role text and block budget),
`tests/tasks_pkg/test_ask_human_nonblocking.py`,
`tests/project_mod/test_coordinator_workers.py` (pending input),
`tests/conversation/test_conversation_command_inject_mode.py` (steer quotes),
`frontend/src/features/coordinator-progress.test.ts`,
`project-coordination-surface.test.ts` and `project-coordination-entry.test.ts`.

### One progress source (owner decision 2026-11-08)

Problem: a Coordinator kept two progress lists. `update_task_progress` wrote
the board; `todo_write` kept a separate task-local checklist (in one owner
Coordinator: 167 board writes beside 87 checklist writes of other, longer
English steps), so the two drifted, and the owner asked to simplify them into
one. The board also did not refresh live: its only refresh was the `project`
push, which `push_event` delivers to the writing process's own sockets, and a
Coordinator's tools run in the resident execution host, which has none under
the default `inproc` push bus. The pinned board changed only after the owner
left the chat and came back. The checklist view stayed live because its round
reaches the browser through the conversation stream, which the API host's
commit watch wakes for writes of every process.

Decision: one progress record with two views.

- Record. The board head stays the only store of a Coordinator that keeps a
  board (its tool ceiling has `update_task_progress`; the Router Watchdog's has
  not). The task's checklist state (`_todoState`, the Turn's `todoState`, the
  context composer's Active Task Checklist) is the board's plan projection
  (`plan_from_board`: tasks in board order without `cancelled` ones, the
  summary as explanation), never a second list. Both writes hold the task's
  progress lock, so they cannot interleave.
- Writes. `update_task_progress` publishes the board and adopts its plan
  (`publish_task_board`). Its receipt adds `plan`, the checklist the model now
  holds, which is also the evidence that keeps the checklist block from being
  re-injected while the receipt is visible. `todo_write` keeps its schema and
  validation; in such a chat it publishes the accepted checklist as the board
  (`plan_publication`, `board_from_plan`): items become tasks, a task keeps its
  note while its title and status are unchanged, the summary stays, and a first
  board takes the explanation when it fits on one line, else its current item.
  A checklist the board cannot show (an item over 120 characters or on several
  lines, or `blocked`) is rejected with that reason and changes neither view;
  so are a replaced binding and a failed save. Every other chat keeps its own
  checklist exactly as before.
- Live refresh. Each progress write's round carries `coordinatorProgress`
  (project, Coordinator, binding revision, board revision) beside the plan's
  `todos`/`todoState`. The retained tool-round renderer feeds both to the live
  rail checklist and, through `runtimeScope.observeCoordinatorProgress`, to the
  coordination surfaces: a board revision newer than the shown one of the same

### Commitments on the task board (owner request 2026-11-08)

Problem: a Coordinator or the Global Router tells the owner "I'll report back
when X" or "I'll resume at 23:20", and nothing records or checks it. The
follow-up happens only if some later event happens to wake the lead. A
Coordinator could not wait for a time at all: with no Worker active, its
continuation counted idle turns as stalls and ended in a blocked report. This
is the promise ledger of [ROUTER.md](ROUTER.md#r10-proactive-coordination-owner-request-2026-11-08) R10.

Decision: a commitment is a board task with a `due` time, so the board the
owner reads is the ledger, and the platform wakes the lead when it is due.

- Record. `progressTask.due` (ISO 8601 date-time with offset) is optional. A
  task carrying it is a commitment to the owner: by then the task is done or
  the lead reports on it. A new or changed `due` must be in the future. An
  open commitment (`pending` or `in_progress`) is identified by its title, so
  two open commitments cannot share a title.
- Lifecycle. Keeping it is `completed`; dropping it is `cancelled` (tell the
  owner why); re-dating it is a new `due`. A write that omits an open
  commitment is refused and changes neither view, so a commitment never
  disappears silently; `todo_write` keeps each task's `due` by title.
- Receipts. The same board head carries a platform-written `commitments`
  list (reconstructible from the board, never authority): per title the first
  and current due, the number of slips, the wake receipt and the closure
  (`kept`, `late`, `cancelled`). It is written in the same CAS as the board, so
  a board and its receipts never disagree.
- Wake. A write that changes the earliest open due time arms one scheduler
  `once:` row for that minute (deterministic id per owner, Coordinator and
  minute; type `coordinator_commitment_due`). The row's handler re-reads the
  head and wakes the lead once for every open commitment due by then that has
  no wake receipt for its current due. Inside an open request with a
  continuation policy, the wake is that request's continuation (reason
  `commitment_due`), so the lead may resume, re-delegate or verify work under
  the request's authority. Otherwise it is one `proactive` notice through
  `dispatch_scheduled_turn(..., inject_mode='steer')`, command id
  `commitment-due:` + digest of (owner, Coordinator, titles and due times):
  a running lead is steered, an idle one starts a turn that can report, ask
  and update the board but cannot delegate. Each due time wakes once. A
  commitment still open after its wake is overdue; the digest and
  `get_router_projects` list it, and nothing wakes the lead for it again.
- Waiting is not stalling. A continuation with no active Worker and an open
  commitment due later waits until that time instead of retrying with
  backoff, so a lead can wait for a quota reset or a run's expected end.

Alternatives rejected: a promise store and list beside the board (the second
progress list the owner asked to remove); detecting promises in reply text (a
model guess, and nothing to show the owner); a reminder interval or repeated
wakes for an overdue commitment (a knob and a wake storm; the digest surfaces
it); task IDs on the board (the board is model-authored in full each write,
and titles already identify tasks for notes and translation).

Verification: `tests/project_mod/test_coordinator_commitments.py` (board rules,
drop guard, receipts, arming, one wake per due time, busy lane, replaced
binding), `test_coordinator_commitment_continuation.py` (future due is a wait
not a stall, due wake while a Worker runs, already-woken dedup, other
Coordinator ignored), and `tests/router/test_proactive_replay.py` (today's
scenarios: stalled worker, overdue promise, quota-reset deadline, channel
reconnect).

### Result-driven Coordinator continuation

Problem: a Coordinator can end its turn before the delegated request is done,
or lose its process while Workers are executing. Decision: the original human
request issues a versioned continuation policy during tool assembly.
Worker/Coordinator durable settlement, delivery notifications, due decisions and
existing startup recovery derive internal `coordinator` grants in the same
dispatch record. Old policies never gain this authority. The ordinary
command/Turn/task lane starts a system-principal continuation; its input remains
synthetic. No model loop, extra worker pool or shadow task state is introduced.

Continuations have no spend ceiling or deadline. Only frozen Coordinator tools
are admitted; it has no file/shell execution or worktree. It can delegate and
review Workers using the original source, model, policy and idempotency
identities. Changed capability settings cannot enlarge that policy. Human queued
input retains priority. Duplicate notifications/CAS retries reuse one grant and
one ordinary birth. Failure wakes only the Coordinator policy and preserves the
existing skip-on-error rule for ordinary queued messages.

`get_project_workers` pages at most 32 thin owned assignment facts and returns
only the leading rows that reach the model inline, with a cursor that resumes
exactly after the last row shown (history pages expose `rowOlderCursors`); full
evidence stays in ordinary conversations. `cancel_project_work` checks the human steering
or original-continuation boundary above and aborts the exact Worker attempt under
the existing publication lock.
`finish_project_request` requires a durable report Turn: `complete` requires all
non-cancelled Workers' exact accepted results, settled effects and confirmed
canonical delivery; `needs_user` requires a decision/blocked report. Its immutable
receipt and new delegation serialize in the same CAS. The receipt stops automatic
continuation; cancel unwanted active Workers explicitly before asking for input.

Continuations run under the model selection of the request they continue.
Problem: admitted from the frozen capability policy alone, they lacked the
request's `chatMode`, `memoryEnabled`, route (`modelRef`, `preferredProviderId`,
`routing`, `preset`) and experiment blocks, and the role's
`programmaticCalling=off` reached human Turns only in tool assembly, after model
replay had pinned their policy. Every human/continuation alternation therefore
refused the validated replay checkpoint (`restore=policy_changed`) and rebuilt
the whole history, and continuations took the legacy model-name route instead of
the request's routed candidate group. Decision: `admission.request_selection`
copies those model-view selections (experiment blocks normalized, never `tools`)
from the delegation's accepted source attempt, the route only when it names the
grant's model; the grant still fixes capabilities, tools and model. Executor
ingress applies the role's tool settings
(`coordinator_policy.pin_coordinator_request_policy`, the same helper tool
assembly and the issued policy use) before the replay pin; a failed role lookup
keeps the submitted settings and tool assembly still fails closed. Real
tools/model/route/experiment/system-prompt changes still refuse replay.
Alternatives rejected: exempting dispatch tasks from witness fields (restores
across real changes); defaulting absent fields inside the witness (cannot see
the role or route, and invalidates every checkpoint); recording the selection in
the grant schema (contract change that leaves existing grants cold, while the
accepted attempt config already is the durable authority). Cost: one source
attempt read per continuation admission. Spec:
`tests/project_mod/test_coordinator_replay_policy.py`.

A continuation keeps its grant's tool settings through tool assembly. Problem:
assembly re-applied `coordinator_tool_settings` to every Coordinator Turn, which
re-normalizes the `tools` block. Once a build retired `toolSearch: auto`, every
continuation whose grant recorded `auto` drifted from that grant, so the
admission fence ("programmatic policy changed after admission") stopped it
before its first model call (`dispatch_authority_lost`) and its request could
neither continue nor finish. Decision: assembly applies the role's settings
only to human Coordinator Turns, as executor ingress already does; admission
fixed a continuation's settings, including `programmaticCalling=off`, and
readers normalize retired values themselves. The fence stays exact.
Alternatives rejected: comparing normalized forms in the fence (weakens an
authority check to excuse a writer), and rewriting stored grants (immutable
evidence). Spec: `tests/project_mod/test_coordinator_continuation.py::
test_continuation_admitted_before_a_tool_flag_retirement_keeps_its_grant`.

Background completion resumes read both predecessor and successor attempts
through the repository's owner-scoped `get_attempt` port. Its default resolves
the selected lifecycle store lazily, just as an injected test reader does.
Calling the optional injected reader directly was rejected: ordinary production
repositories omit it, so a durable successor could be created but never bound
back to its assignment. The worker continuation specification exercises both
reader configurations and preserves the exact predecessor/successor fences.

A background batch's deterministic Continue stays a single wake even after a
later human attempt supersedes it. Replaying its settled receipt neither moves
the assignment backward nor reports a new launch; unconsumed command results
remain available to the next real turn. The ordinary command replay and queue
owners enforce this without weakening dispatch evidence or creating another
receipt store.

A continuation that ends without changed work/review/delivery evidence (including
a failed Coordinator turn) is retried after `stallRetrySeconds` backoff
(30 s, 2 min, 10 min, 30 min, 60 min); only after `maxStalledTurns` (6) such turns
does it publish a deterministic blocked report and stop, using no extra model
request. Waiting for active Workers is not a stall. Unconfirmed model usage never
stops the request; unsettled tool effects still block delivery claims. Stop,
binding withdrawal and missing source evidence refuse further birth. Grants and
continuation receipts share the segmented project-head CAS.

### Decisions with a default

The Coordinator no longer receives this tool (see "Session-free coordination":
it asks with `ask_human(blocking=false)` and proceeds on its stated default).
The mechanism remains for decisions already recorded.
`request_user_decision(report_turn_id, recommendation, wait_seconds=1800)`
followed a `report_to_user(kind=decision)`. It records `pendingDecision` on the
request account and keeps the request open; independent Workers continue. If a
human Turn arrives after the report, that new request steers the work and the
default is not applied. Otherwise, at `dueAt` recovery births a continuation
with `coordinatorWake.reason = decision_default` whose brief says to apply the
recommendation and say so in the next report, and marks the decision
`default_applied` in the same CAS. `finish_project_request(outcome=needs_user)`
remains for cases without a sensible default.

Problem: the continuation brief still told every continuation to follow a
decision report with `request_user_decision`, which session-free coordination
removed from the Coordinator ceiling, so a continuation that needed the human
was refused with advice to delegate. Decision: the brief names only tools its
grant froze. When `admission.asks_human` admits the continuation profile, the
brief says to ask with `ask_human(blocking=false)` and state the default applied
meanwhile. An older grant without `ask_human` proceeds on its recommended default
and says so in its next report, or, without a sensible default, reports
`kind=decision` and finishes with `needs_user`. Alternatives rejected: returning
`request_user_decision` to the ceiling (restores the report-then-wait flow that
session-free coordination removed) and always naming `ask_human` (older grants
cannot call it). Spec: `test_continuation_brief_names_only_tools_its_grant_holds`.

Timed wakes (backoff and due decisions) are a process-local `threading.Timer`,
one per owner/project keeping the earliest due time. They only call the same
idempotent recovery pass; the due time itself is derived from durable records,
so a lost timer is recovered by startup or any later settlement. Rejected: a
durable scheduler job per request (a second authority over the same state) and
indefinite waiting for the human (contradicts unattended completion).

Code delivery is automatic: the Coordinator's review with a checkpoint authorizes
publication, the delivery receiver merges the task delta into the canonical
checkout and, in a repository that opted into automatic commits, commits exactly
that delta onto the current branch, with no human step
([project integration](modules/project_integration.md#task-owned-canonical-delivery),
"Reviewed project deliveries become commits"). A delta that built on uncommitted
canonical bytes stays delivered as working-tree bytes; its `entangled`
acknowledgement names the paths.

Alternatives rejected: treating a notification as human authority, adding a
second scheduler/task state, and reusing a generic queued message with mutable
capabilities. Verification: concurrent notification and finish/delegate races,
lane priority, authority withdrawal, stall backoff, decision defaults, unknown
consumption and native storage restart in `test_coordinator_continuation.py` and
`test_coordinator_workers_authority.py`. Native restart runs one continuation
through ordinary tool assembly/model accounting/review, then actual Git delivery,
report unread state and durable completion; repeated recovery sends nothing.
Internal continuation rows produce neither Worker nodes nor human review cards.
Measured in the deterministic two-assignment fixture: 50 idle callbacks took
0.539 seconds, retained 5,470 bytes unchanged, and produced zero new births,
durable writes or threads. This is metadata-path evidence, not a provider latency
claim. The native journey checks real physical accounting separately.

### Proactive reports and durable attention

Problem: an unseen result in a Worker chat or a volatile notification cannot
reliably tell the human that the Coordinator needs a decision or has delivered.
Decision: the bound Coordinator's `report_to_user` tool publishes a concise
`progress`, `decision`, `blocked` or `delivery` report as an ordinary assistant
Turn in its own conversation. The title is at most 120 characters; the plain
text message is at most 4,000. Role guidance asks for meaningful milestones and
verified delivery, rather than every status change; questions are `ask_human`
cards, never reports (`decision` remains readable for recorded history).
Reporting grants no authority and never implies human acknowledgement or consent.

Minimal human interruption (owner decision 2026-10-26). The system asks the
human only when progress needs something only the human can provide and no
sensible default exists. Pending reviews, unmet dependencies, retries,
re-delegation, and merging/publishing verified work are the Coordinator's to
resolve; role guidance and the `report_to_user` description forbid presenting
them as questions or permission requests. The human can still intervene at any
time by talking to the Coordinator or any Worker. Alternative rejected: a
derived "needs your attention" list of review/dependency/delivery items. It
turned the Coordinator's internal queue into human chores, and it offered no
action the human could take.

`coordinator_reports.py` first retains an immutable publication intent, then
uses a stable canonical Turn command, updates one latest-report/read pointer,
and retires the transient intent. The existing project startup recovery pages
through pending intents; it never invokes a model or creates a task. Lost
acknowledgements, concurrent identical sends and restarts reuse the same Turn.
A changed request under an existing key is rejected without poisoning later
original retries. Older retries cannot replace newer attention or rearm read
messages. Owner, project, Coordinator identity and binding revision are checked;
replacement withdraws pending transport while preserving old conversation history.
Reports can be ingested during the ordinary Coordinator attempt without replacing
that attempt or preventing its settlement.

The attention head is a projection, not an independent transcript. If its Turn
has been deleted, reads return empty attention after rechecking the binding;
they do not rewrite history or the read watermark. Storage failures and a
present Turn with mismatched identity still fail visibly. Treating a missing
Turn as an internal error was rejected because a legitimate history deletion
would break every subsequent report poll.

Model view. Problem: a report Turn is ingested after the still-running reply
that published it. Replaying it as one more assistant message after that reply
makes every later request carry assistant/assistant adjacency, which
`build_body` merges with an "UNEXPECTED pair" warning, and the model reads each
report twice: as its own `report_to_user` arguments and appended to the reply's
final text, so a cold rebuild no longer matches the view the model sent.
Decision: report Turns are human-facing delivery records, not model output.
History projection (`_transform_messages`; the Turn-native builder projects
`_turnKind` as the conversation projection does) omits every
`coordinator_report.*` Turn. The model keeps each report through the publishing
reply's own `report_to_user` call and result (title, message, report Turn ID).
The deterministic stall-stop report was never a model turn either; the next
human Turn carries the steering. Alternatives rejected: declaring a designed
same-role seam silences the guard but keeps the duplicated, misplaced text;

### Stable capabilities, discoverable conversations and diagnosis

#### Session execution control

Problem: a Coordinator could read transcripts and manage its own assignments,
but could not inspect or operate a concrete existing conversation as the owner
could through Continue and Stop. Decision: `get_conversation_status` and
`control_conversation` share `lib/conversations/session_control.py`. The Global
Router can address the owner's conversations; a project Coordinator addresses
conversations in its project. The live binding and owner are checked on every
call. The Watchdog and ordinary Workers receive neither control capability.

Status never reads a whole conversation. Problem: it read the complete
synchronization snapshot and filtered `turn_id` afterwards, so a long history
failed with `database_resource_exhausted` ("turn response exceeds its bounded
streamed payload") even for one Turn, and a medium one spilled every Turn into
an artifact. Decision: an explicit `turn_id` reads that Turn's metadata and its
current Attempt by identity. Otherwise one lane (default `main`) is read
newest-first through `turn.sync.page`, each page one bounded read that the
repository reads again smaller when the authority refuses it at its response
bound, and Turns are admitted while the result still reaches the model inline
under the single tool-result budget (`fits_tool_result_budget` in
`lib/tasks_pkg/compaction/_budget.py`). The newest Turn is always shown;
`window.next_before_ordinal` with `lane_id` pages older Turns. Both forms expose
Turn/Attempt identities, revisions, settlement/resume options and the queue
preview without execution config; the live presentation phase and replay head
stay browser concerns. `get_conversation` remains the transcript reader. Status
is passive and is never cached as authorization. Alternatives rejected: a fixed
Turn count per window (either spills heavy settlements into an artifact or hides
Turns that fit), `turn.sync.snapshot` with `turn_limit` (bounded only for linear
conversations; a branched one still takes the whole-history path), and a new
metadata-only page operation (a new semantic operation on both authorities,
while page reads already stay inside the existing bound). Specification:
`tests/conversation/test_coordinator_status_bound.py` (SQL and native, a history
beyond a 96 KiB response bound).

Partial results are readable by every Coordinator role. A result above the
single tool-result budget becomes a partial envelope whose only recovery is
`read_tool_artifact`/`search_tool_artifact` (kept eager in the registry for
exactly this reason), yet `COORDINATOR_TOOLS` (and so `ROUTER_TOOLS`) and
`WATCHDOG_TOOLS` lacked them: a Coordinator got an `artifactRef` it could not
read. The readers are now in all three ceilings; they only page results the
role already received. Coordinator list reads additionally return a first page
the model reads inline (see `get_project_workers` and project message
directories), so the reader is the fallback for other oversized results
(`get_conversation`, `get_project_assignment`), not the normal path.

Control supports `continue`, `checkpoint_resume`, `regenerate` and exact-attempt
`stop`. It validates the current authorized Coordinator request through the
existing delegation boundary, then reuses the conversation command service used
by the browser. Resumes retain the target's accepted model/config and identity;
they add no human message, answer, approval or enlarged tool grant. Dispatch
attempts retain their exact `TrustedDispatch` admission; an automatic Coordinator
continuation may control only its original request's dispatched Workers.
Ordinary session resumes retain their existing human-authorized execution.
Nonhuman notifications without an authorized request cannot issue controls,
with one exception: the Global Router acting under the owner's delegation
(owner decision 2026-11-06, [ROUTER.md R9](ROUTER.md#r9-the-owners-delegation-the-global-router-acts-for-the-owner-owner-decision-2026-11-06)).
When its request has no owner message of its own (a standing instruction, a
nonhuman notice), `control_conversation(owner_delegation={reason, trigger})`
checks the owner's grant in the lifecycle approval gate, resolves the owner
trigger, records one audit action before the command and settles it with the
outcome (a refused trigger is recorded too). The command is the unchanged
`control_session`: the delegation stands in only for the current request's
source principal (`acting_principal`), so every Attempt, revision, tenant and
replay check still applies and the resumed Attempt keeps the target's own
accepted execution identity. It allows only `continue`, `checkpoint_resume` and
`stop` of the pinned Attempt, in any project of the owner, never `regenerate`; a
dispatched Worker keeps its exact grant. Passing `owner_delegation` always uses
the grant; without it the owner's own message keeps the unchanged path. This is
how the Router resumes the exact Attempts a
restart interrupted (`tests/conversation/test_coordinator_session_control.py`
covers it on SQL and native storage after boot recovery settled them).

Callers pin the source Attempt, Turn revision and idempotency key. A retry uses
the same command identity and stored source config; conflicts require a fresh
status read, never a silently selected successor. Stop targets only the named
current Attempt and uses the ordinary Stop/withdrawal owner; a terminal Attempt
is a no-op so replay cannot withdraw newer work. Resuming an earlier Turn has the
same later-history removal semantics as the browser command. A lost mutation ACK
is reported as uncertain, not as proof that nothing started. Read-only sessions
cannot be mutated. The tool call and ordinary command receipts retain provenance.

Alternatives rejected: generating a new user message would change the meaning of
Continue; starting a private executor would split lifecycle authority; granting
an arbitrary synthetic user the owner's identity would bypass dispatch grants.
A Coordinator's next instruction to an ended Worker is the separate `follow_up`
action ("Continuing an ended Worker session" below), never a resume.
Session settings, new messages, human confirmations and deletion remain separate
commands. Verification: `tests/project_mod/test_coordinator_session_control.py`
and `tests/conversation/test_coordinator_session_control.py`.

The browser's own Continue, checkpoint resume, regenerate and guidance answer
follow the same rule for a Worker Turn. When the Turn's current attempt was
dispatched, the conversation command service resumes it through that attempt's
`TrustedDispatch` admission (same task identity, grant fence and assignment
association). When the grant can no longer authorize a resume, the command
refuses with `worker_binding_refused` and an explanation, before anything is
written. Problem: on 2026-11-06 a browser Continue on a Worker conversation
started an ordinary chat attempt in the API host. It had another task identity
and no grant, and its result never reached the Coordinator. Alternative
rejected: refusing every browser Continue on Worker conversations would take
the owner's direct recovery control away for no gain; the binding is the same
authority the Coordinator uses. Turns the owner typed into a Worker
conversation keep their ordinary execution. Verification:
`tests/conversation/test_worker_ui_continue_binding.py`.

A successor Attempt of a Worker Turn resolves its grant through one owner,
`admission.turn_dispatch`. The public attempt command performs the same lookup
before capturing configuration, so a browser resume keeps the assignment's
principal and account. An invalid grant raises `worker_binding_refused` before
acceptance; it never falls back to an unbound owner task. The real-start suite
also verifies that refusal leaves the current attempt and recorded usage intact.
Synthetic callers keep their supplied principal and must already match the
explicit grant; they cannot borrow this owner-originated resume authority.
Problem (2026-11-07 10:45, worker-80e6d733, assignment 6ddab2df): a browser
Continue that ran unbound (before the browser path bound Worker Turns) became
the Turn's current attempt. Both `control_conversation` and the browser read the grant only from the
selected attempt's config, so the Coordinator's continue started, but also
unbound. It ran under the owner's principal with no ledger, and the assignment
kept naming its failed attempt. Decision: when the selected attempt carries no
grant, the dispatch birth's `project-dispatch:<assignment>:output` presentation
locates the assignment. Its grant applies only when the association names this
exact Turn of this recipient conversation; the successor then advances the
association from the attempt it names, and `bind_account` accepts the unbound
attempt as the settled predecessor. A Turn without that presentation reads
nothing more. Alternatives rejected:
- Adopting the unbound attempt's result: its effects ran outside the grant and
  were never recorded, and its checkout may be another one.
- Refusing Continue on such Turns: the lane can then only be re-delegated.
- The latest assignment of the conversation without the exact Turn match: a Turn
  the owner typed into a Worker conversation would be captured by the grant.
Verification:
`tests/conversation/test_worker_attempt_real_start.py::test_a_continue_after_an_unbound_owner_attempt_runs_under_the_assignment`
(Coordinator and owner) and `::test_an_owner_continue_of_a_failed_worker_turn_runs_under_the_assignment`.

#### Continuing an ended Worker session (follow_up)

Problem: one Worker session per goal is faster and cheaper (owner direction
2026-11-08: "adding an elephant could always be discussed within a single
session"), yet a Coordinator could only regenerate an ended Worker Turn or
delegate a new Worker that rediscovered the context. Nothing created a new Turn
in a Worker conversation under its grant, and a new Turn's attempt could not bind
the assignment's account: `bind_account` recognised only the storage-issued
`_resumeSource` of an attempt in the same Turn and refused the rest with "Worker
tool reservations cannot be replenished".

Decision: `control_conversation(action=follow_up, instruction=...)` pins the
Worker's latest settled Turn, its Attempt and its projectionRevision, like every
session control. The instruction becomes that conversation's next Turn: a
`virtual_user` input stamped by the Coordinator (never a human message), and the
ended Turn keeps its attempt, revision and result.
- An unreviewed result whose delivery receipt is not `delivered` continues its own
  assignment (`ProjectDispatchService.follow_up`). The input attaches right after
  the pinned Turn (`requireParentIsLaneTail`), and `TrustedDispatch(follows=...)`
  advances the association only from the exact association the Coordinator read.
  Grant, checkout and account carry over: the accepted config carries the
  predecessor as `_projectDispatchFollowUp`, which `bind_account` checks against
  the settled attempt before it continues the ledgers. The result is reviewed with
  `review_project_work` as usual. As for every in-place resume, the follow-up's start
  reopens the held receipt for its own attempt and its settlement captures the checkout
  ("Delivery follows the attempt that completes" in
  [project integration](modules/project_integration.md)), so the accepted checkpoint
  carries the earlier and the follow-up edits.
- A review is immutable and a `delivered` receipt never reopens (its checkout may
  already be reclaimed). Such a result continues as a new assignment of the current
  request in the same conversation, through the ordinary delegation with the
  conversation reused, with a fresh checkout of the current branch. Its identity is
  the pinned association, so a retry replays it and another instruction for the same
  result is refused; an accepted result whose delivery has not landed is refused
  until it lands.

A replay with identical arguments reports the accepted Turn and starts nothing; once
the session moved on, an older pin is refused. Human messages and steers in the
Worker conversation keep their ordinary paths: a queued human input supersedes the
follow-up, and a running Worker takes context through `send_project_message`, not
`follow_up`. Workers gain no authority. Automatic continuations follow up only
their original request's Workers (`worker_control`), and the owner's delegation
(Router R9) never follows up.

Reuse or split: reuse the session for follow-ups of the same goal, including fixes
the Coordinator would otherwise request with `decision=rework` (follow up before
reviewing). Split into a new Worker for independent parallel work, an unrelated
goal, or a session that keeps failing or whose context no longer helps.

Alternatives rejected:
- Regenerating the Turn discards the result and its context.
- A project message that wakes an idle Worker would make the passive mailbox an
  execution scheduler.
- A new assignment for every follow-up moves the checkout and the account on each
  step and loses undelivered work.
- Reopening a reviewed assignment would make reviews mutable.

Verification: `tests/conversation/test_worker_attempt_real_start.py::test_a_follow_up_continues_an_ended_worker_session_as_its_next_turn`
(through review and a committed delivery of both attempts' edits),
`::test_a_follow_up_after_a_final_result_continues_the_session_as_a_linked_assignment` and
`::test_a_follow_up_is_refused_before_anything_starts_when_the_session_cannot_continue`
(SQL and native), and the follow-up specifications in
`tests/project_mod/test_coordinator_session_control.py` and `test_coordinator_workers.py`.

### Fresh Coordinator backend guarantee

Problem: selecting a historical chat imports unrelated conversation context, and
revision-derived candidate IDs could cause creation to adopt a pre-existing chat.
Decision: `/create` at the current binding revision creates a new ordinary empty
conversation with a fresh identity and only canonical project/folder settings,
then CAS-binds it. It never scans or copies historical chats, transcripts or
settings. A pre-existing identity or failed create fails closed, never becoming
proof of ownership of the candidate. Creation starts no execution.

An explicit current-revision create can replace an already available Coordinator
without deleting or altering the old conversation. GET is read-only. Existing
valid bindings remain usable on restart; stale create retries return the current
available binding without allocating another chat. Stale unavailable bindings
conflict. `/bind` now only clears a binding or reaffirms its current available
ID; selecting another existing chat returns 400. Clearing uses revision CAS.
Existing clients offering historical selection must use explicit creation instead.

Alternatives rejected: automatic current/latest-chat binding contaminates context;
checking that a historical chat is empty still adopts user-owned history; predictable
candidate reuse can adopt an orphan that gained content. Creation and binding
remain separate storage commands: each attempted create allocates at most one
empty conversation, and a failed binding CAS can leave that chat unbound. Retries
never adopt it or delete user data; concurrent requests cannot replace a newer
binding because CAS retains authority. No background loop or cleanup worker is
added. Narrow guards: `tests/project_mod/test_project_coordination.py` and
`tests/api/test_api_v1_project_coordination.py`.

The demand-loaded workspace uses the project's native dialog and shared tabs:
overview, team, messages, files/delivery and work management. Overview separates
failed work, active work and results. Review/dependency/delivery state stays
on the task row as Coordinator-owned status, never as a human to-do count.
Completion alone never means delivered.
Team cards open the ordinary conversation canvas, including conversations with

Temporary child interaction remains in the existing Swarm/agent surfaces.

read on return without remounting forms or message pagination. Only one workspace
read runs at a time; events during that read coalesce into one follow-up. Unchanged

read is shown as unavailable, not an empty project. The shared graph projection

Alternatives rejected: a second supervisor engine duplicates cancellation and

## Passive project conversation messages

Problem: `_peerNoWake` guards only some legacy queue drains; restoring its sender
can trigger paid work and default synthetic input to human attribution.
Decision: portable record CAS stores passive originals and consideration without
a dispatchable queue source, resident worker, polling thread or automatic wake.
The existing natural root round acquires optional input after complete tool pairs.
Alternative rejected: heartbeat-only guards cannot protect startup/completion drains.

Durable history. Problem: one record per original owner/project/recipient held
at most 128 originals for its lifetime and rewrote the whole list on every
receipt, so a months-long Project or Global Router exhausts its mailbox.
Decision: `ProjectMailbox` keeps append-only segmented history on the same
generic record CAS (key layout: `history` in `contracts/project_messages_v1.json`).
The head holds only the open segment (at most `messagesPerSegment` = 128, the
old per-record bound) and the sealed count. Each append first claims its
message locator, which is also the history-wide idempotency check, and commits
with one head CAS; an append that finds the open segment full first seals it
(segment copy with per-sender links, sender pointers, pending index). Position
= segment × 128 + slot never changes, so `before_id` stays a stable cursor;
sealed receipts CAS their segment record and keep per-message revision CAS. A
legacy single record is read as open segment 0 and sealed by its next append;
nothing is copied away or deleted first. Acquisition reads sealed pending
originals through the pending index and skips departed senders without reading
their segments.
Alternatives rejected: raising the cap (still a lifetime ceiling, larger
rewrites); archiving or evicting considered originals (durable user evidence);
writing every locator while sealing (measured 1.9 s, up to 21 s under host
load, on each 129th send); `record.list` sender/pending indexes (SQL prefix
lists are unindexed `LIKE` scans of the whole namespace); a new two-authority
storage operation (one head CAS already commits each append atomically).

`reference/consult/report/question/assign/steer` classify context, not execution
grants. Explicit accepted/rejected/deferred/conflict decisions use message revision
CAS, independently of input confirmation. Accepted is a stated commitment, not
executor birth or delivery. Causal replies must identify an actual incoming
message from the addressed sender. Queries never read private transcripts.

Owned current metadata is checked before send/acquisition, at logical-call
admission, and at the canonical prepared-input physical-attempt boundary. This is not a persistent conversation
project-generation fence: returning to the original project can make retained
originals eligible again. Different-project mailboxes never inherit those records.
Restored witness carriers are validated even when fresh acquisition fails; child
bootstrap removes previous-run mailbox carriers from its copied checkpoint, not
from durable evidence. The exact same mailbox/run retains confirmed carrier
context during recovery, subject to live dispatch validation. Conversation-mode
children retain parent context text but strip its mailbox receipt authority.
Unknown/mismatched authority fails before dispatch; a new authorized turn remains
the execution owner.

Sender validation has one owner, `project_messages.validate_sender`, shared by
acquisition and logical/physical input admission. Problem: acquisition admitted
the owner's currently bound Router Watchdog across projects, but dispatch
reapplied only the ordinary same-project rule and rejected its messages before
the model call. Decision: all three boundaries use the same live sender rule;
only the current available Watchdog binding grants the existing cross-project
exception. Recipient ownership/project identity and durable-original checks
remain mandatory. Alternatives rejected: trusting injection-time eligibility
would miss revocation while waiting to send; allowing every cross-project
sender would widen authority. Tests cover all three provider protocols, binding
replacement/unavailability, foreign owners, recipient rebinding and storage
read failures, plus delivery through real storage authorities.

## Input receipts and recovery limits

Exact carrier text is matched only in input-bearing fields. A request-local
observer composes with the existing model-budget attempt lease, and revalidates
scope against sealed translated input after dispatcher waits and before provider
ingress, including floor resends. This adds no second budget/dispatch owner.
Tool descriptions, routing and metadata cannot prove consumption. Only matches
from the selected verified response become eligible for ACK; failed/dropped input
cannot inherit previous IDs. Unobserved custom transports produce no physical
receipt. This does not independently prove serialized-wire identity after every
possible downstream adaptation. Credential recovery, when present, must wrap
per-attempt receipt validation, never the reverse. Local delivery failures retain
the original cause, not a provider fallback; the shared-runtime composition
specification executes only where those owners are present.

Validation is not atomic with the network send: a revocation immediately after
checking can race ingress. Relay/proxy-internal retries need their own enforcement
and are not claimed here. A scope-denied floor resend records already-known paid
usage as non-authoring discarded rounds; it cannot trigger another route or ACK.

Receipt ACK loss remains unknown: no persisted successful-request pending-ACK
outbox exists. No new paid request is purchased to reconcile a receipt. The exact
turn/attempt/task occurrence is recorded where available. Neither input confirmation,
consideration, task completion nor canonical delivery implies the other facts.

## Conversation execution identity boundary

Problem: carrying only a tenant and reconstructing every principal as a user can
silently turn a future system dispatch into an attended human executor.
Decision: `contracts/conversation_execution_identity_v1.json` defines a private,
server-stamped envelope in the existing accepted-attempt config. Public create,
resume and plan-execution config cannot supply identity, attendance or task
scopes. Authenticated subject/owner/tenant are retained; task scopes stay empty
rather than inheriting API scopes as durable tool grants. The executor validates
the envelope before context construction or registration, including recovery.
Present malformed, wrong-owner, wrong-tenant and nonhuman generic envelopes fail closed.
Alternative rejected: `_attended=False` alone is neither provenance nor a grant.

This remains **not automatic dispatch**. Generic system principals are rejected;
the separate private `_projectDispatchAdmission` carrier is admitted only through
validated internal `TrustedDispatch`, never public config or agent text.
Only absent legacy envelopes retain the existing explicit-owner user path;
explicit nonhuman/false-attendance markers cannot take that fallback. Existing
numeric-owner internal Goal continuations retain their existing semantics; this
boundary does not retroactively certify them as new project grants. No new loop,
thread or resident worker is added. Guard:
`tests/conversation/test_execution_identity.py`.

## Explicit-human bounded dispatch

The dispatch schema owns request, grant, assignment, admission, physical-attempt
ledger and review/view DTOs. An owning human with `chat` scope explicitly submits
a coordinator human turn and exact projection revision, distinct same-project
recipient, brief, model, token/request caps and Unix-second deadline. Admission
rechecks owner/tenant, canonical project, available coordinator binding, current
source revision/human provenance and grant revision/revocation. Synthetic input
is not authorization. The recipient is a system/chat principal, unattended and

brain-attributed; the ordinary user identity contract is not relaxed.

New grants pin the original positive coordinator binding revision. Every birth,
physical admission, dependency-evidence and publication gate checks that epoch;
A→B→A rebinding cannot restore old authority. Idempotent replay retains its old
pin. Legacy unpinned grants remain readable but cannot acquire fresh paid/file
admission or be upgraded in place; a new explicit human command is required.
Finite responsibilities also freeze their original binding epoch before triggers.

A scoped idempotent command maps to one assignment and the existing deterministic
conversation command, then an immutable turn/attempt association; task identity
and result status come from that attempt. Binding precedes executor birth.

Problem: the delegation binds (or, for a restart-paused continuation, advances)
the association only after its create/resume command returns. Under slow storage
the accepted-attempt recovery scan claimed such an attempt first and started it
unbound, so the executor refused it as not matching its "immutable birth
association"; the delegation's own claim then lost and the attempt stayed failed.
Decision: an attempt started by that recovery performs the same idempotent bind
or exact continuation from its accepted config's server-captured carrier, under
its exclusive start claim and before birth. A successor reserved only by its own
start claim (`@dispatching:<attemptId>[:<owner>]`) is unbound evidence for that
continuation; any other task binding still refuses. A refusal settles the attempt
with that cause. Alternatives rejected: a longer recovery grace (a tuned delay that
only moves the race), skipping unbound dispatch attempts (strands them pending),
and binding before the claim (a refusal could then neither settle nor stop retrying).
Guards: `test_recovery_scan_between_birth_commit_and_bind_starts_under_the_grant_association`
and `test_continuation_accepts_a_successor_reserved_only_by_its_own_start_claim`.

### Restart-paused Worker continuation

Problem: startup recovery skipped every assignment that already had an execution
association, while a background-completion wake created an ordinary, unbound turn.
The assignment therefore stayed `interrupted` on the old attempt, and its result,
delivery and Coordinator wake never arrived.

Decision: a restart-paused assignment resumes automatically through the existing
startup recovery pass and the ordinary Continue command, in its own conversation,
under the same grant. Each assignment that the pass leaves unresumed is logged
with its reason: a warning when a restart-paused lane's grant was revoked or its
deadline passed, info for an in-scope lane that had run (a coordinator profile
or a grant without the durable-Stop lifecycle), debug for plain filters and
settled executions. One `skipped` counter used to hide all of these (after the

said why). Verification: `tests/project_mod/test_project_dispatch_recovery_reasons.py`. A new assignment records one deterministic workspace task
identity (`project-worker:<assignmentId>`) in accepted config and its association;
an older assignment without that field inherits its interrupted attempt's actual
workspace task. Every physical attempt works under that identity (its work id),
so the existing isolated checkout, its uncommitted bytes,
checkpoint lineage and delivery receipt continue instead of being recreated.
Its task event stream likewise continues after the predecessor's durable cursor
([Task event delivery](TASK_EVENT_DELIVERY.md#reused-task-identities-continue-their-durable-stream)),
and the resumed attempt, as its Turn's current bound Attempt, takes over the task
result recovery left `interrupted` while the predecessor stays fenced
([Storage](STORAGE.md#restart-readiness-and-recovery)).

Coordinator wakes continue the same way. Problem: continuation treated a
restart-interrupted Coordinator wake as settled and, once its backoff ran out,
minted a new wake whose brief made the Coordinator re-read every Worker; after
the 2026-11-08 restart both Coordinators lost their interrupted round this way.
Decision: `continuation._proposal` hands a restart-paused previous wake back as
`existing`, so `dispatch_authorized` continues it in place through the same
restart continuation (`project-dispatch-resume:<assignment>:<attempt>`) under
its grant. A restart-paused human request Turn that has no wake yet proposes
`resume_source`, and `recover_coordinator` continues that Turn in place through
the ordinary resume command of the restart resume pass
([Run continuity](RUN_CONTINUITY.md#restart-paused-conversations-resume-by-themselves)),
idempotent with that pass. A request Turn continued in place (by either, or by
the owner's Continue) owns follow-through until its current Attempt settles:
previously its interrupted original Attempt counted as settled, so a wake could
race the continued Attempt. Once the continued Turn settles, Worker results wake
the request as before. Alternatives rejected: keeping the fresh wake and adding
the interrupted round to its brief (a second resume path that still re-reads the
Workers); leaving the request Turn to the restart resume pass alone (it depends
on quiesce records the stopping generation writes, which the restart deploying
this change does not). Verification:
`tests/project_mod/test_coordinator_continuation.py::test_a_restart_paused_coordinator_wake_continues_in_place_instead_of_a_new_wake`,
`::test_a_restart_paused_human_request_continues_in_place_instead_of_a_new_wake`
and `::test_a_request_turn_the_owner_continued_owns_follow_through_until_it_settles`.

Durable-worker attempts. Problem: `turn.attempt.dispatch_worker` binds every
Attempt to its own task `conversation-attempt:<attemptId>`, while task
registration adopted the accepted config's workspace task id as the physical
id. The two never match, so after the durable admission cutover every
Coordinator continuation and Worker failed at registration (`prepared task
identity differs from conversation worker`), and no failed or restart-paused
Worker could continue. Decision: the physical task and the work id are separate
identities. A worker claim alone names the physical task, which owns the task
result, event stream and Turn binding of that one attempt; only an unclaimed

`taskId`: `bind_account` stamps it on every physical attempt
(`workspace_delivery.workspace_work_id`). The checkout registration, binding,
delivery settlement, publication, review, shared-file candidates and the

as its single root. A successor therefore binds the predecessor's checkout and
resumes the model, tool and reservation sequences instead of colliding with
them. That holds whether the predecessor was interrupted by a restart or failed
before entry. The workspace origin records the physical attempt in it as
`executorTaskId`, and delivery recovery reads that attempt's verdict while
settling the work id. Alternatives rejected:
- Keeping the work id as the physical task: storage fences worker writes by the

- Executing project dispatch in the API process again: this reverses the durable

- Refusing such successors: no Worker could continue after any failure or

- Re-keying the checkout to each new task: this needs a storage handoff

ordinary wake. Alternatives rejected: Regenerate discards the Worker's transcript
and checkpoint; classifying refusals by retry count or error text adds a knob and
still re-issues the refused command; a fresh queued turn has no exact
predecessor/successor association. Specs:
`tests/project_mod/test_coordinator_workers.py::test_worker_execution_without_continue_settles_its_background_batch_once`
and `::test_background_batch_issues_its_continue_once`.

`blocked: task_background_commands_running` means that durable publication was
captured while the Worker's background commands were still running; it is not a
successful delivery and does not prove those commands survived the old server.
Startup command recovery publishes finished results or an explicit died-with-server
result. The collective completion resumes the same assignment and clears the hold
through the existing delivery retry/settlement owner once its exact task and
background work are no longer running. There is no storage rewrite, new poller,
fresh delegated Worker or replacement worktree. Alternatives rejected: a new
Worker rebuilt from the old transcript loses execution context and can put two
Workers on one checkout; binding only a later turn by conversation ID lets an
unrelated turn steal the assignment; clearing `blocked` at boot can publish an
unfinished checkpoint.

Problem: a completion that arrived after `cancel_project_work` still fell through
to the ordinary collective wake, creating a tool-capable turn whose result was not
linked to the cancelled assignment. The same wake could already be leased when the
grant was withdrawn.

Decision: the existing background-batch owner checks the frozen assignment binding
before either Continue or the collective wake turn. When its exact grant is revoked
and its bound Turn and Attempt have settled, it attaches the complete durable command
receipts as one deterministic `_bgCommandInjects` evidence block on that cancelled
Turn and starts no wake. No model attempt, replacement Worker or new evidence store
is created, and no still-running command is killed. Replay of the same block is
idempotent, and a wake row stored by an earlier release is retired without a turn.
A revoked grant whose execution is still settling, lacks evidence, or loses the
projection race also starts no model turn; its durable receipts remain available
for a later evidence-settlement pass. Because those receipts stay queued, every
maintenance tick re-evaluates them: its decisions read Turn metadata only, and
the Worker Turn's projection is read only to attach the block or to observe it
once at a new `projectionRevision`; while that revision stands, the process
remembers the attached block instead of rereading a multi-megabyte projection
per tick (2.4% of the execution host's GIL samples on 2026-11-08). Exact assignment reads expose the evidence
through the bound result. A human entering
the Worker conversation still uses the ordinary human-authorized command path;
this is not a user Stop and never reports an authority refusal as one.

Alternatives rejected: killing background commands at cancellation discards
useful finished evidence and adds a second command-lifecycle owner; relying only
on `TrustedDispatch.checked()` raises a revocation error that the legacy ordinary
wake path would otherwise bypass; deleting the completion queue rows would lose
evidence; appending a settled user Turn would fabricate human/model activity and
leave the assignment unbound. Ordinary non-Worker completions retain their
existing collective model wake, and restart-paused assignments continue through
the same Continue path described above.

Problem: a Worker turn that ran without its assignment binding (started by an
older wake path, or by human input in the Worker conversation) leaves receipts
with no binding. Their completions took the ordinary collective wake after
cancellation, and each wake turn's own receipts were unbound again, so the Worker
conversation kept working. Cancellation reached only the attempt named by the
execution association, which can be long settled while such a turn runs.

Decision: a Worker conversation (created with `_coordinatorSource`) is governed by
its assignment. A background batch whose receipts carry no binding resolves the
conversation's latest recipient admission through its canonical project
(`recovery.worker_conversation_admission`) and follows the revoked-grant settlement
above; a live grant keeps the existing wake. Revocation through
`cancel_project_work` or the assignment revoke API stops the associated attempt and
every other live attempt in the Worker conversation, with the same
`dispatch_grant_revoked` cause and provenance. A Coordinator continuation grant
names the Coordinator conversation as its recipient, so its turns are never swept.
Human input in a cancelled Worker conversation still runs on the ordinary command
path; its command results also settle as durable evidence instead of waking a
model turn.

Alternatives rejected: recording a durable conversation Stop for the Worker
reports an authority withdrawal as a user Stop and still admits wakes requested
after it; refusing every unbound automatic turn in Worker conversations would also
block steering and human takeover of live Workers; rebinding an unbound wake into
a trusted Continue fails on the stale association and would retroactively give
that chain the assignment's authority.

The existing command/start handshake owns execution, lane-idle admission and
queued-human priority. Busy/superseded dispatch is deferred. After the existing
human/background queues drain, the lane-settlement callback retries the same grant;
startup discovers persisted owner/project records through existing cursor pagination.
Only new `lifecycleVersion=1` grants auto-retry; legacy evidence remains readable,
not automatically upgraded. Exact-command retry cannot buy a second execution.

`ExecutionBudget` remains reservation/settlement authority. Its physical-attempt
observer persists `dispatch_intent/settled/voided`, root/attempt task IDs, ordinal,
reserved/reported tokens, usage completeness and an account nonce. Retries share
the grant caps. Unresolved intent, incomplete paid usage or former-task usage
blocks new spending; restart/account recreation does not replenish authority.
Every settlement must retain its nonce and occurrence identity; even an unsent
settlement cannot void durable uncertain intent. Live authority is revalidated
before physical admission; this is not atomic network revocation or provider
exactly-once. Consultation still exposes no tools. An explicit `files` profile
names only first-party `read_files/write_file/edit_file`, relative read/write
prefixes and a tool cap. Write prefixes must permit preimage reads; `.` is an
explicit whole-project prefix, never a directory scan or metadata exemption.
Tool admission and nonce-bound durable occurrences conserve the same authority.
Shell, recursive indexes, PTC, MCP, remote/ref adapters, plugins, children and
paid auxiliary translation stay closed. `autoTranslate` is forced false.
Auxiliary compaction summaries charge the grant's own bound account under its
recorded ceilings ([CONTEXT_COMPACTION.md](CONTEXT_COMPACTION.md#auxiliary-summaries-under-dispatch-grants)).
Batch admission judges only calls that can execute: a call already rejected by
parse or its contract returns that rejection, and a file-scope argument-shape
refusal (for example `read_files` with both `path` and `reads`) is a contract
rejection of that call only; authority refusals still fail the turn. Decision:
`docs/contracts/TURN_SETTLEMENT.md`; specification:
`test_project_dispatch_tool_contract_rejection.py`.

Problem: a tool name/path string alone can borrow a plugin, alias or canonical
checkout. Decision: pin the exact first-party handler, bind the physical task's
registered isolated workspace, and use anchored directory descriptors, no-follow
regular-file I/O, byte-exact preimages, durable undo and cooperative target leases.
Ordinary tasks default to direct execution, but dispatched file workers always
retain isolation, including with `TOFU_WORKSPACE_MODE=direct` or local
`tofu.workspaceMode=direct`; those settings cannot bypass review/publication.
Recheck live authority and workspace ownership at I/O/publication. Reads consume
complete UTF-8 text; writes and exact preimage capture have no private byte quota.
Every explicit read/edit batch entry is admitted by its path/tool grant, not a
20/30-entry ceiling. Explicit human call allowances remain authoritative.
Runtime, Git, credential and cache paths are refused even under `.`. Alternatives
rejected: opaque programs and generic converters cannot be safely path-fenced.
This is not an OS sandbox against privileged external reparenting after the final
ancestry check; those writers remain outside cooperative containment.

Revocation uses grant-revision CAS and cancels the bound existing attempt; a
repeat retries the same cancellation after ACK loss. Human Stop remains the
existing turn/attempt cancellation authority, not natural-language steering.
Neither late reports nor read/recovery reactivate stopped or revoked work.
Review requires the current completed result revision and records immutable
`accept/rework/reject` evidence; it does not change task completion or grant
revision. `reworkOf` links the exact old grant/result and immutable rework review;
execution requires a fresh human source, command, model and budget, not renewed
old authority. Stop entry points durably withdraw existing referenced grants;
TTL expiry, late reports and boot/idle retry cannot restore withdrawn authority.

Stop also stores one monotonic owner/conversation watermark in the declared
`stopNamespace`, independent of current project metadata. Admission checks two
point reads; this prevents restoring an old project from restoring authority.
Human attempt/queued/task/registry-miss Stop paths record it; exact-grant internal
cancellation does not withdraw peer grants. Storage failure is not a durable-Stop ACK.

Problem: a Stop signals the executor first, then revokes each referenced grant
through the shared project CAS. A revocation that lost its bounded CAS to concurrent
dispatch writers failed the whole Stop: the person saw an unconfirmed Stop for a
signalled task, and no later pass revoked the grant record. Decision: the
acknowledged watermark is the withdrawal, because admission and every live executor
fence refuse each grant created before it. Only `DispatchContention` after that ACK
(bounded CAS attempts ended in conflicts or uncertain ACKs) is absorbed: the Stop
receipt reports `dispatchWithdrawal: pending_revocation` instead of `complete`, the
remaining revocations stop at the first contention, and lane-settlement or startup
recovery revokes, from the same durable watermark, an unstarted grant it would
otherwise retry. Admission already fences every other referenced grant, including a
started executor's; a repeated Stop also revokes its record. An
unacknowledged watermark, or any other storage, integrity or metadata failure, still
fails the Stop; the executor stays signalled and its idle projection is still
published, and repeating the same Stop is idempotent. Alternatives rejected:
catching every revocation failure (hides storage and configuration faults), retrying
beyond the CAS budget or adding a revocation queue or poller (unbounded work), and
writing the watermark before the executor signal (delays every Stop behind dispatch
storage). Specifications: `tests/project_mod/test_project_dispatch_recovery.py`.

Problem: automatic completed-file delivery would precede review. Decision: stamp
the assignment admission into initial workspace registration and hold all
initial/no-change/recovery/postgate publication paths. Acceptance remains review
only. Explicit `/publish` pins grant, result and `expectedCheckpointSha`; existing
Git gates and `origin.delivery` own publication. Final fresh checks run under the
same repository lock used by grant revocation, before intent and apply/fast-forward.
Changing the checkpoint cannot reuse an old publish request. No new delivery store
or worker is introduced. `canonicalDelivery=true` derives only from the exact
owner/project/task-matching durable `delivered` receipt with commit evidence
(`delivery.canonical_delivery`), not completion, acceptance, candidate `merged` or a
publish request; an uncommitted working-tree publication projects as `pending` or
`blocked` (`delivered_uncommitted`).
Alternatives rejected: acceptance-as-publication and UI-only fencing lose authority.

### Dispatch storage waits

Problem: a transient storage `deadline_elapsed` while validating a grant or
recording a physical occurrence stopped a healthy Worker as
`dispatch_authority_lost`, even when the authority recovered moments later.
Decision: live dispatch validation and its model/tool occurrence observers use
the shared `lib/tasks_pkg/persistence_wait.py` lifecycle. Typed transient storage
failures wait with the existing backoff and liveness witness, without an
agent-attempt ceiling. Only the read or idempotent occurrence mutation repeats;
no model request, tool effect, grant or execution account is recreated.
Repository contention errors retain the final storage cause, so their bounded
CAS loop cannot erase the distinction between transient pressure and a permanent
refusal. Malformed config is refused before a workspace ownership lookup.
Validation rereads live authority on recovery, and new intents revalidate after
their durable ACK before allowing effects. Stop cancels admission waits; already
observed model/tool settlement continues to ACK after Stop. Shutdown retains the
existing persistence-debt failure behavior. Permanent integrity/permission
failures and real revocations still fail closed with their original causes.
An uncertain ACK reuses the exact occurrence; an existing identical finite-grant
intent consumes no second allowance.

Alternatives rejected: ignoring a failed authority check could execute without
authorization; retrying the whole turn could repeat paid or external effects;
another retry count/deadline would kill work during longer storage outages.
Specifications: `tests/project_mod/test_project_dispatch_persistence.py`,
`tests/storage/test_project_dispatch_persistence.py` and the existing dispatch
runtime, occurrence accounting and stop-cause contracts.

### Dispatch contention is not an authority verdict

Problem: every dispatch write commits through one head per owner/project: each
Worker and Coordinator model or tool occurrence, reservation, delegation,
binding, review and revocation. Every segmented snapshot read is fenced by the
same head. A write retries its CAS `casAttempts` times back to back and then
raises `DispatchContention`; a read raises it when the head advanced under each
snapshot. The storage waits above classified only transient storage codes. So a
Worker whose own model settlement lost to concurrent writers (a Coordinator
burst, or the herd a storage stall releases at once) stopped as
`dispatch_authority_lost`. The same verdict failed a Worker's tool intent as a
tool error, ended a Coordinator request as `ModelAdmissionRefused`, and reached
the Coordinator as `get_project_workers` "retry reading".

Decision: contention proves only that another writer committed.
`repository.transient_dispatch_failure` classifies it by the nearest dispatch
verdict in the cause chain: `DispatchContention` is transient, and every other
`ProjectDispatchError` (revocation, a changed source or binding, malformed
evidence) is final. Without one, the transient storage codes decide.
`admission.wait_for_dispatch` runs the persistence wait with that classifier.
Sites that never had a persistence fence use `admission.reread_on_contention`:
the first attempt runs as before, so an uncontended call keeps its existing
Stop handling, and only a transient failure enters the wait. Together they
cover every dispatch call site that runs inside a task:
- Worker validation (`validated_dispatch`), its account read and reservation
  counter, and its model, tool and reservation occurrences;
- the Coordinator request account (`bind_source_account`): source read, account
  registration, dispatch admission, occurrences and tool reservations;
- the Coordinator reads `get_project_workers`, `get_project_assignment`, the
  polls and snapshots of `await_project_workers`, and the pre-dispatch read of
  `dispatch_project_assignment`;
- `delegate_project_work`, whose documented recovery is to replay unchanged
  arguments.
Each repeat reads and validates the live grant again. A revocation or Stop that
committed meanwhile is met on the next read and stops at once with its own
cause.

Bound: the persistence-wait liveness contract, not a count: ACK, owner Stop
(reads and intents) or server shutdown (settlement debt returns to the recovery
owner). Its existing backoff spreads a herd's retries, and every CAS round has
a winner, so a burst drains. No retry count, interval or timeout was added.

Alternatives rejected:
- raising `casAttempts` or adding jitter: a tuned knob, and a longer burst still
  kills;
- per-assignment heads or head-free ledger commits: they remove most contention
  structurally, but change the storage contract implemented by the SQL and
  native authorities, so they are a separate proposal;
- re-running a whole `await_project_workers`: it would lose a settled Worker's
  progress result.

Specifications: `tests/project_mod/test_project_dispatch_contention.py`. It
races Coordinator delegations and foreign commits against a Worker's model and
tool occurrences, tears authority snapshots, revokes and Stops during
contention, and covers the Coordinator request account, delegation and read
tools. The Coordinator write tools are covered by the next section. Not
covered: the dispatch itself of `dispatch_project_assignment` still returns
contention as an uncertain outcome with its existing recovery. A contended
`wake_project_dependents` is still retained for the next settlement or startup
recovery.

### Coordinator write tools read through dispatch contention

Problem: the same head CAS the reads race also serializes every Coordinator
write. At 16:15 CST on 2026-11-06, with about 17 Workers live,
`review_project_work` returned
`{"error": "Concurrent/uncertain dispatch update; read before retrying"}` and
the review was lost until the Coordinator replayed it by hand. The review's CAS
callback re-reads the Worker's full Turn projection on every attempt, so a
multi-megabyte result makes each of the bounded attempts slow enough to lose
again. `cancel_project_work`, `finish_project_request` and
`request_user_decision` share the same path.

Decision: `execute_coordinator_tool` runs these four commands through
`reread_on_contention`, exactly like delegation. The first attempt runs as
before; only contention enters the persistence wait, bounded by its existing
liveness contract (ACK, owner Stop, server shutdown). Each repeat re-validates
live authority and re-takes the publication lock, so a contended call never
holds that lock while it waits. Replay is unchanged: an identical review,
cancel, finish receipt or pending decision is a durable no-op (the decision
keeps its first due time), and a different one is still refused as immutable.
A real verdict met on the re-read — a revoked grant, a changed binding, an
already settled request — still refuses at once. `consider_project_message`
and `send_project_message` are unchanged: they commit through the per-recipient
mailbox CAS, never the dispatch head, so this contention cannot reach them.

Alternatives rejected: waiting inside the publication lock (a contended review
would block publication), returning the contention to the caller with recovery
text (the Coordinator must then replay by hand, and the first attempt already
proved the command is idempotent), and shortening the review's evidence read
(useful, but a separate optimization, not an authority fix; it now reads Turn
metadata, see the compact receipts below).

Specifications: `tests/project_mod/test_project_dispatch_contention.py`
(review/cancel/finish/decision races, replay, a revocation committed during
contention) on in-memory storage. Not covered: these tools racing the real
head on SQLite and PostgreSQL. There the head race is specified for a Worker's
writes only
(`tests/storage/test_project_dispatch_persistence.py::test_racing_head_commits_never_stop_a_segmented_worker`).

### Compact review and cancel receipts (2026-11-08)

Problem: `review_project_work` and `cancel_project_work` returned the whole
Coordinator view: the request (brief, granted tools, delegation policy) and the
Worker's complete Turn projection. In the 2026-11-08 Coordinator conversation
(first 145 of 315 messages) 51 reviews and 18 cancels returned 1.3 MB (review
median, max 12 MB) and 3.1 MB (cancel median, max 9.5 MB) of JSON; the model saw
a 12,000-character prefix, about 3.2-3.8k tokens of brief and tool names that
never reached the decision or delivery, or only "Tool returned a structured
result." when the JSON stayed under 1 MB. Each call also materialized the
projection and persisted it as a multi-megabyte artifact.

Decision: both tools return a compact effect receipt: `assignment_id`,
`decision` (`accept`/`reject`/`rework`, or `cancelled`), `grant_revision`,
`revoked`, `result_revision`, `execution_status`, `checkpoint_sha`, `delivery`,
`canonical_delivery` and `next_step`. The service answers from the
settlement-only view, and the review's ownership pre-check and its revision
check read Turn metadata, so neither command materializes the projection.
Evidence stays with `get_project_assignment` and `get_conversation`. Measured on
two real calls of that conversation (receipt rebuilt from their recorded
delivery state, same token counter): an accepted review with a checkpoint went
from 3,469 to 365 visible tokens (its 7.2 MB result no longer read or stored), a
cancel from 3,473 to 155 (3.8 MB). `tests/project_mod/test_coordinator_receipts.py`
pins the shape and the metadata-only reads.

Alternatives rejected: keeping the full view and relying on the artifact readers
(every review still writes a multi-megabyte artifact and needs a second call to
reach its own outcome), trimming the view but keeping its evidence shape (the
request alone is 3-25k characters and is not an effect), and returning only an
acknowledgement (the Coordinator would need `get_project_assignment` again for
the revisions a rework or dependency pin copies and for the delivery state).

### A repeated Stop of an ended attempt does not withdraw later work

Problem: `abort_attempt` withdrew the whole conversation's dispatch even when
the attempt had already settled. A human Stop of an ended turn therefore planted
a NEW watermark dated at the retry, revoking every earlier grant in that
conversation — including grants created after the original Stop. The 11/06
`dispatch_grant_revoked` investigation of assignment 4143b9a2 did not come from
this path: that grant was revoked by its own Coordinator's
`cancel_project_work` at 07:49:59 CST (turn acd247ee, attempt 32ac97a5), so the
background-delivery verdict was correct. But the mechanism remains a real
authority hazard, and `control_session`'s stop branch already refuses it.

Decision: the withdrawal is dated at the attempt's settlement (`settledAt`,
falling back to `createdAt`, else epoch 0), never at the retry. The original
withdrawal is still retired — the watermark record keeps the maximum timestamp
and the revocation pass still runs — but it never moves forward to withdraw
grants created after the human's Stop. Live attempts are unchanged: their Stop
is dated now, before the executor is signalled.

Alternatives rejected: skipping the withdrawal entirely on a terminal retry
(would strand the original pending revocation, contradicting the recovery
contract that a repeated Stop retires it), and using the attempt's `createdAt`
only (a long-running attempt would misdate its own Stop).

Specifications: `tests/project_mod/test_project_dispatch_recovery.py`
(`test_stop_of_an_ended_attempt_never_withdraws_later_work`,
`test_terminal_attempt_stop_reuses_the_original_watermark`, and the existing
Stop-watermark suites).

### Delegated Workers and outside-workspace writes (proposal, not implemented)

Problem: on 2026-11-06 three delegated project Workers set
`allow_outside_workspace=true` and registered a new workspace root (`tofu_2`),
and a fourth did so on `interview-materials` after a refusal. The flag's
contract requires the USER's explicit confirmation of the exact destination.
A delegated Worker's input is delegated context, so it cannot carry that
confirmation: the Worker cannot distinguish "the human said write here" from
"the Coordinator's brief says write here". Today nothing in the write path
knows the caller is a delegated Worker, so the flag is accepted verbatim.

Decision (proposed, awaiting owner approval; no code changed): a delegated
Worker (a task whose config carries `_projectDispatchAdmission`, including a
Coordinator continuation and its swarm children) may not use
`allow_outside_workspace=true` to register a new workspace root. The write is
refused with an instructive error naming the boundary: write inside the
registered isolated workspace, use `/tmp` for scratch (which stays exempt), or
have the owner write there directly. Detection uses the existing admission
carrier in the task config at the write-path owner
(`lib/project_mod/write_tools/_paths.py`), reached through the same
`tool_admission_scope` the file-scope admission already uses, so it covers
write_file/edit_file/apply_diff/insert and the MCP local-path adapter without
changing the file-grant scoped path, which never consults the flag. The tool
schema description stays truthful for humans; the refusal names why the flag
cannot apply to this caller.

Alternatives considered:
- Record an owner confirmation in the Worker's grant and accept the flag only
  when the grant names the exact destination. Rejected for now: the only owner
  delegation grant that exists (`lib/lifecycle_approval.DELEGATION_SCOPES`)
  covers restart/conversation_control, and docs/ROUTER.md R9 requires a new
  owner decision to add an operation; the router-grant lane also notes that a
  tool-level human confirmation is a different boundary, and the grantee there
  is the owner's Router, never Workers. This remains the right shape if the
  owner later wants a per-destination approval flow, and would then be an
  explicit new grant kind with the destination path in its scope, not a flag.
- Refuse only the root registration but still write the file. Rejected: the
  write is the side effect the confirmation exists for; the root is merely how
  the workspace records it.
- Do nothing and rely on the briefs. Rejected: it already happened four times.

### One dispatch head per owner and project (measurement and proposal)

Problem: every dispatch write commits against one CAS head per owner and
project (`ProjectDispatchRepository._change` committing through
`SegmentedDispatch.commit`), including every Worker's
model and tool records, reservations, delegations, bindings, reviews and
revocations. Since the contention fix (live 14:54 CST 2026-11-06) losers wait
instead of dying, so with about 20 Workers the head serializes the project.

Measurement (2026-11-06, an ad-hoc count of the `[AgentPersistence]` wait and
completion lines and the contention verdicts in `logs/app.log*`; the script is
not part of the repository): before the fix
there were 15 authority stops by contention and 16 'read before retrying'
verdicts. After the fix: 30 contended Worker model-occurrence calls (median
2.2 s, p90 8.2 s, max 70 s), 19 tool occurrences (median 2.9 s), 17 tool
reservations (median 1.8 s), and 10 Coordinator delegations whose waits
dominated: median 517 s, p90 608 s, max 739 s, about 72 minutes of Coordinator
wall time over 1 h 40 m. The delegation path re-reads a whole cohort per
attempt, so a busy head tears almost every snapshot; the Worker's own
single-assignment writes are two orders of magnitude shorter.

Proposal (report only; not implemented): keep one head for cross-assignment
invariants, but stop making every per-assignment ledger write depend on it.
Concretely, an occurrence/reservation commit for one assignment would commit
against that assignment's own document version (and, where a new document is
created, an assignment-scoped sequence) instead of the project head, while the
project head still fences multi-document reads, delegation, review, revocation
and migration. Invariants that must hold on every backend (TofuDB, SQLite,
Postgres): (a) a multi-document read's snapshot witness still covers every row
it reads, so per-assignment writes must advance some witness the reader checks;
(b) revocation and review still linearize with the assignment's own document,
so a contended per-assignment write can never resurrect a revoked grant;
(c) the head's `nextSequence`, counts and allowance indexes stay exact, which
is the part that forces either an assignment-scoped sequence or a head write
on document creation; (d) the SQL and native authorities implement the same
commit contract, so this is a storage-contract change, not only a repository
one. Because (c) and (d) span owners and both storage backends, this stays a
proposal until that contract is agreed; the contention fix above removes the
kills in the meantime.

### Dispatch authority stop causes

Problem: a dispatched task halts through the abort lane when its grant is revoked
or its authority can no longer be re-established (`validate_task`, the model,
tool and reservation observers, `admit_tool`, summary admission, or the
grant-withdrawal cancel port). Every such stop settled `interrupted/user_abort`,
so the Worker Turn, its activity row and `await_project_workers` presented it as
if the person had pressed Stop, and the Coordinator reported phantom Stops.

Decision: the site where the authority fails names the cause together with the
cooperative abort, before any further provider or tool call.
`admission.stop_on_authority_failure` stamps `_abort_reason`:
`dispatch_grant_revoked` when a `DispatchGrantRevoked` caused the failure (a
revoked grant, or one withdrawn by a durable Stop in the Coordinator or
recipient conversation), otherwise `dispatch_authority_lost` (lost carrier,
changed task identity, execution association or registered workspace, or an
unreadable grant record). `validate_task` applies it to every refusal, the
model usage observer to revocation races and unacknowledged usage writes,
`admit_tool` to authority it cannot re-establish (still raising
`ToolAdmissionRefused`), and summary admission to unknown continuation
authority. `abort_project_attempt` passes `dispatch_grant_revoked` to the exact
attempt cancellation: `TaskRuntime.abort_owned` stamps it under its lock only
when it is the task's first stop, and an attempt without a live executor
settles with it directly. Every stop also carries its provenance as
`_abortReasonDetail`, appended to the settled error detail: the cancel port's
caller names the actor (`cancel_project_work` names the Coordinator
conversation, task and assignment; the revoke API names the principal; a scope
change names its change), and an authority check names its refusal, which
includes the assignment and the Coordinator or Stopped conversation. A Worker's
failed Turn is therefore traceable to the Coordinator decision that ended it
without searching logs. The Turn records `failed`, `evidence:
external_authority`, the cause and a non-retryable envelope of the same kind
(`docs/contracts/TURN_SETTLEMENT.md`); the request activity row reports `failed`
with that `errorKind`. Whole-turn auto-retry never applies: the task is stopped
and `should_auto_retry_turn` refuses the envelope; the failed Turn keeps its
ordinary manual resume options. The first cause wins: a person's Stop keeps `interrupted/user_abort`, a task already
stopped is never restamped, and the port arriving after a Stop renames nothing.

Alternatives rejected: settling every abort-lane exit of a dispatch task as
failed (a person's Stop of a Worker would read as an authority failure);
reusing `tool_call_rejected` or `internal_fence_abort` (the first names one
call's refusal, the second a storage fence with a retryable envelope); returning
the refusal as a model-visible tool result (the Worker would continue past the
authority check); automatic retry (the same grant refuses again, so the recovery
is a new delegation). Remaining gap: a finite grant's exhausted model allowance
is a policy refusal, not lost authority; it still halts through the plain abort
lane and reads as a user Stop until it has its own typed cause. Specifications:
`tests/project_mod/test_project_dispatch_abort_cause.py`,
`tests/turn_lifecycle/test_dispatch_authority_settlement.py` and the dispatch
cases of `tests/turn_lifecycle/test_turn_verdict.py`.

### One live validation per admission

Problem: every tool call of a dispatched task crosses `scope.admit_tool`, which
validated the grant inside `validate_task` (the identity restore), reread the same
assignment row for its execution association, then validated the grant again for
its profile; the executor's file-handler selection repeated validate-then-reread.
One validation loads the dispatch snapshot, checks the admission schema, reads both
Stop watermarks, both conversations, the binding and the human source Turn with its
projection; Worker and Coordinator grants also read the delegation source Turn,
attempt and request budget. A 2026-10-28 stall dump caught an agent thread inside
this path. Decision: `admission.validated_dispatch` returns the binding together
with the row its single validation returned, and the execution check, the
admission profile and `is_file_dispatch_task` decide from that row. A Worker or
Coordinator grant's request budget is checked against the same snapshot when it
holds that row (`validate_source(..., value=...)`; its authority fields are
immutable and its accounts append-only), so one validation loads and
schema-validates the budget document once instead of twice. The association
is immutable once bound and binding precedes executor birth; request and profile
are immutable through `mutate`; so a reread or second validation of the same state
returns the same row. The row serves only that admission (a tool batch shares it
with its calls' gates; see the next section): descriptor I/O, the tool and model
intent fences, the next admission and publication each validate live again. A
change committed between the former first and second validation was
refused by the second; it is now refused by the next live fence before any effect,
the same outcome as a change committed just after the former second validation.
Alternatives rejected: retaining validated rows or verdicts across admissions or
requests (owner decision: a revocation, Stop, rebinding or source change must reach
the next admission without an invalidation protocol), and dropping the I/O or
intent rechecks (they fence effects, not admission).
`benchmarks/project_dispatch_admission_reads.py` admits one live file grant on a
disposable SQL Sidecar (conversations, binding and human source Turn are in-memory
ports there). An admission made 14 storage RPCs before and 6 after: two validations
and one reread became one validation. Fresh-process ABBA medians of 200 admissions
were 11.49/11.55 ms before and 5.27/5.24 ms after; beside four CPU-bound Python
threads they were 2,481/2,253 ms before and 769/1,023 ms after, with admission-thread
CPU of 17.5 instead of 7.4 ms. These are host observations of one component.
`test_project_dispatch_executor_admission.py` pins the outcome and stop cause of
ten authority faults in every mode (the former admission passed the same table),
and that one decision reads exactly one validation's ports plus the bound executor,
with a row equal to a fresh validation and reread.

### One live validation per tool-batch admission

Problem: 2026-11-07/08 `[RoundPrepTiming]` records charged project Workers p50
904 ms and p90 1.8 s of `build_body.tool_metadata` per round (ordinary chats p50
54 ms): `coordinator_scope` validated the Worker's grant and validated it again
through `current_continuation` on every round to learn a role the grant fixes for
its lifetime. Tool calls repeated the pattern: incident phase records show
`dispatch_authority` eight times per call in 257 of 313 slow tool calls (417 s).
Batch admission, the pipeline and executor role checks, the executor admission,
the file-handler selection, both tool-intent checks and each nested handler
scope validated live, each reading the dispatch record, three Stop watermarks,
the binding twice, both conversations, both source Turns, the delegation attempt,
the bound executor and the registered checkout. Both intent checks ran under the
ExecutionBudget lock, so they serialized the concurrent calls of one batch.

Decision: validate once per admission and keep one live fence per effect.

- Request building reads no dispatch storage. `bind_account` pins the role of
  the grant it validated (`_projectDispatchRole`: that carrier and, for a
  Coordinator continuation, the scope from immutable request/grant fields);
  `coordinator_scope` returns it after checking the carrier is unchanged (a
  lost carrier still stops the task). Live authority stays where effects are
  admitted: every model request's dispatch intent (validation, intent CAS with
  its revocation check, validation) and tool admission below. A revocation
  between rounds is refused by the next round's model dispatch intent, before
  any provider sees the request, with the same stop cause as before.
- A tool batch is one admission. `_admit_dispatch_tool_calls` validates once
  (`admission.admit_dispatch` → `DispatchAdmission`), decides every call from it
  and hands it to its calls' executors (`_execute_tool_one(dispatch_admission=)`).
  `admitted_call` makes it the call scope, so the executor admission, the
  file-handler selection, the intent's pre-check and every nested `tool_scope`
  decide from it: `validated_dispatch(admission=)` reruns only the in-memory
  carrier, identity, execution and account fences, and the admission resolves
  the registered checkout at most once. A caller without a batch (streaming
  prefetch, a direct executor call) validates once per call and shares it the
  same way. An admission is never stored on a task or used by another batch.
- Each call's tool intent remains its effect fence. The intent CAS refuses a
  revoked or revised grant against the authoritative row it writes (exact
  invalidation keyed to the grant revision, as model intents already do), and
  one live validation follows the durable intent before the handler runs, at
  the same point as the former second intent check. A refusal there settles the
  intent `not_entered`. Descriptor I/O, model intents and every later batch
  still validate live.

The effect fence cannot share the batch's validation: the verdict depends on
evidence the dispatch record does not own. A Coordinator Stop whose grant
revocation lost its CAS is witnessed only by its Stop watermark; the binding
epoch, the source Turns, both conversations, the bound executor's attempt and
the registered checkout have their own owners. No authoritative revision covers
them together, so sharing up to the effect would need a TTL or count (excluded)
or a storage-contract change that makes each owner advance one witness, and a
call waiting behind an ordered sibling would start after an acknowledged
withdrawal. The intent CAS invalidates exactly what the record owns at no extra
read; the rest is read once, at the latest point before the effect.

Read counts on the injected storage fakes (`record` covers the dispatch record
and Stop watermarks; every port read counted): request building per round, a
Worker 23 → 0 and a Coordinator continuation 33 → 0; one tool batch of one
`read_files` call 143 → 29 reads, of three calls 429 → 59 (one validation per
batch and per call, plus one checkout read per batch; ledger writes unchanged at
two per call); one streamed (prefetched) project read 51 → 14. Each saved
validation is about thirteen reads, and the intent holds the ExecutionBudget
lock for one validation instead of two.

Alternatives rejected: a TTL or round/batch verdict cache (a revocation, Stop,
rebinding or source change must reach the next admission; owner decision above);
keying a shared verdict on the dispatch head or assignment revision alone (blind
to the evidence listed above); dropping the intent's live validation (it fences
the effect); keeping the pre-intent validation instead of the post-intent one
(a change committed during the intent CAS would no longer be refused); a
process-local revocation signal (the API and execution hosts do not share it).
Specification: `tests/project_mod/test_project_dispatch_admission_once.py`
(zero reads and unchanged role decisions per round; a removed carrier stops
request building; revocation between rounds; exact batch and prefetch reads; and for a
revoked, durably stopped, rebound, source-changed, settled, superseded,
workspace-discarded or carrier-less grant both refusal at the next batch
admission and refusal before any handler when committed after a batch's
admission, with the former per-gate revalidation's stop cause; these decision
specifications pass unchanged on the former code).

### Stored-row schema verdicts and metadata Turn reads

Problem: a live py-spy GIL profile of the server spent 20.8% of all samples in
jsonschema `is_valid`, mostly `_check_record` re-walking every stored assignment,
request-budget and Coordinator-settlement row on each dispatch load: per Worker
round (`coordinator_scope` → `validate_task`), tool admission, Coordinator timed
wake and settlement recovery. Separately, `delegation.source_for_task` (every
Coordinator model dispatch), `delegation.validate_source`, the background-completion
resume fence in `message_queue.dispatch_completed_background_batch`, the resume
model-switch probe `command_service._resume_model_switch_from` and
`validate_publication` read whole Turns (tens of MB live) for identity, actor,
parent and `projectionRevision` only.

Decision: schema validity is a pure function of (definition, exact JSON value).
`repository._validate_stored_row` keeps, per definition and stored row identity
(assignment `id`, request budget `id`, settlement `sourceAttemptId`, the repository
key for a legacy whole record), the SHA-256 of the canonical JSON (sorted keys,
compact, unescaped UTF-8, finite) that last passed a full walk. An equal digest skips
the walk; other content is walked in full, and only a completed validation records
its digest, so a race can repeat a validation but never skip changed content. A
value that differs from its decoded canonical JSON (a tuple or a non-string key
encodes like a list or string key but validates differently) is always walked.
Retention is one digest per row identity the process has checked, replaced on
change, with no size, age or flag; mutation checks reuse it for their unchanged
rows. Caller-supplied request, batch, source, admission and Stop
validation, the derived admission projection, the finite JSON checks and every
ownership, occurrence, budget, graph, Stop, binding and source check still run on
every read: the memo states only that exact stored content is well-formed and
caches no row or authority. The listed Turn reads use
`include_projection=False`, the same public metadata normalization as the
prerequisite-evidence decision; `validate_human_source` and the resume probe's
parent `contextSnapshot` keep their body reads. A malformed metadata record now
fails closed as a permanent storage error instead of an identity mismatch.

Alternatives rejected: skipping stored-row validation loses integrity; caching rows
or admission verdicts (owner decision above); an LRU or TTL bound adds a tuning
knob where an absent entry only costs one walk; plain `hashlib` releases the GIL per
row above 2 KiB, so digests use `sha256_holding_gil`.
`benchmarks/project_dispatch_record_validation.py` checks 100 delegated Worker rows
(20 model and 20 tool occurrences each, one shared request budget and settlement,
1.38 MB). Fresh-process ABBA medians of 21 checks were 582.6/577.6 ms before and
77.3/81.1 ms after with unchanged rows, and 611.5/581.3 ms before and 83.8/86.8 ms
after when one more row had advanced. Beside four CPU-bound Python threads they were
3,132/3,225 ms before and 389/369 ms after (checking-thread CPU 633/662 and 84/80
ms). The remainder is mostly each assignment's profile and admission-projection
walks. These are host observations of one component with identical snapshot digests.
Specifications: `test_project_dispatch_record_validation.py` (unchanged rows skip
the walk; changed, invalid, tuple-valued and other-definition rows are walked),
`test_coordinator_workers.py` (source and background-completion reads),
`test_project_dispatch_dependencies.py::test_publication_validation_reads_the_result_turn_as_metadata`
and `test_turn_lifecycle.py::test_resume_model_switch_reads_the_submitted_turn_as_metadata`.

Profile validation follows the same rule (2026-11-08). `scope.validate_profile` runs on
every tool admission, admission projection and dispatch ledger write (`profile_for`) and
for every assignment on every load; its repeated schema walk was about 5% of the
execution host's GIL samples on 2026-11-08. The walk and its path/tool checks are a
pure function of the JSON value, so the process keeps the digest of each exact profile
content it proved valid (`_VALID_PROFILE_DIGESTS`, canonical JSON, the stored-row
exactness rule) and returns a fresh decoded copy for equal content. Any other content,
including a caller's not seen before, is walked, and content that fails is never
remembered; retention is one digest per distinct valid profile, with no size, age or
flag. Same benchmark, fresh-process ABAB medians: 82.2/82.1 -> 45.0/45.2 ms with
unchanged rows and 88.1/88.0 -> 50.5/50.4 ms with one advanced row; one 36-tool project
profile 490-512 -> 16 microseconds per call. Specification:
`test_project_dispatch_scope.py::test_profile_content_walks_its_schema_once_and_invalid_content_never_passes`.

## Atomic bounded conversation batches

Problem: individually approved fan-out can persist half a plan after a failed
last admission and has no immutable original goal or aggregate allowance.
Decision: `ProjectDispatchRepository.authorize_batch` commits one manifest and
all ordinary child grants in the existing owner/project CAS. The machine
contract adds `batchRequest`, `batchRetry`, `batch` and `batchView`; manifests
share the segmented project-head CAS. A batch names 1..8
**existing distinct conversations**, the original objective, one genuine human
source, exact worker briefs/models/profiles and finite aggregate tokens/model
requests/deadline. Child ceilings are allocated before any execution; their sums
cannot exceed the aggregate, and deadlines cannot outlive it. Unused allowances
never transfer or renew. The common binding epoch and immutable manifest/member
requests are checked on every record read. Each child receives the original
objective and its responsibility in its existing bounded immutable brief.

Exact command replay returns the original manifest even after revocation,
expiry or rebinding; it does not restore execution authority. Changed objective,
worker order, budget, source or granter conflicts. Admission is atomic;
**physical launches are not**. The service submits independent asynchronous
ordinary conversation commands without a threadpool or waiting for results.
Human-queued/busy lanes defer. A failed or lost launch reply is `unknown` with
`dispatch_unconfirmed`, not definite rejection or successful completion; exact
turn/attempt evidence remains independently inspectable. Existing lane-idle and
startup drivers recover eligible child grants, never mint replacement grants.
Each child retains Stop, live budget, scope, review and publication gates.

Public v4 routes: POST `/project/coordination/batches` authorizes and dispatches
with `Idempotency-Key`; GET the same path with exact `path` and `commandId`
reads `{batch: ... | null}` without wake/write/spending; POST `/batches/dispatch`
retries only `{projectPath, batchId}`. A null read cannot prove no in-flight
write. All batch endpoints require the owning human principal with `chat` scope.
The current-request delegation tool above has a separate internal admission port.

Batch admission alone is not a complete autonomous supervisory loop. Current-request
delegation/review and result-driven continuation reuse ordinary Coordinator Turns
under the original policy; standing renewal is not implied. Evolution's private goal spokesperson remains separate;
its journal assignments do not authorize project work. Alternatives rejected:
serial grant writes lose all-or-none authorization; a new persistent scheduler
splits lifecycle authority; batch acceptance-as-success erases partial starts.
Focused guards: `test_project_dispatch_batches.py`,
`test_project_dispatch_batch_service.py`, `test_project_dispatch_batch_routes.py`.
No provider, deployment or multi-day autonomy proof is implied by these tests.

## Version-pinned result dependencies

Problem: prose references cannot fence stale results, revocation or Stop. Decision:
up to eight distinct predecessor assignments pin exact grant/completed-result
revisions; file predecessors also pin checkpoint SHA. Edges are immutable and
backward within the same owner/project/tenant record; corrupt, dangling or cyclic
graphs fail integrity checks. Consultation requires accepted review; files also
require the matching actual delivery. Waiting review/delivery, invalid evidence
and unknown evidence are separate read facts, not task/ProjectWorkItem states.
Present owner fields must be exact positive integers, not equality-compatible
booleans/floats. Unrecognized tool-ledger phases remain uncertain; only the
schema-owned terminal phase vocabulary proves tool settlement for readiness
or publication.
Waiting and GET create no executor or spending. Direct/transitive dependencies
are checked at existing birth, model/tool and publication gates; historical
predecessor spending expiry does not erase accepted evidence. Changed evidence
never silently replaces pins, rewrites downstream results or replays effects.
The drawer clears consent on selection changes and compares every pin on ACK
reconciliation. Older responses without states remain unknown. Durable accepted-review/exact-delivery ACK triggers a bounded best-effort wake
of direct/transitive dependents across lanes, outside publication/repository locks.
It is a hint: existing birth gates recheck pins, Stop, deadline and human priority.
Lost hints use ordinary retry/lane-idle/startup; no queue or grant is added. Validation is not atomic with network
send or arbitrary external writers. Alternatives rejected: a mutable forward DAG
adds another scheduler; candidate merge cannot prove delivery; automatic rework
repeats side effects. Owner: `lib/project_dispatch/dependencies.py`; enforcement:
`repository.validate`; spec: `test_project_dispatch_dependencies.py`.

Problem: readiness evaluation read the complete Worker Turn of every reachable
prerequisite, a projection that grows to megabytes, on each history refresh of a
dependent row and at dispatch, birth, model/tool and publication gates. The
predicate uses only that Turn's identity, actor and `projectionRevision`.
Decision: `dependencies._evidence` reads it with `include_projection=False`. Both
authorities build that metadata with the full read's public normalization (SQL
`_turn_public_metadata`, native `metadata_read` with `public_turn`;
`test_turn_metadata_read.py` asserts equality without the projection), so verdicts
over well-formed Turns are identical. A record that the metadata reader rejects as
malformed becomes `unknown/evidence_unavailable` instead of
`invalid/result_changed`; neither state is ready. Attempt, review, Stop, binding,
scope, delivery and publication evidence stay live. The human source Turn keeps its
body read because `require_human_turn` inspects its projection. Alternatives
rejected: caching prerequisite verdicts, which needs invalidation across attempts,
Stops and bindings; and a new revision-only storage operation, since the existing
metadata read already carries identity, revision, status and settlement. Measured
with `benchmarks/project_assignment_page_reads.py --dependencies` (16 of 32 rows pin
an accepted 2 MiB prerequisite, SQLite): a warm page build returns 151,613 instead
of 67,566,883 storage bytes, because 16 prerequisite body reads become metadata
reads (244 RPCs in both trees). Guards: `test_project_dispatch_dependencies.py`
counts zero prerequisite body reads through grant, view and dispatch, and replays a
12-case verdict matrix against the former body read;
`test_project_dispatch_history.py::test_dependency_states_read_prerequisite_turns_as_metadata`
repeats the count and verdict over real Turns.

## Accepted checkpoint publication recovery

Publication authority for a `project` Worker is the source Coordinator's
`review_project_work` accept with `checkpoint_sha`, inside a grant derived from
a genuine human Coordinator Turn. The integration receiver re-checks it on every
tick (`resume_pending_workspace_deliveries` retries `blocked` rows), so a
transient hold such as "accepted before review" self-heals once the pin exists.

Problem (result drift): a completed Worker Turn can gain later projection
revisions after review, e.g. a late background-command completion. The pin
requires `turn.projectionRevision == publication.resultRevision`, so it failed
permanently, the failure was reported as `project_publication_authority_missing`,
and review immutability left no recovery. Decision: the repository raises
`PublicationResultChanged`, delivery reports `project_publication_result_changed`,
and the Coordinator may re-affirm an existing accept at a newer current result
revision for the identical pinned checkpoint. Decision, checkpoint, grant and
all other review/publication fields stay immutable; no new authority is created.
Alternatives rejected: tolerating any later revision (late output may report
failures the reviewer never saw), and requiring a new repair assignment (re-runs
work whose bytes are already accepted). Spec:
`tests/project_mod/test_coordinator_publication_recovery.py`.

Problem (stale hold): the receiver evaluates held rows serially, so a hold
written before the pin kept reading `project_publication_authority_missing`,
and `await_project_workers(wait_for=delivery)` returned at once as held, for as
long as the receiver was busy elsewhere (2026-11-06: 7509d68d behind another
project's multi-hour checkpoint capture). The underlying refusal was logged at
DEBUG only. Decision: under the publication lock, after `validate_publication`,
the service asks `release_publication_hold` to rerun the same live fence for
that exact receipt; a cleared hold becomes `pending`, which views and waits
report as delivery in progress. The receiver still publishes and rechecks every
fence, and a failed release leaves the hold to its next pass. A fail-closed hold
names its hidden cause at WARNING once per process, and again whenever the cause
changes or the hold clears and returns. Keying on the reason code alone missed
holds already stored before a restart and a new cause under the same code. The
process keeps the last logged cause per held row, and a row drops out once its
check no longer fails closed. Alternatives rejected: reading the pin's time
against the receipt in the view (an unchanged later refusal never rewrites the
receipt, so it would read as pending forever); logging every retry (one line per
held row per pass); persisting the cause in the receipt (a new durable receipt
field and a write per cause change, only to deduplicate a log line). Specs:
`test_publication_pin_retires_the_stale_hold_without_publishing` and the pin
and cause cases in `test_coordinator_publication_recovery.py`.

Problem (duplicated content): overlapping Worker chains re-carry commits already
delivered under other SHAs. `git apply --3way` cannot merge a creation patch
onto an existing path ("does not match index"), so a byte-identical file already
published blocked the whole delta as `task_delta_conflict` with no conflict
paths. Decision: `task_delta_delivery` drops paths whose captured canonical entry
already equals the checkpoint entry and reports a creation over different bytes
as an explicit conflict path. Alternatives rejected: merge commits with real
ancestry (working-tree publication deliberately commits nothing, and the
duplicates have different SHAs anyway), and a scratch-worktree merge per
delivery (materializes a checkout, which this path avoids). Spec: the
duplicate/add-add cases in `test_workspace_first_delivery.py`.

## Scope withdrawal, finite responsibility and shared versions

Problem: steering text cannot withdraw paid authority or prove Stop. Decision:
`scope_changes.py` and `project_scope_change_v1.schema.json` require a genuine
human source and exact current grant pins. One dispatch-record CAS withdraws
scope under the existing publication lock; cancellation targets only existing
attempts, notifications are passive mailbox originals. Revocation, abort signal,
terminal Stop, submission, input confirmation and consideration remain separate.
GET is read-only; retry reconciles the same command. A project Stop can pin an
empty current set and fences earlier finite responsibilities for the same tenant
and coordinator. Later triggers disable those definitions without reserving tokens
or creating a child; a fresh explicit-human responsibility is separate. Current
cancellation confirmation does not attest automation disable ACK. Alternative
rejected: natural-language Stop or broad cancellation retains authority or affects unrelated work.

Problem: responsibility must not silently renew a grant. Decision:
`responsibilities.py` / `responsibilities_adapter.py` and
`project_responsibility_v1.schema.json` freeze the original authenticated human,
explicit mode/tool/path scope, finite run count, aggregate allowance and deadline.
Existing automation triggers own occurrences; each permanently reserves its full
per-run token ceiling before child authorization. Unknown ACK stays unknown,
fully debited; no refund, reset or rollover. Pause/cancel disables the definition;
cancel withdraws children, and live source/binding/Stop checks remain. Alternative
rejected: a second scheduler or refunds split authority or restore uncertain credit.

Problem: filenames/model labels cannot prove shared knowledge. Decision:
`shared_files.py` and `project_shared_files_v1.schema.json` index only declared
relative file/purpose/source/revision/digest metadata. Adoption requires exact
canonical delivery and matching immutable delivered-tree bytes; candidate is not
adopted. No scanner, transcript/vector index or prompt injection is added.
Content is exact-version, on-demand `untrusted_data`, never permission; consult
gets no file tools. Changed/missing/unsafe/unavailable/oversized observations stay
separate. Refresh keeps the old pin and may record a human-authorized replacement,
never substitutes bytes or writes a file. Alternative rejected: automatic
scan/adoption grows idle work and confuses evidence with authority.

## Bounds and cost

A project mailbox has no lifetime count. Per-message wire bounds are unchanged:
4096 characters / 16384 UTF-8 bytes plus a 2048-character consideration note.
One record holds at most one segment of 128 originals (2 MiB body content before
JSON/framing and notes), so an append or receipt rewrites at most one segment
whatever the history length. Considered originals are never evicted or archived;
pagination never reclaims anything.

The mailbox uses point reads and expected-version writes only; nothing lists or
scans history. An append reads the head and writes its locator claim and the
head. Sealing adds a read and write of the segment copy and the pending index
and of one pointer per distinct sender in the segment. Exact-ID lookup reads the
head, the locator and one segment; an incoming page reads at most two segments;
an outgoing page follows the sender's segment links, at most one segment per
returned original. Remaining limit: acquisition work and the pending index grow
with unconfirmed, unconsidered backlog (including originals from senders that
left the project and stay eligible for their return), never with history.

Measured on a disposable SQLite Sidecar under host load (load average about 15)
with 500-character originals from seven senders: at 128 and 1,280 originals an
append took one read and two writes (median 45 / 29 ms, p95 111 / 71 ms; the
difference is load noise). Each of the nine seals at 1,280 took 17 reads and 11
writes (75-214 ms); writing all locators while sealing took 145 writes (1.9 s).
At 1,280, exact lookup of the oldest original read three records, considering
it four reads and two writes, the first acquisition batch three reads and an
outgoing page three. Durable values are 731 / 724 bytes per original at 1,280 /
128 (the per-original JSON dominates) plus one locator key of about 110 bytes.
`tests/project_mod/test_project_message_history.py` (many segments, cursors,
outgoing pages, ACK loss, interrupted and racing seals, legacy records, threads,
isolation) and `tests/storage/test_project_message_history.py` (SQLite,
PostgreSQL and native authorities) are the executable specifications.

Each active configured project round performs scoped metadata and one head point
read, plus the pending index and the segments of eligible pending originals once
segments are sealed; never an owner-wide scan. A directory shows up to 20
previews of 256 characters, keeping the newest that reach the model inline, with
a stable-ID backward cursor across segments; exact-ID tool lookup retrieves the
original. Input selection defers whole messages using
token/headroom and escaped-byte budgets. Final canonical prompt admission still
owns total cost. Idle adds no executor.

Dispatch retains up to eight CAS retries, eight direct dependency references,
64 physical model requests and 512 tool occurrences per grant (or its lower
explicit caps). A dependency projection memoizes reachable predecessor evidence
and bounds one chain at 128 nodes / 1024 edges. No dependency work runs while idle.

`ProjectDispatchRepository` selects the persistence boundary in
`contracts/project_dispatch_storage_v2.json`. Problem: raising the 128/4 MiB ceiling retains
whole-history rewrites on every model receipt and eventually exhausts memory.
Decision: keep domain policy in the repository and provide an owned atomic
head CAS plus individually versioned assignment, request, account, occurrence,
batch, settlement, scope-change and index documents. Both authorities execute the same
transaction; native compilation reuses existing versioned-document IR. A late
child conflict rolls back the head, earlier children and command receipt.
Alternatives rejected: larger monolithic records; deleting settled evidence;
independent per-row writes that can split admission from reservation; a second
budget/task store; and a generic multi-record write API without domain ownership.

The port has no project-lifetime row limit or background activity. One commit
accepts at most 512 document changes and 8 MiB of document JSON; point documents
remain at most 4 MiB, head state 16 KiB, index summaries 2 KiB. A page returns
at most 64 index summaries or evidence headers, never a collection of large
evidence values. Cursors use exact owned ASCII prefixes and bytewise order.
SQLite uses its existing primary-key range; SQL schema 68 installs a private
PostgreSQL C-collation partial index through the explicit migration lifecycle.
Native uses its existing entity range. Generic record operations refuse both
private namespaces. Only reconstructible indexes support deletion.

`tests/storage/test_project_dispatch_segments.py` exercises real SQLite,
PostgreSQL and native authorities: more than 128 retained documents, bounded
history pages, exact receipt replay, late conflict rollback, two racing grants,
owner/project isolation, namespace bypass refusal and native full reopen.
`segmented.py` migrates only on mutation or lifecycle recovery. It first freezes
the original v1 record with its exact CAS; old pending writes conflict and old
readers reject the marker. Bounded copy transactions retain every grant, receipt,
batch and scope change. Queries use the frozen original until the complete copy
is committed. Only then is the redundant original removed and the head activated;
the small owner/project locator remains. Lost acknowledgements at every phase
resume without granting twice. No backend switch, new task or resident worker
is involved. Startup isolates a failed import to its scope.

Point reads, execution binding and ordinary receipt updates address exact
documents. Source and request indexes select only their cohort; immutable count
witnesses detect missing index entries before allowance reduction. Changes to
grants, source cardinality and request cardinality commit together under one
head witness. Reads retry a changed witness and perform no writes. The 512-change
transaction preserves atomic withdrawal of the existing 128-target scope limit.

Domain verification covers 160 retained assignments on all three authorities,
four cutover crash boundaries, exact legacy model/execution preservation,
concurrent first mutations, and missing-index refusal. Actual SQL conservation
tests include live source/Worker migration and 132 successive ordinary Worker
conversations under one request with unused allowance released. Provider/Turn
completion is controlled in this count test; it is not paid model throughput.

A disposable strict-native repository probe compared 32 and 1,024 retained
assignments. Twenty point-read plus receipt-update cycles at each size used six
queries per cycle, no history scan, and at most 1,324 / 1,330 command bytes.
With Python allocation tracing enabled, mean cycle times were 13.020 / 13.024 ms

## Complete scoped file work

Problem: file-only dispatch had independent 512 KiB reads, 16 MiB write/preimage
limits and 20/30-entry input ceilings after ordinary project tools stopped
using those quotas. Decision: descriptor-fenced first-party execution consumes
complete granted sources and every explicit operation. `FileScope.read` has an
unbounded default; an explicitly supplied read limit remains supported by its
caller. Regular-file checks, write hard-link rejection, ancestry/inode matching,
live grant/owner revalidation, lexical prefix membership, freshness and durable
undo remain separate authority requirements. No generic converter, shell,
plugin or trusted recovery authority is borrowed by a file grant.


Scoped read evidence binds the bytes actually returned by the descriptor to the
owned root identity. Explicit ranges beyond EOF fail before any batch observation
is published; an unranged read of an empty file remains valid. A failed later
read or source binding does not certify earlier, undisplayed batch items.

Scoped `edit_file` shares ordinary edits' compute-only matcher and accepts the
same batch-level `path` as the unscoped tool: an edit takes the batch file
unless it names its own, and every edit must still resolve to a file inside the
granted prefix or the call is refused before any I/O. It defaults to
whole-batch `atomic: true` preflight: all file reads, operations, freshness checks
and common journal admission complete before the first requested publication.
An invalid plan returns failed/skipped receipts in original request order,
without file or undo changes. Only an explicit boolean `atomic: false` enables
partial application. Descriptor-fenced I/O, exact grant revalidation and the
pending-recovery refusal remain mandatory. This is not cross-file rollback after
a later I/O failure; see [the write contract](PROJECT_FILE_UNDO.md).
Alternatives considered: larger constants repeat valid-work refusal; using
generic project fallback bypasses the descriptor and grant fence. The existing
caller-owned byte buffer remains proportional to the source; this does not
claim constant memory or grant additional tools/calls.
`test_project_dispatch_scope.py` verifies actual 32-file batches, a source over
512 KiB, 64 ordered edits with one exact undo transition, a 17 MiB post-image,
and a small append to a 17 MiB preimage with SHA-256 undo checks. Revocation,
symlink/reparent, hard-link, pending recovery and publication-failure neighbors
remain required.

### Cross-process steer delivery (owner report 2026-11-06)

**Problem.** The personal deployment runs an API process (browser commands and
every Global Router reply they start) beside an execution process (channel
ingestion, relays, queue drains and project continuations); a Coordinator Turn
runs in whichever process started it. `lib.agent_inbox` is process-local, so
`route_to_project` reported `disposition="steered"` while its wakeup waited in
the wrong process's inbox. `await_project_workers` and the round-boundary
injector both read only that inbox, and the finalizer salvaged only it, so the
Coordinator kept waiting and never saw the owner's words.

Live evidence, `coordinator-1a390889aa954da2b18551d1b4a32625` Turn
`ef0c4900-ae96-492c-ae29-e37a33a92196` (execution process): the owner's decision
(`router-forward:a6355e6697a915186b913805e2008ad660eb565bd6dabcce0498bec45f000baf`,
Router Turn `00b4444e…`, 09:19:41) and bug report
(`router-forward:4e7a7198e140402fff4b7f2858d926bae6bde15e476301b495b4490189c60f0a`,
09:29:23) were accepted by API-process Router tasks `e40a9f26` / `71e57b88` and
stayed `pending` through the 09:05:46–09:32:12 await (1,586.6 s), across the
`ask_human` question `hg_bf52fce334c5` the decision had already answered. Two
other forwards in the same window arrived, because their Router tasks ran in the
execution process. The same happened to owner messages typed directly into the
Coordinator (`tmp_*` command ids). All ten items reached the model only at
10:24:26, when a later Coordinator Turn happened to start in the API process
(the compaction mentioned in the report was that Turn's first step). A second
defect shared the lane: a replayed forward (same command id) re-published the
inbox item, so owner text `router-forward:c5631617548708c3165ce65af7880…`
reached the model twice (11:09:24 round 2 and 11:15:10 round 4).

**Decision.** The pending steer record on the live Turn is the cross-process
delivery; the inbox item is the same-process fast path.

- Acceptance (`_deliver_while_running`) publishes a local wakeup only when this
  process's task registry executes the attempt. Otherwise it commits the steer
  record alone and logs the executing-process split.
- `lib.tasks_pkg.committed_steers` reads those records at the existing delivery
  points: the round-boundary injector (`take_steers`), the durable recheck of
  `await_project_workers`, and the finalizer. The finalizer re-queues an undelivered
  steer as the next turn through the same turn command. No new timer, cadence or
  knob: it rides the round boundary and the existing 0.5/5 s recheck.
- One owner-bound Turn metadata read per boundary/recheck; the body is read
  only after a foreign write (the executor's last written view answers the
  unchanged case). Delivery follows the record's commit order and a block is
  taken at most once, which also closes the replay double delivery.
- Await results add `waiting`: each pending input's kind (`human`, `nonhuman`,
  `background_command`, `project_message`), source (Global Router forward,
  channel, typed here, message id) and preview, bounded by the injection preview
  the records already store (1,200 characters).
- Authority is unchanged: an owner's message carries its committed `steerAuthor`
  (actor, text, origin) exactly like a same-process steer, and is verified again
  when it authorizes; a steer with no author was nonhuman and stays nonhuman,
  including when it is re-queued.

**Alternatives considered.** Queuing the steer instead (either unconditionally or
when the executor is not local) preserves full fidelity but the text arrives only
after the model chooses to end its turn — not the next round, and not guaranteed
at all; it also splits a forwarded request and its Router note into two turns.
A cross-process wake port is a new transport, plus a subscription owner, for no
benefit over records that already exist. Storing the full steered text on every
record changes the native TofuDB engine and the SQL authority together, outside a
small fix. Skipping the record read whenever the process role is `all` would
hide foreign steers in a multi-replica layout, so the read always happens and
its cheap path covers the common no-steer case.

**Residual limits.** A nonhuman text longer than the stored preview (the Router
note always exceeds it) reaches a cross-process executor as that preview plus an
explicit truncation note; the owner's own words arrive complete from their
author record. A steer committed after the finalizer's last read but before the
attempt closes can still miss the turn; closing that needs a settlement-side
hand-off and is not changed here. `pending` records left on already settled
Turns are display evidence, not a delivery queue, and stay `pending`.

**Verification.** `tests/conversation/test_conversation_command_inject_mode.py`
(typed, Router-forwarded and 大象 owner input for a remote executor; commit
order, exactly once, authority, full owner text, next-turn salvage; the cheap
read; the replayed forward), `tests/project_mod/test_coordinator_workers.py`
(cross-process steer ending an await on all three sources, naming its source and
arriving at the next boundary once; a project message naming its id). Nine specs
