# Project Coordinator and team workspace

Responsibility: explicit coordinator binding, passive same-project messages,
consideration receipts, optional model-input boundaries and explicit-human
consultation or bounded-file dispatch, linked rework and checkpoint-pinned publication. This describes the source contract in this
checkout, not deployment status: an isolated tested candidate does not prove
canonical integration or live backend loading.

Problem: importing the file-scope admission boundary for an ordinary project
tool eagerly initialized `jsonschema`, even when no dispatch grant existed.
Decision: `repository._validator` imports the schema engine on its first actual
validation, retaining the existing bounded validator cache and exact schema.
The ordinary admission path still checks for bound authority; actual profile
validation fails closed if its validator cannot load. Alternatives rejected:
prewarming taxes startup/idle, and bypassing file-scope admission would remove
live ownership and revocation checks. The fresh-process specification is
`test_project_dispatch_lazy_validation.py`; repository and file-scope tests
retain malformed-input, concurrent admission and revocation coverage.

The frozen repository-tool comparison
retains 1,060 exact-output workers using the prior source/Git path and this
change plus explicit Rust discovery, with identical native CSR ranking.
First-operation P50 ratios are 0.245–0.411 and CPU ratios 0.411–0.558 across
all five repository cases. This cumulative comparison does not isolate native
discovery. Two Python warm CPU pairs still fail, at 1.143 and 1.159; later
phase/processor diagnostics do not waive them. Native discovery remains
explicit, and inherited child RSS, other domains and full application/default
admission remain unresolved. The existing file-lifecycle fixture's missing
durable effect acknowledgement reproduces on the frozen reference as well.

## Interactive Coordinator and workers

Problem: executing work in the Coordinator or its temporary children hides the
independent worker conversations that users need to follow. Decision: the binding
selects an ordinary root Agent with a registered `project_coordinator` context
block and dispatch-only tool policy (`lib/tasks_pkg/coordinator_policy.py`).
It plans, delegates the current human request into independent workers, reviews
their results, exchanges project messages and reports to the human. File, shell,
browser, arbitrary program and Swarm/retained-agent execution are denied before
tool effects, including discovered tools and batch calls. Catalog filtering alone
is not authorization. Restrictions remain pinned through the selected turn;
provider-native multi-agent and programmatic execution stay disabled even when
old turn/checkpoint latches requested them.

`lib/conversations/coordinator_tools.py` adapts `create_conversation`,
`dispatch_project_assignment` and `get_project_assignment` to the existing
conversation repository and ProjectDispatchService. Creation retries use immutable
request/binding identity, tolerate normal retitles/settings edits and verify the
owner-scoped readback. Creating a chat never starts execution or grants permission.
`dispatch_project_assignment` consumes an existing grant. `delegate_project_work`
derives a grant from the current accepted human request as described below; model
text and worker reports never become human authorization. Workers use the ordinary command → turn/attempt → task path.
The Coordinator has no separate model loop, scheduler, task states or budget.
Binding starts no work; existing turn/continuation policies retain ownership.
Unbound, foreign, child and storage-free invocations receive no role. The narrative
cursor remains independent. Alternatives rejected: prompt-only restrictions can
be bypassed; temporary children remain in the parent conversation; another runtime
would duplicate admission, Stop, settlement and publication authority.

### Delegation within the current request

Problem: requiring the human to create and authorize every Worker defeats the
Coordinator entry point. Decision: `delegate_project_work` creates an ordinary
conversation in the Coordinator's folder and admits a `project` worker through
the existing dispatch repository and command service. The frozen capability
ceiling comes from ordinary tool assembly before the Coordinator-only filter.
Worker input includes the original request (explicitly marked excerpt above
12,000 characters, with source Turn/conversation links) and the delegated brief;
custom system-prompt settings are preserved. Context never enlarges the grant.
The live owner, tenant, binding epoch, physical assistant Turn/Attempt and its
canonical human parent must agree. Execution principals with no reusable API
scopes are supported without manufacturing a human principal. Arbitrary synthetic
inputs, Plan/read-only requests, stale attempts and durable Stop cannot delegate.
Only an internal continuation grant may reuse the exact original request policy.
Public grant APIs cannot supply this internal policy. Legacy consult/file grants
keep their narrower behavior. Worker calls use ordinary tool resolution and
registered isolated Git workspaces; recursive agents, timers, schedules and
arbitrary tool programs are excluded. This profile is intended for local Git
projects; non-Git/remote workspace support is not yet established.

`await_project_workers` waits in the existing tool invocation using disposable
terminal subscriptions, with a five-second durable fallback and interruptible
Stop. It creates no polling model request, new pool or idle daemon. At most the
existing 128 assignment references are observed per call; excerpts are capped at
4,000 characters with explicit truncation. A timeout preserves running workers.
The same ordinary Coordinator loop then reviews evidence and arranges further
work under the original request. `review_project_work` pins the exact completed
result; its `actor=coordinator` never means human acceptance. An optional exact
registered checkpoint requests publication through existing integration gates.
`await_project_workers(wait_for=delivery)` observes the real delivery receipt.
`delegate_project_work` accepts the existing version-pinned `dependencies` and
`rework_of` shapes. They use the same dependency/review/publication admission;
no parallel graph executor is introduced. Pending review or delivery defers the
same grant, and changed result/checkpoint pins refuse execution. The graph reads
these durable links. `test_coordinator_dependency_links.py` exercises automatic
delegation, deferred replay, stale pins and exact rework links.
Unknown model/tool effects, source withdrawal and checkpoint changes still block
publication. A completed Worker or an accepted review alone never proves delivery.

Physical retries/resumes of the same accepted human input retain one source
cohort, idempotency identity, first issued Worker policy and shared allowance.
They recover, review and finish the earlier Workers; a new physical attempt
cannot hide unfinished work or reset its spending. A new human message can read
`get_project_workers(scope=project)` through bounded history pages and review or
cancel earlier Workers in the same live owner/tenant/Coordinator binding epoch.
Returned source Turn/current-request facts distinguish earlier objectives. Review
still requires live original authority and exact completed evidence; cancellation
never renews a grant. Synthetic continuations can read that history but control
only their original request. The alternatives—attempt-local status, treating a
new message as an empty project, or giving every synthetic continuation human
steering authority—lose continuity or cross the original authorization boundary.
`test_coordinator_worker_handoff.py` and its three-authority storage replay verify
resume/replay, completion, human steering, bounded history and synthetic refusal.

Cost defaults live in `project_dispatch_v1.schema.json`: each new accepted human
request receives 2,000,000 tokens, 128 physical model requests, 4,096 tool slots
and two hours across its initial Coordinator, Workers and automatic continuations.
A default Worker receives at most 250,000 tokens/16 requests/512 tools, narrowed
to remaining aggregate headroom. Explicit source execution limits narrow the
same allowance. Legacy tasks without a registered source receipt still refuse
automatic delegation under explicit token/tool limits. A deadline bounds every
related task. Tokens are an execution allowance, not a currency price guarantee.
Concurrency derives from the existing launch resource
probe, retaining a Coordinator slot; ordinary admission remains authoritative.
Exact retries reuse both conversation and grant; a changed brief/key payload
cannot silently create another execution. Old results remain passively readable.

### Conserved request allowance and user controls

Problem: independent accounts could exclude the initial Coordinator from the
Worker pool, and changing defaults or resuming an input could replenish spending.
Decision: the existing dispatch CAS also retains immutable `requestBudgets`, keyed
by accepted human Turn/projection and binding epoch. Each physical root account
has an immutable task/attempt/nonce. Task startup registers that receipt after
durable task binding and before spawning, inside existing rollback. Plan counts
its own usage while retaining the no-delegation rule. Every source send/slot
rechecks source, principal, binding, Stop and deadline. A new attempt on the same
human input keeps its original policy and cumulative consumption.

`ExecutionBudget` remains the sole physical admission owner. Optional composition
ports narrow pristine limits, expose aggregate output headroom, and observe every
reserved tool slot including slots whose executors never entered. Source model
intents, settlements and Worker grant reservations share one CAS. Final model
dispatch rechecks capacity after output reservation; races fail before provider
entry. Active Workers retain their entire grant, confirmed terminal usage releases
unused allowance, and uncertain usage retains at least its reservation. Reported
overshoot is recorded in full and blocks further admission; estimates cannot
guarantee a provider's final charge. Retries cannot reset counts or change terms.
No wallet, physical account, execution loop or background poller is added.
Alternatives rejected: summing only final usage races concurrent work; independent
per-Worker caps multiply spending; changing a running cap on a settings save would
silently expand the original authorization.

GET/POST `/api/v4/project/coordination/budget` use owner-scoped `conversations`
authority. GET is passive. POST checks the current binding and expected settings
revision; the separate defaults record affects only future new human requests.
Settings do not rebind, start, stop or resume any task. The conversation graph and
workspace show actual, reserved and available token/model/tool allowances; Manage
work contains the defaults editor. Existing project events/manual refresh update
the projection without idle polling, and passive refresh preserves dirty edits.
Unknown usage, unavailable reads, stale writes and save failures remain visible.
`get_project_workers` returns this same passive allowance projection to the
Coordinator, whose role guidance preserves headroom for review and reporting.
Focused guards are `test_coordinator_request_budget.py`, composed-budget and task
startup rollback tests, native Worker/restart/settings tests, the real budget HTTP
journey and `coordinator-budget.test.ts` plus the browser Coordinator journey.

Alternatives rejected: treating role binding as standing authority, forcing a
human click per Worker, copying a separate model loop, and repeatedly asking the
model to poll. Current scope is the original accepted human request;
standing missions and aggregate-only allowance reads remain outstanding.
Automatic continuation below uses the same finite request. Segmented persistence
retains assignments beyond the former project-lifetime limit. Verification includes
`test_coordinator_workers.py` and `test_coordinator_workers_authority.py`: native
Turn birth, ordinary file/shell tools, isolated Git delivery, report unread state,
exact replay and storage restart, without paid provider calls. The wait test
observes zero additional physical sends and zero retained terminal callbacks;
the native journey verifies the delivered worktree is reclaimed.

### Result-driven Coordinator continuation

Problem: a Coordinator can end its turn before the delegated request is done,
or lose its process while Workers are executing. Decision: the original human
request may issue a versioned, finite continuation policy during tool assembly.
Worker/Coordinator durable settlement, delivery notifications and existing startup
recovery derive internal `coordinator` grants in the same dispatch record. Old
policies never gain this authority. The ordinary command/Turn/task lane starts a
system-principal continuation; its input remains synthetic. No model loop, idle
poller, extra worker pool or shadow task state is introduced.

Each continuation reserves at most 250,000 tokens, 16 physical requests and 512
tools from the original 2,000,000/128 pool, with the same deadline. Only frozen
Coordinator tools are admitted; it has no file/shell execution or worktree.
It can delegate and review Workers using the original source, model, policy and
idempotency identities. Changed capability settings cannot enlarge that ceiling.
Human queued input retains priority. Duplicate notifications/CAS retries reuse
one grant and one ordinary birth. Failure wakes only the Coordinator policy and
preserves the existing skip-on-error rule for ordinary queued messages.

`get_project_workers` pages at most 32 thin owned assignment facts; full evidence
stays in ordinary conversations. `cancel_project_work` checks the human steering
or original-continuation boundary above and aborts the exact Worker attempt under
the existing publication lock.
`finish_project_request` requires a durable report Turn: `complete` requires all
non-cancelled Workers' exact accepted results, settled effects and confirmed
canonical delivery; `needs_user` requires a decision/blocked report. Its immutable
receipt and new delegation serialize in the same CAS. The receipt stops automatic
continuation; cancel unwanted active Workers explicitly before asking for input.

Three completed continuations without changed work/review/delivery evidence stop
with a deterministic blocked report, using no additional model request. Waiting
for active Workers is not counted as a stall. Expired/exhausted allowance is also
reported; unknown paid usage keeps its full reservation. Stop, binding withdrawal
and missing source evidence refuse further birth. Grants and continuation
receipts share the segmented project-head CAS and retain their own document bounds.

Alternatives rejected: treating a notification as human authority, adding a
second scheduler/task state, and reusing a generic queued message with mutable
capabilities. Verification: concurrent notification and finish/delegate races,
lane priority, authority withdrawal, bounded stalls, unknown consumption and
native storage restart in `test_coordinator_continuation.py` and
`test_coordinator_workers_authority.py`. Native restart runs one continuation
through ordinary tool assembly/model accounting/review, then actual Git delivery,
report unread state and durable completion; repeated recovery sends nothing.
Internal continuation rows produce neither Worker nodes nor human review cards.
Measured in the deterministic two-assignment fixture: 50 idle callbacks took
0.539 seconds, retained 5,470 bytes unchanged, and produced zero new births,
durable writes or threads. This is metadata-path evidence, not a provider latency
claim. The native journey checks real physical accounting separately.

### Conversation-first project entry

Problem: a small top-strip workspace button hid the bound Coordinator among date
buckets and made the management drawer feel like the primary work surface.
Decision: `project-coordination-surface.ts` owns a fixed sidebar card outside
Today/Yesterday groups. Its scope follows the selected folder (an unconfigured
folder never inherits another conversation's project), while the center follows
the active conversation. Clicking the sidebar entry opens the bound Coordinator
in the ordinary chat canvas directly, never a management dialog, including when
that conversation is outside the loaded catalog page:
`project-conversation-navigation.ts` resolves server metadata through the catalog
owner, then existing TurnStore hydration owns the transcript. Later navigation
or a new draft fences late reads.

An unbound card offers **Create project Coordinator** explicitly; it calls the
create/bind facade only on click, disables duplicate clicks, shows errors
for retry and requires a selected project folder. Opening an ordinary chat never
promotes it. Historical same-project chats cannot be selected as Coordinator.

Problem: a folder click cleared the sidebar container and painted the card only
after the binding read resolved, so the conversation list jumped up and back
down while the entry popped in late. Decision: every project/folder switch paints
the card shell synchronously (`aria-busy`, localized loading line) before the
read starts, and the surface retains the last resolved Coordinator per project so
a return visit paints the real identity — and the list filters that conversation
— on the first frame. A failed read converts the pre-painted shell into the
error state instead of collapsing the container. A taller skeleton, a fixed
spacer, or hiding the entry outside a bound Coordinator were rejected: the first
two still shift the list, and the third removes the only route into an unbound
project.

The bound chat shows a compact work list, eight rows per visible page. The
recorded dependency graph is collapsed and mounted only on disclosure, preserving
space for conversation and composer. The user's fold state survives live
refreshes. **Manage work** explicitly opens
the demand-loaded management dialog; it is not the primary navigation action.

Problem: repeated completion/failure labels and status lanes buried the actual
work and did not show who delegated it or which result another task needs.
Decision: `project-coordination-work-list.ts` renders actionable, bounded work
rows first; `project-coordination-canvas.ts` exposes the optional graph as
selectable Coordinator/Worker nodes. Dashed delegation, solid dependency and dotted rework
edges describe only recorded relationships. The Coordinator remains the root
while its conversation is open. Historical Board records without assignment
links remain unconnected; the UI never guesses relationships from titles or order.

Current work and its prerequisites are visible first. Unrelated completed/cancelled
history is an explicit disclosure, and the selected node stays visible when it
finishes. Selection reveals result, dependency, revocation and delivery evidence
and an action opening the ordinary Worker conversation. Counts and coverage are
secondary disclosed information. Project-local selection, history and bounded
zoom survive push refreshes; a project change clears them. Container queries
select matching one/two/three-column card and SVG geometry without observers,
new polling or model calls. Native scrolling preserves readable node sizes on
narrow screens. All controls use the shared kit; EN/ZH labels, keyboard access
and three themes share the same view. The fixed sidebar entry remains navigation.
Long titles occupy at most three lines and result digests one line inside each
fixed-size node; the selection inspector preserves the full title and detail.
Its conversation action wraps within narrow panes. Expanding node height was
rejected because it breaks the shared node/edge geometry; truncating stored
content would discard evidence. Browser coverage includes long localized text
inside the ordinary conversation summary, not only an isolated graph.
Alternatives rejected: a graph-first display makes routine status expensive to
scan; eliminating the graph loses dependency evidence. An LLM-generated chart
adds cost and can invent state; another conversation renderer duplicates Turn
ownership. SVG lines and ordinary DOM controls preserve accessible actions.
Ordinary chats have no Worker role label and no top workspace shortcut; actual
related-work evidence alone can offer a return-to-Coordinator link. The card is
not duplicated in date groups. Alternatives rejected: automatic current-chat
binding, a second chat renderer, and a new polling loop. Project push invalidation
coalesces reads; stable facts retain DOM/focus and expanded state. These are source
contracts, not claims that a running service has loaded this checkout.

### Proactive reports and durable attention

Problem: an unseen result in a Worker chat or a volatile notification cannot
reliably tell the human that the Coordinator needs a decision or has delivered.
Decision: the bound Coordinator's `report_to_user` tool publishes a concise
`progress`, `decision`, `blocked` or `delivery` report as an ordinary assistant
Turn in its own conversation. The title is at most 120 characters; the plain
text message is at most 4,000. Role guidance asks for meaningful milestones,
decisions, blockers and verified delivery, rather than every status change.
Reporting grants no authority and never implies human acknowledgement or consent.

`coordinator_reports.py` first retains an immutable publication intent, then
uses a stable canonical Turn command, updates one latest-report/read pointer,
and retires the transient intent. The existing project startup recovery pages
through pending intents; it never invokes a model or creates a task. Lost
acknowledgements, concurrent identical sends and restarts reuse the same Turn.
A changed request under an existing key is rejected without poisoning later
original retries. Older retries cannot replace newer attention or rearm read
messages. Owner, project, Coordinator identity and binding revision are checked;
replacement withdraws pending transport while preserving old conversation history.
Reports can be ingested during the ordinary Coordinator attempt without replacing
that attempt or preventing its settlement.

The sidebar's fixed Coordinator entry shows an unread dot and the latest title.
Clicking it opens the ordinary conversation. A compact disclosure above the node
graph exposes the report and an explicit **Mark this message as read** action.
The read command captures the displayed Turn ID and binding revision; a stale
tab reading A cannot clear newer B. Fetching, mounting, opening the disclosure
or navigating never acknowledges a message. Failed refreshes retain known
attention only within the exact binding, show a retry, and do not invent read
state. Project/conversation push events are refresh hints; reconnect/reload reads
the durable projection. Full report history remains solely in canonical Turns.
No new timer, subscription transport, worker or polling model call is introduced.

Alternatives rejected: local-storage badges lose cross-session state; clearing
the latest pointer on navigation can discard unseen concurrent reports; a
separate inbox transcript duplicates the conversation authority. Verification:
report race/recovery specifications, real registered tool pipeline and HTTP
journeys, SQLite and source-matched native restart/active-attempt checks, and a
real browser journey covering push while another chat is open, exact reading,
reload, three themes and widths down to 320 px. Storage uses one `project.coordinator.reports.v1` head per
owner/project and `project.coordinator.reports.pending.v1` intents until confirmed
publication or binding revocation. The existing recovery lifecycle reads at most
32 intents per page; it adds no resident queue or cache. UTF-8 shape measurement
with a 4,096-character project path, 256-character conversation/Turn IDs,
120-character title, 4,000-character body and 200-character retry key measured
17,557 bytes for the head and 34,069 per intent (four-byte characters in
path/title/body/key). These are record-shape measurements, not latency/RSS claims.
The 33-intent recovery test verifies page advancement and retirement to one head;
completion deletes transport records, never messages.

### Stable capabilities, discoverable conversations and diagnosis

Problem: permitted Coordinator tools were absent from default keyword-routed
wire schemas and had to be rediscovered on every new task. Decision:
`coordinator_policy.prepare_coordinator_tool_surface` derives required-direct
exposure from the existing role policy intersected with the **post-gate**
executable catalog. Assembly applies it to genuine bound roots and validated
continuations, not ordinary chats, foreign owners or transient children. It
preserves Plan/readonly/selection/authorization checks and does not expand a
worker's issued tool scope. Alternatives rejected: making tools global `_ALWAYS`
entries grants irrelevant visibility; a separate role whitelist drifts from
execution authority. `test_coordinator_tool_surface.py` verifies actual wire
schemas, retries, discovery modes and negative authority cases.

Problem: assignment inventory, conversation inventory and actual execution were
conflated, hiding zero-Turn workers. Decision: persisted empty catalog entries
remain navigable; transient local drafts retain their existing cleanup. Search
hits never stand in for full metadata: exact-ID navigation hydrates canonical
owned metadata before activation and does not move the global paging boundary.
Prefixed coordinator/worker IDs participate in instant local ID search.

`GET /api/v4/project/coordination/conversations` supplies the passive roster from
`coordinator_conversations.conversation_page`. One call reads at most 64 metadata
headers through the selected authority, filters owner/project/archive scope,
and returns a scope-bound keyset cursor and explicit coverage. Empty matching
pages may still have `nextCursor`; they are not evidence of no workers. No
transcripts, new worker store, grants, model calls or execution are created.
The UI replaces each roster page on demand, joins assignment recipients, and
never silently truncates a lifetime inventory. A zero-Turn shell without an
assignment is **Not started**, never queued. Other history remains distinct.

Every coordinator/work row exposes a copyable reference and inspectable IDs
without Debug mode. **Ask assistant to diagnose** prepares an ordinary visible
read-only-project draft containing the exact conversation/project references.
It never auto-sends or overwrites existing text/attachments. Normal conversation
navigation and Turn rendering remain the sole owners.

Context organization and a fresh working view are distinct from coordinator
replacement. No safe idle fresh-view command currently exists: manual compaction
folds canonical Turns used by authorization/report references. The management
surface explains that organize/fresh actions are unavailable rather than
calling `/create` as a fallback. The shared compaction service and persistence
adapter reject protected Coordinator contexts before summary work and again at
canonical application; see `CONTEXT_COMPACTION.md` for conservative project
protection and the remaining historical-reference limitation. **Replace
Coordinator** lives under management, explains preserved history and invalidated
old authority, requires confirmation, then rereads binding before CAS. Read
failure has a read-only retry, not an automatic repeat of replacement.

### Fresh Coordinator backend guarantee

Problem: selecting a historical chat imports unrelated conversation context, and
revision-derived candidate IDs could cause creation to adopt a pre-existing chat.
Decision: `/create` at the current binding revision creates a new ordinary empty
conversation with a fresh identity and only canonical project/folder settings,
then CAS-binds it. It never scans or copies historical chats, transcripts or
settings. A pre-existing identity or failed create fails closed, never becoming
proof of ownership of the candidate. Creation starts no execution.

An explicit current-revision create can replace an already available Coordinator
without deleting or altering the old conversation. GET is read-only. Existing
valid bindings remain usable on restart; stale create retries return the current
available binding without allocating another chat. Stale unavailable bindings
conflict. `/bind` now only clears a binding or reaffirms its current available
ID; selecting another existing chat returns 400. Clearing uses revision CAS.
Existing clients offering historical selection must use explicit creation instead.

Alternatives rejected: automatic current/latest-chat binding contaminates context;
checking that a historical chat is empty still adopts user-owned history; predictable
candidate reuse can adopt an orphan that gained content. Creation and binding
remain separate storage commands: each attempted create allocates at most one
empty conversation, and a failed binding CAS can leave that chat unbound. Retries
never adopt it or delete user data; concurrent requests cannot replace a newer
binding because CAS retains authority. No background loop or cleanup worker is
added. Narrow guards: `tests/project_mod/test_project_coordination.py` and
`tests/api/test_api_v1_project_coordination.py`.

The demand-loaded workspace uses the project's native dialog and shared tabs:
overview, team, messages, files/delivery and work management. Overview separates
failed work, active work and results, and projects review/dependency/delivery
attention from existing assignment facts. Completion alone never means delivered.
Team cards open the ordinary conversation canvas, including conversations with
no work record. The same project entrance returns users to the Coordinator.
Temporary child interaction remains in the existing Swarm/agent surfaces.
Management forms and file/message reads mount only when disclosed. Committed
project events refresh the open overview; demand accumulated on another tab is
read on return without remounting forms or message pagination. Only one workspace
read runs at a time; events during that read coalesce into one follow-up. Unchanged
rendered facts retain their DOM; changed cards restore focus by work/assignment ID.
Background failures keep the workspace usable with a visible retry. Closing
disposes the subscription and pending refresh timer. A failed board or assignment
read is shown as unavailable, not an empty project. The shared graph projection
in `project-coordination-graph.ts` renders task nodes linked to their ordinary
worker conversations. Recorded assignment dependencies and rework links are
explicit edges; dispatch links are visually distinct, and layout never implies
a timeline. A separate Coordinator node dispatches and tracks; its own work is
excluded from worker execution progress.

Assignments are the primary graph evidence when present. Otherwise the graph
shows observed work with an explicit coverage caveat: Board work IDs and assignment
IDs have no shared public task identity, so they must not be summed or guessed to
be duplicates. Queued/running/completed/failed/cancelled/blocked/unknown remain
distinct. Unknown prerequisites and missing references remain visible. Progress
counts completed tasks against displayed tasks, not a fabricated whole-project
percentage; unavailable progress is never 0%. Delivery requires both canonical
receipt confirmation and delivered status. Review/dependency/delivery decisions
remain separate management actions. Assignment-only status changes invalidate
the graph even when observed work and decision counts stay unchanged.
The setup action creates a new empty Coordinator instead of selecting an old chat;
previous conversations are preserved.

Workers now use `send_agent_message` / `get_agent_messages` for exact-run team
communication. Original server-stamped identity and the live child assignment
fence sends; worker-to-worker messages and interim reports to a running root
reuse the same durable run mailbox and verified-input receipts. The root target
is `agent_id == swarm_run_id`. A worker cannot activate retained agents, change
permissions or wake an idle root. See [team identities](RETAINED_AGENTS.md).

Alternatives rejected: a second supervisor engine duplicates cancellation and
budget authority; independent worker chat widgets duplicate Turn rendering;
putting all operational forms before status makes ordinary coordination harder.
Trailing-edge debounce can starve updates under continuous events; overlapping
reads waste work and full background rerenders discard user input and focus.

Resource impact: no new idle executor or poller. A bound root pays one extra
binding/owned-conversation lookup per context assembly and at most 600 role
prompt tokens. The open overview reads binding, board and existing assignments;
project pushes coalesce in a fixed 300 ms window. The slow-read regression sends
10 events across one second: one refresh starts at 300 ms, concurrency stays one,
and all events during it produce one follow-up. No timer polls while idle or on
another tab. Board input groups cap records at 100 each. Team/roster uses explicit
page navigation instead of a silent 100-entry slice; visible lists render eight
rows at a time. An opened workspace requests one bounded roster page alongside
existing reads; no roster reads occur merely to display the fixed sidebar entry.
Assignment history loads one page of at most 32 owned records;
the graph retains a defensive 128-node input ceiling for other callers.
For 128 assignments with up to eight prerequisites each, the default work-first
view measured 146 DOM elements and zero mounted graph nodes. Explicitly opening
topology renders 128 assignments plus the Coordinator: Chromium measured 4,156
DOM elements and about 55 ms for the combined initial render/expansion/layout,
with a 480 px viewport. The browser gate bounds the default view below 400
elements and the expanded view below 5,000. Only one responsive wire layer is
visible; no observer or timer is allocated.
This is a local layout measurement, not a universal latency promise.
Browser tests cover 1440/390/320 widths and all three themes; unit/pipeline tests

Decision: portable record CAS stores passive originals and consideration without

Alternative rejected: heartbeat-only guards cannot protect startup/completion drains.

executor birth or delivery. Causal replies must identify an actual incoming
message from the addressed sender. Queries never read private transcripts.

admission, and at the canonical prepared-input physical-attempt boundary. This is not a persistent conversation

## Input receipts and recovery limits

Exact carrier text is matched only in input-bearing fields. A request-local
observer composes with the existing model-budget attempt lease, and revalidates
scope against sealed translated input after dispatcher waits and before provider
ingress, including floor resends. This adds no second budget/dispatch owner.
Tool descriptions, routing and metadata cannot prove consumption. Only matches
from the selected verified response become eligible for ACK; failed/dropped input
cannot inherit previous IDs. Unobserved custom transports produce no physical
receipt. This does not independently prove serialized-wire identity after every
possible downstream adaptation. Credential recovery, when present, must wrap
per-attempt receipt validation, never the reverse. Local delivery failures retain
the original cause, not a provider fallback; the shared-runtime composition
specification executes only where those owners are present.

Validation is not atomic with the network send: a revocation immediately after
checking can race ingress. Relay/proxy-internal retries need their own enforcement
and are not claimed here. A scope-denied floor resend records already-known paid
usage as non-authoring discarded rounds; it cannot trigger another route or ACK.

Receipt ACK loss remains unknown: no persisted successful-request pending-ACK
outbox exists. No new paid request is purchased to reconcile a receipt. The exact
turn/attempt/task occurrence is recorded where available. Neither input confirmation,
consideration, task completion nor canonical delivery implies the other facts.

## Explicit-human bounded dispatch

The dispatch schema owns request, grant, assignment, admission, physical-attempt
ledger and review/view DTOs. An owning human with `chat` scope explicitly submits
a coordinator human turn and exact projection revision, distinct same-project
recipient, brief, model, token/request caps and Unix-second deadline. Admission
rechecks owner/tenant, canonical project, available coordinator binding, current
source revision/human provenance and grant revision/revocation. Synthetic input
is not authorization. The recipient is a system/chat principal, unattended and

brain-attributed; the ordinary user identity contract is not relaxed.

New grants pin the original positive coordinator binding revision. Every birth,
physical admission, dependency-evidence and publication gate checks that epoch;
A→B→A rebinding cannot restore old authority. Idempotent replay retains its old
pin. Legacy unpinned grants remain readable but cannot acquire fresh paid/file
admission or be upgraded in place; a new explicit human command is required.
Finite responsibilities also freeze their original binding epoch before triggers.

A scoped idempotent command maps to one assignment and the existing deterministic
conversation command, then an immutable turn/attempt association; task identity
and result status come from that attempt. Binding precedes executor birth.
The existing command/start handshake owns execution, lane-idle admission and
queued-human priority. Busy/superseded dispatch is deferred. After the existing
human/background queues drain, the lane-settlement callback retries the same grant;
startup discovers persisted owner/project records through existing cursor pagination.
Only new `lifecycleVersion=1` grants auto-retry; legacy evidence remains readable,
not automatically upgraded. Exact-command retry cannot buy a second execution.

`ExecutionBudget` remains reservation/settlement authority. Its physical-attempt
observer persists `dispatch_intent/settled/voided`, root/attempt task IDs, ordinal,
reserved/reported tokens, usage completeness and an account nonce. Retries share
the grant caps. Unresolved intent, incomplete paid usage or former-task usage
blocks new spending; restart/account recreation does not replenish authority.
Every settlement must retain its nonce and occurrence identity; even an unsent
settlement cannot void durable uncertain intent. Live authority is revalidated
before physical admission; this is not atomic network revocation or provider
exactly-once. Consultation still exposes no tools. An explicit `files` profile
names only first-party `read_files/write_file/edit_file`, relative read/write
prefixes and a tool cap. Write prefixes must permit preimage reads; `.` is an
explicit whole-project prefix, never a directory scan or metadata exemption.
Tool admission and nonce-bound durable occurrences conserve the same authority.
Shell, recursive indexes, PTC, MCP, remote/ref adapters, plugins, children and
paid auxiliary compaction/translation stay closed. `autoTranslate` is forced false.

Problem: a tool name/path string alone can borrow a plugin, alias or canonical
checkout. Decision: pin the exact first-party handler, bind the physical task's
registered isolated workspace, and use anchored directory descriptors, no-follow
regular-file I/O, byte-exact preimages, durable undo and cooperative target leases.
Ordinary tasks default to direct execution, but dispatched file workers always
retain isolation, including with `TOFU_WORKSPACE_MODE=direct` or local
`tofu.workspaceMode=direct`; those settings cannot bypass review/publication.
Recheck live authority and workspace ownership at I/O/publication. Reads consume
complete UTF-8 text; writes and exact preimage capture have no private byte quota.
Every explicit read/edit batch entry is admitted by its path/tool grant, not a
20/30-entry ceiling. Explicit human call allowances remain authoritative.
Runtime, Git, credential and cache paths are refused even under `.`. Alternatives
rejected: opaque programs and generic converters cannot be safely path-fenced.
This is not an OS sandbox against privileged external reparenting after the final
ancestry check; those writers remain outside cooperative containment.

Revocation uses grant-revision CAS and cancels the bound existing attempt; a
repeat retries the same cancellation after ACK loss. Human Stop remains the
existing turn/attempt cancellation authority, not natural-language steering.
Neither late reports nor read/recovery reactivate stopped or revoked work.
Review requires the current completed result revision and records immutable
`accept/rework/reject` evidence; it does not change task completion or grant
revision. `reworkOf` links the exact old grant/result and immutable rework review;
execution requires a fresh human source, command, model and budget, not renewed
old authority. Stop entry points durably withdraw existing referenced grants;
TTL expiry, late reports and boot/idle retry cannot restore withdrawn authority.

Stop also stores one monotonic owner/conversation watermark in the declared
`stopNamespace`, independent of current project metadata. Admission checks two
point reads; this prevents restoring an old project from restoring authority.
Human attempt/queued/task/registry-miss Stop paths record it; exact-grant internal
cancellation does not withdraw peer grants. Storage failure is not a durable-Stop ACK.

Problem: automatic completed-file delivery would precede review. Decision: stamp
the assignment admission into initial workspace registration and hold all
initial/no-change/recovery/postgate publication paths. Acceptance remains review
only. Explicit `/publish` pins grant, result and `expectedCheckpointSha`; existing
Git gates and `origin.delivery` own publication. Final fresh checks run under the
same repository lock used by grant revocation, before intent and apply/fast-forward.
Changing the checkpoint cannot reuse an old publish request. No new delivery store
or worker is introduced. `canonicalDelivery=true` derives only from the exact
owner/project/task-matching durable `delivered` receipt, not completion, acceptance,
candidate `merged` or a publish request. Automatic byte delivery need not change HEAD.
Alternatives rejected: acceptance-as-publication and UI-only fencing lose authority.

## Atomic bounded conversation batches

Problem: individually approved fan-out can persist half a plan after a failed
last admission and has no immutable original goal or aggregate allowance.
Decision: `ProjectDispatchRepository.authorize_batch` commits one manifest and
all ordinary child grants in the existing owner/project CAS. The machine
contract adds `batchRequest`, `batchRetry`, `batch` and `batchView`; manifests
share the segmented project-head CAS. A batch names 1..8
**existing distinct conversations**, the original objective, one genuine human
source, exact worker briefs/models/profiles and finite aggregate tokens/model
requests/deadline. Child ceilings are allocated before any execution; their sums
cannot exceed the aggregate, and deadlines cannot outlive it. Unused allowances
never transfer or renew. The common binding epoch and immutable manifest/member
requests are checked on every record read. Each child receives the original
objective and its responsibility in its existing bounded immutable brief.

Exact command replay returns the original manifest even after revocation,
expiry or rebinding; it does not restore execution authority. Changed objective,
worker order, budget, source or granter conflicts. Admission is atomic;
**physical launches are not**. The service submits independent asynchronous
ordinary conversation commands without a threadpool or waiting for results.
Human-queued/busy lanes defer. A failed or lost launch reply is `unknown` with
`dispatch_unconfirmed`, not definite rejection or successful completion; exact
turn/attempt evidence remains independently inspectable. Existing lane-idle and
startup drivers recover eligible child grants, never mint replacement grants.
Each child retains Stop, live budget, scope, review and publication gates.

Public v4 routes: POST `/project/coordination/batches` authorizes and dispatches
with `Idempotency-Key`; GET the same path with exact `path` and `commandId`
reads `{batch: ... | null}` without wake/write/spending; POST `/batches/dispatch`
retries only `{projectPath, batchId}`. A null read cannot prove no in-flight
write. All batch endpoints require the owning human principal with `chat` scope.
The current-request delegation tool above has a separate internal admission port.

Batch admission alone is not a complete autonomous supervisory loop. Current-request
delegation/review and result-driven continuation reuse ordinary Coordinator Turns
under the original policy; standing renewal is not implied. Evolution's private goal spokesperson remains separate;
its journal assignments do not authorize project work. Alternatives rejected:
serial grant writes lose all-or-none authorization; a new persistent scheduler
splits lifecycle authority; batch acceptance-as-success erases partial starts.
Focused guards: `test_project_dispatch_batches.py`,
`test_project_dispatch_batch_service.py`, `test_project_dispatch_batch_routes.py`.
No provider, deployment or multi-day autonomy proof is implied by these tests.

## Bounds and cost

One original owner/project/recipient mailbox holds at most 128 originals, each
4096 characters / 16384 UTF-8 bytes, plus a 2048-character consideration note.
Worst-case body content is 2 MiB before JSON/framing and notes. This is a lifetime
history cap, not unread backlog. Overflow rejects without eviction, even after
consideration; no archive/rollover command exists. Pagination does not reclaim
capacity. Durable segmented history is needed for unbounded ongoing responsibility.

Each active configured project round performs scoped metadata and a point read,
not an owner-wide scan. A directory shows 20 previews of 256 characters with a
stable-ID backward cursor; exact-ID tool lookup retrieves the original. Input
selection defers whole messages using token/headroom and escaped-byte budgets.
Final canonical prompt admission still owns total cost. Idle adds no executor.

Dispatch retains up to eight CAS retries, eight direct dependency references,
64 physical model requests and 512 tool occurrences per grant (or its lower
explicit caps). A dependency projection memoizes reachable predecessor evidence
and bounds one chain at 128 nodes / 1024 edges. No dependency work runs while idle.

`ProjectDispatchRepository` selects the persistence boundary in
`contracts/project_dispatch_storage_v2.json`. Problem: raising the 128/4 MiB ceiling retains
whole-history rewrites on every model receipt and eventually exhausts memory.
Decision: keep domain policy in the repository and provide an owned atomic
head CAS plus individually versioned assignment, request, account, occurrence,
batch, settlement, scope-change and index documents. Both authorities execute the same
transaction; native compilation reuses existing versioned-document IR. A late
child conflict rolls back the head, earlier children and command receipt.
Alternatives rejected: larger monolithic records; deleting settled evidence;
independent per-row writes that can split admission from reservation; a second
budget/task store; and a generic multi-record write API without domain ownership.

The port has no project-lifetime row limit or background activity. One commit
accepts at most 512 document changes and 8 MiB of document JSON; point documents
remain at most 4 MiB, head state 16 KiB, index summaries 2 KiB. A page returns
at most 64 index summaries or evidence headers, never a collection of large
evidence values. Cursors use exact owned ASCII prefixes and bytewise order.
SQLite uses its existing primary-key range; SQL schema 68 installs a private
PostgreSQL C-collation partial index through the explicit migration lifecycle.
Native uses its existing entity range. Generic record operations refuse both
private namespaces. Only reconstructible indexes support deletion.

`tests/storage/test_project_dispatch_segments.py` exercises real SQLite,
PostgreSQL and native authorities: more than 128 retained documents, bounded
history pages, exact receipt replay, late conflict rollback, two racing grants,
owner/project isolation, namespace bypass refusal and native full reopen.
`segmented.py` migrates only on mutation or lifecycle recovery. It first freezes
the original v1 record with its exact CAS; old pending writes conflict and old
readers reject the marker. Bounded copy transactions retain every grant, receipt,
batch and scope change. Queries use the frozen original until the complete copy
is committed. Only then is the redundant original removed and the head activated;
the small owner/project locator remains. Lost acknowledgements at every phase
resume without granting twice. No backend switch, new task or resident worker
is involved. Startup isolates a failed import to its scope.

Point reads, execution binding and ordinary receipt updates address exact
documents. Source and request indexes select only their cohort; immutable count
witnesses detect missing index entries before allowance reduction. Changes to
grants, source cardinality and request cardinality commit together under one
head witness. Reads retry a changed witness and perform no writes. The 512-change
transaction preserves atomic withdrawal of the existing 128-target scope limit.

Domain verification covers 160 retained assignments on all three authorities,
four cutover crash boundaries, exact legacy model/execution preservation,
concurrent first mutations, and missing-index refusal. Actual SQL conservation
tests include live source/Worker migration and 132 successive ordinary Worker
conversations under one request with unused allowance released. Provider/Turn
completion is controlled in this count test; it is not paid model throughput.

A disposable strict-native repository probe compared 32 and 1,024 retained
assignments. Twenty point-read plus receipt-update cycles at each size used six
queries per cycle, no history scan, and at most 1,324 / 1,330 command bytes.
With Python allocation tracing enabled, mean cycle times were 13.020 / 13.024 ms
(p95 13.257 / 13.243 ms), with 102,658 / 105,906 peak traced bytes. This includes
domain schema validation but excludes provider execution and request-cohort
aggregation; it is a component scaling observation on disposable local storage.

Remaining scaling limits are explicit: full recovery readers still
materialize project evidence; accounting loads the current request cohort;
source account/occurrence receipts remain inside a request document. Segmentation
and paged presentation remove the project assignment ceiling and silent browser
truncation, not these recovery/accounting or per-document bounds.

The source-matched native probe (strict durability, disposable local `/tmp`
authority, 20 point-read plus single-document commits at each size) measured
0.829 ms mean / 1.078 ms p95 at 32 assignments and 0.801 ms / 0.908 ms at
1,024. Maximum command payload was 1,263 / 1,265 bytes; the capped index page
was 6,592 / 13,184 bytes for 32 / 64 rows. Python client allocation peaks were
45,275 / 39,503 bytes. This measures the storage port; provider execution,
repository cutover, graph rendering and network-volume latency are separate.
Verification includes all 27 segmented-operation cases across three authorities,
two SQL migration/index-plan cases, 69 Coordinator unit cases, six native
Coordinator/report journeys and 2,005 native library tests (nine existing skips).

The Stop record is overwritten monotonically, never appended: one bounded
owner/conversation/timestamp object (conversation ID ≤256 characters) per stopped
conversation. It adds no thread, pool or timer and is not reclaimed by a TTL.


Scope changes retain at most 128 changes with 128 pinned targets each and a
256 KiB per-change byte gate;
there is no evidence eviction. Responsibility holds at most 32 definitions,
128 occurrences each, eight CAS attempts and a 4 MiB record. Every occurrence
keeps its full declared debit, even on unknown ACK. The existing automation
capacity probe sizes execution; no new idle worker is added.

Shared files retain at most 128 metadata entries in 512 KiB. One demand page
has at most 16 entries / 64 KiB serialized metadata; each declared probe/read
has a 256 KiB content ceiling. A full page may read at most 4 MiB sequentially,
not retain that content in the index. Overflow fails without deleting evidence.
These are executable capacity bounds, not an invented measured latency SLA.

## Complete scoped file work

Problem: file-only dispatch had independent 512 KiB reads, 16 MiB write/preimage
limits and 20/30-entry input ceilings after ordinary project tools stopped
using those quotas. Decision: descriptor-fenced first-party execution consumes
complete granted sources and every explicit operation. `FileScope.read` has an
unbounded default; an explicitly supplied read limit remains supported by its
caller. Regular-file checks, write hard-link rejection, ancestry/inode matching,
live grant/owner revalidation, lexical prefix membership, freshness and durable
undo remain separate authority requirements. No generic converter, shell,
plugin or trusted recovery authority is borrowed by a file grant.


Scoped read evidence binds the bytes actually returned by the descriptor to the
owned root identity. Explicit ranges beyond EOF fail before any batch observation
is published; an unranged read of an empty file remains valid. A failed later
read or source binding does not certify earlier, undisplayed batch items.

Scoped `edit_file` shares ordinary edits' compute-only matcher and accepts the
same batch-level `path` as the unscoped tool: an edit takes the batch file
unless it names its own, and every edit must still resolve to a file inside the
granted prefix or the call is refused before any I/O. It defaults to
whole-batch `atomic: true` preflight: all file reads, operations, freshness checks
and common journal admission complete before the first requested publication.
An invalid plan returns failed/skipped receipts in original request order,
without file or undo changes. Only an explicit boolean `atomic: false` enables
partial application. Descriptor-fenced I/O, exact grant revalidation and the
pending-recovery refusal remain mandatory. This is not cross-file rollback after
a later I/O failure; see [the write contract](PROJECT_FILE_UNDO.md).
Alternatives considered: larger constants repeat valid-work refusal; using
generic project fallback bypasses the descriptor and grant fence. The existing
caller-owned byte buffer remains proportional to the source; this does not
claim constant memory or grant additional tools/calls.
